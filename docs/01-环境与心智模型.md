# 第 01 章 · 环境与心智模型

> 第 00 章讲了 Python 的"价值观"，这一章讲 Python 的"物理世界"：它到底由哪几块拼成、
> 你怎么在电脑上把它跑起来、以及你脑子里那套 JS 经验哪些能直接用、哪些必须重来。
>
> 本章你需要记住的就一件事：**Python 不是"一个程序"，是"语言规范 + 解释器 + 标准库 + 包管理"四样东西的合体，
> 而 `venv` 是你写任何项目前第一件要建的东西。**

## 1.1 Python 到底是什么：四个东西的合体

先给结论：**当你嘴里说"我装了 Python"，你其实装了四样东西。** 别把它们混为一谈，混了后面全乱。

| 组成 | 是什么 | JS 世界的对应物 | 举例 |
|---|---|---|---|
| **语言规范** | 一套语法和语义的"规矩" | ECMAScript 规范 | 缩进、`def`、`list`、异常 |
| **解释器** | 把 `.py` 文件跑起来的程序 | Node.js（V8 引擎） | CPython（最主流）、PyPy |
| **标准库** | 随解释器一起装好的模块 | Node 的内置模块 | `json`、`os`、`math`、`sqlite3` |
| **包管理** | 装第三方库的工具 | `npm` | `pip`、`venv` |

这四个东西里，**最容易被新手误解的是"解释器"**。在 JS 世界里，你写 `node index.js`，
`node` 这个程序负责把你写的 JS 执行出来。Python 完全一样——你写 `python hello.py`，
`python` 这个程序（它有个名字，叫 **CPython**）负责执行你的 `.py`。

### CPython 这个名字什么意思

`python` 命令背后跑的程序，全名是 **CPython**，它是"用 C 语言写的 Python 解释器"。
名字里的 **C** 就是"用 C 写的"这个意思，跟"蟒蛇"没关系。

你之所以要知道这个名字，是因为 Python 的"解释器"不止一个：

| 解释器 | 特点 | 什么时候用 |
|---|---|---|
| **CPython** | 官方默认，最主流，生态 100% 兼容 | 你 99% 的时间用这个 |
| PyPy | 带 JIT，某些场景比 CPython 快几倍 | 纯计算的性能敏感场景 |
| Jython / IronPython | 跑在 JVM / .NET 上 | 基本是历史遗留，别碰 |

**默认情况下，`python` 命令指向的一定是 CPython。** 本教程也只讲 CPython。
所以后面提到"解释器"，你直接理解成"CPython"就行。

### Python 是怎么执行你的 `.py` 文件的

很多从 JS 过来的人以为 Python 是"一行一行解释执行"的，其实**不是**。它有个"半编译"的过程，
了解它对理解后面的报错时机很重要。

你运行 `python hello.py`，CPython 内部大致走三步：

1. **编译**：把 `hello.py` 的源码编译成**字节码（bytecode）**，这是一种中间表示，不是机器码。
2. **缓存**：字节码会存到一个叫 `__pycache__` 的目录里，文件后缀是 `.pyc`。
   下次再运行同一个文件，如果源码没改，就直接复用 `.pyc`，跳过编译。
3. **执行**：CPython 的"虚拟机"逐条解释执行字节码。

所以 Python 常被说成"解释型语言"，但准确说是"**编译成字节码，再由虚拟机解释执行**"。
它和 Java 有点像（都是先编译成中间码），但区别是：Java 要你**手动** `javac` 编译，
Python 是**运行的时候自动**帮你编译缓存，你完全无感。

这个模型解释了三个你可能会观察到的现象：

- **`SyntaxError` 在"编译"阶段就报出来**，所以哪怕代码一句都没执行，只要有一处语法错，整个文件直接拒绝运行。
- 项目里莫名多出来的 `__pycache__` 目录，就是字节码缓存，可以放心删，也可以加进 `.gitignore`。
- Python 慢，一部分原因就是"运行时还要解释字节码"，不像 C 直接是机器码。

你此刻不用深入字节码长什么样，只要知道：**报错分"编译期"（SyntaxError/IndentationError）和"运行期"（TypeError/NameError）两类，前者在你程序跑起来之前就拦下你。**

### 标准库：为什么 Python 不用装任何东西就能干很多活

这是 Python 和 JS 一个巨大的差异，值得单独拎出来说。

在 JS 里，你要读写文件、处理 JSON、发 HTTP 请求，第一反应是 `npm install` 一堆包。
**在 Python 里，这些大部分"开箱即用"，因为标准库把常用的都内置了。**

你装好 Python，立刻就能用这些，**不需要任何 `pip install`**：

```python
import json      # 处理 JSON，对应 JS 的 JSON.parse / JSON.stringify
import math      # 数学函数
import os        # 操作系统接口（路径、环境变量）
import sqlite3   # 内置的 SQLite 数据库
import datetime  # 日期时间
```

在交互式解释器里跑一下，验证它们确实"免费"：

```text
>>> import json
>>> json.dumps([1, 2])
'[1, 2]'
>>> import math
>>> math.sqrt(16)
4.0
```

**为什么标准库这么重要？** 因为它直接改变了你写代码的习惯：JS 里"先 `npm install` 再说"，
Python 里是"先想想标准库有没有，没有才去 `pip install`"。这是本系列贯穿始终的一条原则——
**能用标准库就别引第三方**。第 00 章承诺过"核心章节零依赖"，靠的就是标准库够肥。

### 第一件事：确认你的环境真的能跑

在往下看任何东西之前，先花 30 秒确认你的环境是好的。打开终端，敲：

```bash
python --version
```

应该看到类似输出：

```text
Python 3.13.14
```

只要第一个数字是 **3**，第二个数字 **>= 10**，本教程的代码就都能跑（`match/case` 需要 3.10+，
f-string 需要 3.6+，本教程基于 3.13 实测）。

然后写你的第一个 Python 文件。随便建一个 `hello.py`，内容一行：

```python
print("hello, python")
```

运行：

```bash
python hello.py
```

```text
hello, python
```

**看到这行输出，你的 Python 环境就是通的。** 如果连这都报错（比如 `python 不是内部或外部命令`），
说明 Python 没装或者没加进 PATH，先去官网 python.org 下载安装，勾选 **"Add Python to PATH"** 那个复选框。

> 一句话记住它：**"装了 Python"= 装了一套语言规范、一个 CPython 解释器、一整个标准库、一个 pip 包管理，四样打包在一起。**

## 1.2 `python` 和 `py`：Windows 上这两个命令不一样

**这一节只有 Windows 用户需要看**（macOS/Linux 只有一个 `python3`，没这些幺蛾子）。
但考虑到大多数人第一台机器是 Windows，我必须讲清楚，因为它是一个高频坑。

### 现象：为什么有的电脑敲 `python` 没反应

你在 Windows 上装 Python 时，官方安装器会顺手装一个叫 **Python launcher** 的小程序，
它的命令名是 **`py`**。注意，`py` 和 `python` 是**两个不同的东西**：

| 命令 | 是什么 | 行为 |
|---|---|---|
| `python` | 指向某个具体的 Python 版本 | 具体指向哪个版本，取决于你 PATH 里排在前面的那个 |
| `py` | Python launcher，一个"版本调度器" | 能自动找到你装过的所有 Python 版本，并指定用哪个 |

`py` 最实用的地方是**多版本共存**。假设你同时装了 Python 3.11、3.12、3.13，
用 `py` 可以精确指定：

```bash
py --list        # 列出本机所有已安装的 Python 版本（旧版命令是 py -0）
py -3.13         # 用 3.13 运行
py -3.12         # 用 3.12 运行
py -3            # 用最新的 Python 3 运行
```

而 `python` 命令具体指向谁，全看你的 PATH 环境变量，经常出现"我以为跑的是 3.13，其实是 3.9"的诡异情况。

### 本教程用哪个

**本教程统一用 `python` 命令**，并且假设它指向 Python 3.13（实测版本 3.13.14）。
原因是：教程里的命令要跨平台通用，`py` 是 Windows 专属的，macOS 用户没有。

但你要知道一个 Windows 现实：**如果你装过多个版本，`python --version` 显示的版本可能和你预期不符**。
这时最稳的做法是：

```bash
python --version   # 先看看实际是哪个版本
py -3.13 --version # 再用 py 确认 3.13 在不在
```

如果 `python --version` 不是 3.13 但你想要 3.13，两种解法：一是去系统环境变量里把 3.13 的路径排前面，
二是干脆后面全程用 `py -3.13` 替代 `python`（但本教程的命令就都得自己替换）。

### 顺带讲清：PATH 环境变量是什么

上面反复提到 PATH，但你可能没搞明白它到底怎么起作用。花 30 秒讲透，以后所有"命令找不到"的问题你自己就能诊断。

**PATH 是一个"目录清单"**。当你在终端敲一个命令（比如 `python`），系统会：

1. 把 PATH 里的目录**从头到尾**挨个找一遍；
2. 在第一个"有这个名字的可执行文件"的目录里找到它，就执行；
3. 全部找完都没有，就报"不是内部或外部命令"。

所以"`python` 指向哪个版本"这个问题的真相是：**PATH 里排在最前面的那个 Python 目录决定了 `python` 是谁。**

你可以用下面的命令看到 PATH 里到底有哪些目录：

```bash
# Windows CMD
echo %PATH%

# Windows PowerShell / Git Bash
echo $PATH

# macOS / Linux
echo $PATH
```

输出是一长串用分号（Windows）或冒号（macOS）隔开的目录路径。找到里面带 `Python` 字样的那几个，
你就明白了为什么 `python` 会指向那个版本。

> 一句话记住它：**`py` 是 Windows 上的"版本调度器"，能指定跑哪个 Python；`python` 只是 PATH 里碰巧排最前的那个版本——而 PATH 就是决定"命令是谁"的那张目录清单。**

## 1.3 venv：每个项目一个独立环境（最重要的一节）

如果这一章你只能带走一样东西，带这节。

### 为什么必须有 venv：先看一个你迟早会撞上的事故

Python 的包（第三方库）默认是**装到一个全局共享的位置**里的。这个位置在：

```text
C:\Users\你的用户名\AppData\Roaming\Python\Python313\site-packages   (Windows)
/usr/lib/python3.13/site-packages                                      (Linux)
```

你现在有两个项目：

- 项目 A 用了 `requests` 的 **2.28** 版本
- 项目 B 用了 `requests` 的 **3.0** 版本（假设出了 3.0，改了 API）

问题来了：**全局只有一个 `site-packages`，只能放一个 `requests`。** 你给项目 B 装了 3.0，
项目 A 就悄悄坏了。更糟的是，你可能根本没意识到自己"动了全局"——三个月后项目 A 突然报错，
你完全想不起来为什么。

这就是 **依赖冲突（dependency hell）**。npm 的解法是"每个项目一个 `node_modules` 目录"，
Python 的解法是"每个项目一个**虚拟环境（venv）**"。

**venv 就是一个独立的 Python 包环境，藏在你的项目目录里。** 你在里面装任何包，
都只影响这个项目，跟全局、跟别的项目完全隔离。

用一句话类比：**venv 之于 Python，就是 `node_modules` 之于 Node.js，只不过 venv 不只隔离依赖，还隔离了 Python 解释器本身。**

### 怎么建、怎么激活（Windows + macOS 都要给）

假设你的项目目录是 `myproject`，进去之后执行三步：

**第一步：创建虚拟环境（一次性）**

```bash
cd myproject
python -m venv .venv        # 在项目里建一个叫 .venv 的虚拟环境目录
```

跑完你会看到项目里多了一个 `.venv` 文件夹。**这个文件夹就是你的独立环境**，里面装了一份 Python 解释器的"软链"和它自己的 `site-packages`。

> 命名习惯：`.venv`（带点）是社区约定俗成的名字，`venv` 也行。带点表示"这是个隐藏的、不该提交到 git 的目录"。

**第二步：激活它（每次开新终端都要做一次）**

这一步 Windows 和 macOS 不一样，分开写：

```bash
# Windows（CMD / PowerShell）
.venv\Scripts\activate

# Windows（PowerShell 如果上面被安全策略拦了）
.venv\Scripts\Activate.ps1

# macOS / Linux
source .venv/bin/activate
```

**激活成功的标志**：命令行提示符前面出现 `(.venv)`：

```text
(.venv) C:\Users\admin\myproject>
```

这个 `(.venv)` 前缀就是告诉你：**"你现在所有的 `python`、`pip` 命令，作用范围都在这个虚拟环境里。"**

**第三步：验证你的 `python` 已经指向虚拟环境**

```bash
which python        # macOS/Linux：应该输出 .../myproject/.venv/bin/python
where python        # Windows CMD：应该输出 ...\myproject\.venv\Scripts\python.exe
```

### 激活之后，一切照旧

激活后你继续正常用 `pip install`、`python xxx.py`，只是它们都只作用于当前项目：

```bash
pip install requests      # 只装进 .venv，全局一点不动
python -c "import requests; print(requests.__version__)"
```

### 退出虚拟环境

```bash
deactivate
```

（Windows 和 macOS 通用，都是 `deactivate`。）

### 三个新手最容易犯的错

1. **忘了激活就 `pip install`** —— 结果装进了全局，你以为是"项目里"，其实污染了全局。**每次 `pip install` 前，先确认命令行前面有 `(.venv)`。**
2. **把 `.venv` 提交到 git** —— `.venv` 目录可能几百 MB，而且它是"环境"不是"代码"。应该在 `.gitignore` 里加一行 `.venv/`。
3. **换电脑后直接把项目拷过去** —— venv 里的解释器路径是硬编码的，拷过去不能用。正确做法：拷代码，新机器上重新 `python -m venv .venv` + `pip install -r requirements.txt`（下一节讲）。

> 一句话记住它：**venv 是每个项目的"独立包环境"，建一次（`python -m venv .venv`），每次开工激活一次（`activate`），装包前先确认有 `(.venv)` 前缀。**

## 1.4 pip 和 requirements.txt：Python 的 npm

上一节说"包隔离"，这一节说"包到底怎么装、怎么记录"。

### pip 是什么

**pip 是 Python 的包管理器，对应 JS 的 `npm`。** 装包、卸包、看装了什么，全靠它。

常用命令一张表：

| 命令 | 作用 | npm 对应 |
|---|---|---|
| `pip install 包名` | 装一个包 | `npm install 包名` |
| `pip install 包名==版本号` | 装指定版本 | `npm install 包名@版本号` |
| `pip install -r requirements.txt` | 按清单批量装 | `npm install`（按 package.json） |
| `pip uninstall 包名` | 卸载 | `npm uninstall 包名` |
| `pip list` | 列出已装的所有包 | `npm list` |
| `pip show 包名` | 看某个包的详情 | `npm view 包名` |
| `pip freeze` | 导出所有包+版本 | 生成 package.json 的 dependencies |

装一个包试一下（在激活的 venv 里）：

```bash
pip install requests
```

装完你就能直接 `import`：

```python
import requests

resp = requests.get("https://httpbin.org/get")
print(resp.status_code)   # 200
print(resp.json())
```

> 本教程核心章节不用第三方库，唯一会用到的第三方库（`requests`、`pytest`、`flask`）
> 都会在对应章节写清楚 `pip install` 命令。这里演示 `requests` 只是为了讲 pip。

### requirements.txt：把"项目依赖"固化下来

你有两个选择来告诉别人"我这个项目依赖哪些包"：

**方式一：手写 `requirements.txt`**（最传统，最直白）

文件里一行一个包，`==` 后面是版本号：

```text
requests==2.32.3
flask==3.0.3
pytest==8.3.3
```

别人拿到这个文件，一条命令装齐：

```bash
pip install -r requirements.txt
```

**方式二：`pip freeze` 自动生成**（适合"把当前环境原样导出"）

```bash
pip freeze > requirements.txt
```

但 `pip freeze` 会把**当前环境里所有包**都导出来，包括那些你顺手装、早就不用的。所以：

- **要精确记录项目依赖** → 手写 `requirements.txt`，只写你 `import` 过的包。
- **要完整复刻某个环境** → 用 `pip freeze`。

**为什么版本号很重要？** 因为不加 `==版本号`，`pip install requests` 永远装"最新版"，
而最新版可能在某个深夜悄悄改了 API，让你的代码第二天就崩。**锁定版本 = 锁定可复现性**。

> 一句话记住它：**`pip` 是 Python 的 npm，`requirements.txt` 是 Python 的 package.json——装包用 `pip install`，固化依赖用 `requirements.txt` + 锁定版本号。**

## 1.5 交互式 REPL 和 `python -m`：两个你每天都会用的入口

### REPL：Python 最好的调试器

在终端里直接敲 `python`（不带文件名），会进入一个**交互式解释器（REPL）**：

```text
$ python
Python 3.13.14 (main, Jun 11 2026, 04:04:46) [MSC v.1944 64 bit (AMD64)] on win32
Type "help", "copyright", "credits" or "license" for more information.
>>>
```

那个 `>>>` 就是提示符，你可以一行一行敲代码，**每行立刻出结果**：

```text
>>> 1 + 2
3
>>> name = "world"
>>> f"hello {name}"
'hello world'
>>> [n * 2 for n in range(5)]
[0, 2, 4, 6, 8]
```

**REPL 是你最好的调试器和学习工具。** 第 00 章的 README 说过一句话：看不懂的代码，先 `print` 出来。
而 REPL 比 `print` 更快——你不用写文件，直接敲进去看结果。

几个 REPL 小技巧：

| 操作 | 作用 |
|---|---|
| `exit()` 或 `Ctrl+D`（Windows 是 `Ctrl+Z` 回车） | 退出 |
| `help(对象)` | 看某个对象的文档 |
| `dir(对象)` | 列出某个对象的所有属性和方法 |
| `_` | 上一个表达式的结果 |
| 上下方向键 | 翻历史命令 |

试一个 `dir`：

```text
>>> dir(str)
['__add__', '__class__', '__contains__', ... 'upper', 'zfill']
>>> "hello".upper()
'HELLO'
```

> **注意**：REPL 里你**不需要 `print` 也能看到结果**——因为 REPL 会自动"回显"表达式的结果。
> 但**在 `.py` 文件里，你必须写 `print` 才会输出**。这是新手常混的一点：文件里 `1 + 2` 这行什么都不显示。

### `python -c`：命令行里跑一句话

不想开 REPL，只想跑一句话：

```bash
python -c "print(1 + 2)"
```

会输出 `3`。适合快速验证一个小语法。

### `python -m`：以"模块"的方式运行某个东西

这是 `python` 命令最有用、也最容易被忽略的用法。`-m` 的意思是 **"把后面的名字当作模块来运行"**。

它和"直接敲命令"的区别在哪？看几个例子你就懂了：

**例一：`python -m venv`**

你在 1.3 节已经用过了。`venv` 其实是一个标准库模块，`python -m venv .venv` 就是"运行 `venv` 这个模块"。
它比某些系统上那个可能不存在、可能版本错乱的 `virtualenv` 命令要可靠。

**例二：`python -m pip`**

```bash
python -m pip install requests    # 和 pip install requests 等价
```

为什么推荐 `python -m pip`？因为 `pip` 命令可能指向另一个 Python 版本的 pip（又是多版本共存的坑），
而 `python -m pip` **保证用的就是你 `python` 指向的那个解释器的 pip**，绝不会错。

**例三：`python -m json.tool`（最实用）**

你的接口返回一串挤成一行的 JSON，肉眼根本没法看。`json.tool` 能帮你格式化：

```bash
echo '{"name":"alice","age":30}' | python -m json.tool
```

输出：

```json
{
    "name": "alice",
    "age": 30
}
```

**例四：`python -m http.server`（零依赖起一个静态服务器）**

在任意目录下：

```bash
python -m http.server 8000
```

然后浏览器打开 `http://localhost:8000`，你就能访问这个目录下的文件。这是"临时分享个文件给同事"的最快方式，**一行命令，零配置，零依赖**。

### 小结这张入口地图

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| `python file.py` | 运行一个脚本 | 正常写代码 |
| `python` | 进 REPL | 快速验证、调试 |
| `python -c "..."` | 跑一句话 | 快速验证一个表达式 |
| `python -m 模块` | 以模块方式运行 | `venv`、`pip`、`json.tool`、`http.server` |

### 顺带讲清 `print` 的两个参数：`sep` 和 `end`

你会写 `print` 一辈子，但它有两个参数是新手从 JS 迁移过来时最容易忽略的，值得现在就讲。

**`sep`：多个参数之间用什么连接。**

```python
print("a", "b", "c")            # 默认用空格连：a b c
print("a", "b", "c", sep="-")   # 改成短横线：a-b-c
print("a", "b", "c", sep="")    # 改成空串，直接拼起来：abc
```

运行：

```text
a b c
a-b-c
abc
```

**`end`：`print` 结束后追加什么（默认是换行符 `\n`）。**

```python
print("第一行")            # 默认末尾带换行
print("第二行")

print("同一行", end="")    # 末尾不加换行
print("继续接上", end="。\n")
```

运行：

```text
第一行
第二行
同一行继续接上。
```

这两个参数对应到 JS 里的区别是：`console.log(a, b, c)` 也是用空格连、末尾自动换行，但你想改它没这么方便；
Python 把这两个行为暴露成了**显式参数**（又是"显式优于隐式"）。你写日志、拼进度条时天天会用到 `end=""`。

> 一句话记住它：**REPL 是你随时可用的"草稿纸"，`python -m` 是"以模块身份运行"——用它跑 `pip` 和 `venv` 能避开多版本共存的坑。**

## 1.6 编码问题：UTF-8 源码 vs Windows GBK 控制台

这一节是**中文 Windows 用户的专属坑**，但几乎每个国内 Python 新手都会撞一次，所以必须讲透。

### 先记住两个独立的"编码"

你在 Python 里会遇到**两种**编码，它们**不是一个东西**：

| 编码 | 管什么 | Windows 默认 | macOS/Linux 默认 |
|---|---|---|---|
| **源码编码** | 你的 `.py` 文件本身用什么编码保存 | UTF-8（Python 3 强制） | UTF-8 |
| **系统/控制台编码** | 你的终端、你的 `open()` 读文件时用什么编码 | **GBK（cp936）** | UTF-8 |

**关键事实：Python 3 的源码文件默认按 UTF-8 读。** 这是 PEP 3120 定死的，从 Python 3 第一天就生效，
所以你可以在 `.py` 文件里随便写中文，不用像 Python 2 那样在文件头加 `# -*- coding: utf-8 -*-`。

**但问题出在第二个编码上：Windows 控制台（还有 `open()` 读文件的默认编码）是 GBK。**

### 真实报错长什么样

你在 Windows 上写了一个 UTF-8 的中文文件，然后：

```python
with open("data.txt") as f:      # 没写 encoding，默认用系统编码 GBK 去读
    content = f.read()
```

如果 `data.txt` 是 UTF-8 编码，里面正好有 GBK 不认的字节，你会看到：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte 0x80 in position 0: illegal multibyte sequence
```

这是我在真实 Windows 环境复现出来的（写了一个含 `0x80` 字节的文件，用 GBK 去读）。

而另一个方向——**GBK 文件用 UTF-8 读**——报的是：

```text
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc4 in position 0: invalid continuation byte
```

### 最阴险的情况：不报错，而是乱码

还有一种更恶心的情况：**字节碰巧两个编码都能解，结果不报错，而是静默乱码。**

UTF-8 的 emoji `🎉`（字节 `F0 9F 8E 89`）被 GBK 强行解读，会变成一堆看不懂的字：

```text
emoji: 🎉   →   GBK 读成  →   emoji: 馃帀
```

**不报错比报错更可怕**，因为乱码会一路传到你的数据库、你的接口返回值里，等你发现时已经晚了。

### 两个标准解法

**解法一：读文件、写文件时，永远显式写 `encoding="utf-8"`**

```python
with open("data.txt", "r", encoding="utf-8") as f:    # 显式指定，不依赖系统默认
    content = f.read()

with open("out.txt", "w", encoding="utf-8") as f:     # 写也显式指定
    f.write("中文内容")
```

**这一条是本教程的铁律**：只要你的代码里出现 `open()`，就带上 `encoding="utf-8"`。
省得未来某天代码跑到一台 GBK 机器上突然崩了。

**解法二：输出中文到控制台乱码时，重配置 stdout**

如果你的 `print("中文")` 在 Windows 控制台乱码，可以在程序开头加：

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")
```

它把标准输出流从"系统默认编码"重设成 UTF-8。

```python
import sys

print("重配前 stdout 编码:", sys.stdout.encoding)     # Windows 控制台可能是 utf-8 或 cp936
sys.stdout.reconfigure(encoding="utf-8")
print("重配后 stdout 编码:", sys.stdout.encoding)     # utf-8
print("中文输出测试：你好，世界")
```

### 另一个隐蔽的坑：BOM（Windows 记事本的"好心"）

BOM 是 **Byte Order Mark**（字节序标记），三个字节 `EF BB BF`，藏在文件最开头。
它原本是给 UTF-16 用的，但 **Windows 的老版记事本**用"UTF-8 带 BOM"保存文件时，会在文件开头塞上这三个字节。

问题来了：**BOM 是看不见的，但它会被当成"内容的一部分"读进来。**

举个真实的例子。你用记事本存了一个 `config.txt`，内容是 `name=alice`，但它带 BOM。
你用 Python 读第一行：

```python
with open("config.txt", encoding="utf-8") as f:
    first_line = f.readline()
    print(repr(first_line))     # '\ufeffname=alice\n'
```

看到开头那个 `\ufeff` 了吗？那就是 BOM。它看不见，但会黏在第一个字符串上，
导致你后续 `first_line.startswith("name")` 判断为 `False`，或者 JSON 解析直接报错。

**解法**：读文件时用 `encoding="utf-8-sig"`，这个编码会自动帮你吃掉开头的 BOM：

```python
with open("config.txt", encoding="utf-8-sig") as f:
    first_line = f.readline()
    print(repr(first_line))     # 'name=alice\n'，BOM 没了
```

`utf-8-sig` 里的 `sig` 就是 signature（签名），专指 BOM。**记不住也没关系，记住一件事：
只要发现读出来的字符串开头有个甩不掉的 `\ufeff`，就把 `encoding="utf-8"` 换成 `encoding="utf-8-sig"`。**

### 一个诚实的补充：为什么你的电脑可能"碰巧没事"

你可能会说："我 Windows 上 `print` 中文从来没乱码过啊？"

原因有三，都值得知道：

1. **新版 Windows 10/11 的终端（Windows Terminal / 新版控制台）已经默认 UTF-8 了**，老 cmd.exe 才是 GBK。
2. **你设置了 `PYTHONUTF8=1` 或 `PYTHONIOENCODING=utf-8` 环境变量**，这会强制 Python 用 UTF-8。
3. **你的源码和系统编码"碰巧一致"**，没触发冲突。

我实测的这台机器：`sys.stdout.encoding` 是 `utf-8`（因为环境里设了 `PYTHONIOENCODING=utf-8`），
但 `locale.getencoding()` 返回 `cp936`（GBK）——这说明**系统默认编码是 GBK，只是被环境变量覆盖成了 UTF-8**。

所以结论是：**别赌"碰巧没事"。显式写 `encoding="utf-8"`，是零成本的保险。**

> 一句话记住它：**Python 3 源码一定是 UTF-8，但 Windows 的系统/控制台默认是 GBK——读写文件永远显式写 `encoding="utf-8"`，输出中文乱码就用 `sys.stdout.reconfigure(encoding="utf-8")`。**

## 1.7 `if __name__ == "__main__"` 是什么、为什么需要

这是几乎每个 Python 文件末尾都会出现的一行，但**没几个人第一次就看懂**。把它彻底搞明白，你才真正理解了"模块"是怎么回事。

### 先看这行代码本身

```python
if __name__ == "__main__":
    main()
```

拆开看：

- `__name__` 是一个**每个 Python 文件都自带的特殊变量**（前后各两个下划线）。
- 它的值取决于**这个文件是被"直接运行"，还是被"import 导入"**。
- `if __name__ == "__main__":` 就是在问："我现在是被直接运行吗？如果是，执行下面这段。"

### 用一个实验把 `__name__` 看透

建两个文件，`mylib.py` 和 `main.py`：

```python
# mylib.py
print("mylib 被加载了，__name__ =", __name__)

def add(a, b):
    return a + b

if __name__ == "__main__":
    print("我是主程序，add(1,2) =", add(1, 2))
```

```python
# main.py
import mylib
print("main 里调用 mylib.add(3,4) =", mylib.add(3, 4))
```

**先直接运行 `mylib.py`**（把它当主程序）：

```bash
python mylib.py
```

```text
mylib 被加载了，__name__ = __main__
我是主程序，add(1,2) = 3
```

看到没？**直接运行时，`__name__` 的值是字符串 `"__main__"`**，所以 `if` 成立，`add(1,2)` 被执行。

**再运行 `main.py`**（它 `import` 了 `mylib`）：

```bash
python main.py
```

```text
mylib 被加载了，__name__ = mylib
main 里调用 mylib.add(3,4) = 7
```

这次 `mylib.py` 被**当作模块导入**，它的 `__name__` 变成了 `"mylib"`（模块名），
所以 `if __name__ == "__main__":` 那段**没执行**——这就是你要的效果。

### 为什么需要它：一个不加它就会出的事故

想象你写了个工具脚本 `utils.py`，里面有函数，也有"直接运行时的测试代码"：

```python
# utils.py（没有 if __name__ 保护的错误写法）
def helper(x):
    return x * 2

print("执行测试:", helper(10))   # 这行"测试代码"裸露在模块顶层
```

现在你在另一个文件里 `import utils` 想用 `helper` 函数：

```python
# app.py
import utils
print(utils.helper(5))
```

运行 `app.py` 会发生什么？

```text
执行测试: 20      ← 你只是 import 一下，utils 顶层的 print 就跟着执行了！
10
```

**你只是想用它的函数，结果它顶层的"测试代码"全跑了一遍。** 这就是没有 `if __name__` 保护的后果：
模块被导入时，**顶层代码（不在函数里的代码）会全部执行**。

### 正确写法

```python
# utils.py（正确写法）
def helper(x):
    return x * 2

def main():
    print("执行测试:", helper(10))

if __name__ == "__main__":
    main()
```

这样：

- 直接 `python utils.py` → `__name__` 是 `"__main__"` → `main()` 执行，测试代码跑。
- 被 `import utils` → `__name__` 是 `"utils"` → `main()` 不执行，只有函数定义被加载。

### 一个类比帮你记住

JS 里你 `require("./utils")` 或 `import utils`，模块顶层的代码也会执行。
但 JS 社区的习惯是"模块只导出，不执行副作用"。Python 用 `if __name__ == "__main__"` 显式地把"我是主程序才执行的代码"圈出来，
这就是第 00 章说的"显式优于隐式"——**你要不要执行，写得明明白白**。

> 一句话记住它：**`__name__` 在"直接运行"时是 `"__main__"`，在"被 import"时是模块名；`if __name__ == "__main__":` 就是"这段代码只有被直接运行时才执行"，防止 import 时误触发顶层代码。**

## 1.8 和 JS 的核心差异对照表

前面讲了环境，这一节把"你脑子里那套 JS 经验"和 Python 做个系统性对照。**不是要你背，是要你在写 Python 时随时能查。**

### 差异一：缩进是语法，不是风格

这是最根本、也最先撞上的差异。

| | JavaScript | Python |
|---|---|---|
| 代码块边界 | `{ }` | **缩进** |
| 语句结束 | `;`（可省略） | 换行（`;` 一般不用） |
| 缩进错了 | 不报错，只是看起来怪 | **报 `IndentationError`** |

JS 里你可以随便排版，靠 `{}` 表达层次：

```js
if (a) { if (b) { x(); } y(); } z();   // 合法，虽然丑
```

Python 里**缩进就是 `{}`**，层次由缩进决定：

```python
if a:
    if b:
        x()
    y()      # 这一行的缩进决定了它在哪个 if 里
z()
```

如果你缩进错位，会看到真实报错：

```text
IndentationError: unindent does not match any outer indentation level
```

或者：

```text
IndentationError: unexpected indent
```

**为什么这么设计**，第 00 章 0.5 节已经讲透了：缩进强制"所见即所执行"，
世界上不存在"看起来在 if 里、其实不在"的 Python 代码。

**给你的两个实操建议：**

1. **统一用 4 个空格**（PEP 8 官方规定），**绝不混用 Tab 和空格**——混用会报 `IndentationError` 或更诡异的 `SyntaxError`。
2. 用现代编辑器（VS Code / PyCharm），把 Tab 自动转成 4 空格。

### 差异二：变量声明

JS 有三个声明关键字 `var` / `let` / `const`，Python **一个都没有**：

```js
// JavaScript
let name = "alice";
const PI = 3.14;
```

```python
# Python
name = "alice"       # 直接赋值就是声明
PI = 3.14
```

**Python 里"给一个名字赋值"就是"声明变量"**，没有"声明但不赋值"这回事。
第一次给某个名字赋值，它就诞生了。

**常量**：Python 没有真正的常量。`PI = 3.14` 只是"大家约定俗成：全大写名字别去改它"，是约定不是语法约束。

### 差异三：类型系统

| | JavaScript | Python |
|---|---|---|
| 类型何时检查 | 动态，运行时 | 动态，运行时 |
| 隐式类型转换 | **有**（`"1" + 2` → `"12"`） | **几乎没有**（`"1" + 2` 直接报错） |
| 类型注解 | 无（TS 才有） | 有（可选，第 07 章讲） |

JS 的隐式转换是个著名噩梦：

```js
"1" + 2      // "12"
"1" - 2      // -1
[] + {}      // "[object Object]"
```

Python **拒绝**隐式转换，这是第 00 章 0.6 节"显式优于隐式"的直接体现：

```python
"hello" + 1
```

真实报错：

```text
TypeError: can only concatenate str (not "int") to str
```

想拼，必须显式 `str(1)`：

```python
"hello" + str(1)   # 'hello1'
```

**这个差异对你的影响是：Python 的报错比 JS 来得更早、更凶，但bug 也更容易定位**——因为它从不"悄悄帮你转"。

### 差异四：作用域

| | JavaScript | Python |
|---|---|---|
| 变量作用域 | 函数级（`var`）或块级（`let`/`const`） | **函数级 + 模块级** |
| `if` 块里的变量 | `let` 只活在块里 | **`if` 块不产生新作用域** |

一个典型差异：在 Python 里，`if` 块里赋值的变量，**块外面照样能访问**：

```python
if True:
    x = 10          # 在 if 块里赋值

print(x)            # 10，块外能访问！
```

这在 JS（用 `let`）里是不可能的，`let x` 出了 `{}` 就死了。

**Python 产生新作用域的只有：函数（`def`）、类（`class`）、模块（每个文件）。** 块（`if`/`for`/`while`）不产生作用域。函数作用域和闭包，第 03 章会详细展开。

### 差异五：其他零散但高频的对照

| 场景 | JavaScript | Python |
|---|---|---|
| 真/假值 | `0`、`""`、`null`、`undefined`、`NaN`、`false` | `0`、`""`、`None`、`False`、空容器（`[]`/`{}`/`()`） |
| 空值 | `null` 和 `undefined` 两个 | **只有 `None` 一个** |
| 布尔值 | `true` / `false` | **`True` / `False`（首字母大写）** |
| 与或非 | `&&` / `\|\|` / `!` | **`and` / `or` / `not`** |
| 三目运算符 | `cond ? a : b` | **`a if cond else b`** |
| 数组/列表 | `Array` | `list` |
| 对象/字典 | 普通对象 | `dict` |
| 函数定义 | `function f() {}` 或箭头函数 | `def f():` |
| 遍历 | `for...of`、`.map()` | `for x in xs` |
| 字符串格式化 | 模板字符串 `` `...${x}` `` | **f-string `f"...{x}"`** |

挑几个容易写错的单独强调：

**1. 布尔值首字母大写，写小写直接报错：**

```python
if True:
    print("对")

if true:            # ❌ 小写
    print("错")
```

真实报错：

```text
NameError: name 'true' is not defined
```

**2. 与或非是英文单词，不是符号：**

```python
if age > 18 and age < 60:     # 不是 &&
    pass
if a == 1 or b == 2:          # 不是 ||
    pass
if not done:                  # 不是 !
    pass
```

**3. f-string 对应模板字符串：**

```js
// JS
`hello ${name}`
```

```python
# Python
f"hello {name}"
```

f-string 是 Python 3.6+ 的特性，本教程全部用它做字符串格式化。

### 差异六：真值判断和 `None`

JS 里有 `null` 和 `undefined` 两个"空值"，还区分"假值"（falsy）。Python 里简化成了：
**空值只有一个 `None`，假值是一组"空"的东西。**

**`None` 是 Python 唯一的空值**，对应 JS 的 `null`（也部分对应 `undefined`）。
判断一个东西是不是 `None`，**用 `is` 而不是 `==`**：

```python
x = None
if x is None:        # ✅ 惯用写法
    print("是 None")

if x == None:        # ⚠️ 能跑，但不推荐（第 02 章讲 is vs == 的区别）
    print("也是 None")
```

`is None` 和 `== None` 的区别，第 02 章会展开。这里先记住惯用写法是 `is None`。

**Python 的假值（falsy）是一组"空"的东西：**

| 假值 | 说明 |
|---|---|
| `False` | 布尔假 |
| `None` | 空值 |
| `0` / `0.0` | 零 |
| `""` | 空字符串 |
| `[]` / `{}` / `()` / `set()` | 空容器 |

**其余全是真值。** 所以 Python 有个超级常用的惯用写法——判断"容器是不是空的"，直接：

```python
items = []

if not items:            # ✅ 空列表是 falsy，等价于 if len(items) == 0
    print("列表是空的")
```

对比 JS，你通常会写 `if (items.length === 0)`；Python 里直接 `if not items`，更短也更"Pythonic"。

### 差异七：字符串方法，形似神不似

Python 的字符串方法和 JS 的**名字很像，但细节不一样**，最容易"顺手写错"。挑最高频的几个：

| 需求 | JavaScript | Python | 注意点 |
|---|---|---|---|
| 分割 | `s.split(",")` | `s.split(",")` | 名字一样，但 Python 无参 `split()` 会**按空白切并去掉空串** |
| 拼接 | `arr.join(",")` | `",".join(arr)` | **Python 是"分隔符.join(列表)"，顺序反的** |
| 转大写 | `s.toUpperCase()` | `s.upper()` | 驼峰 → 小写+下划线 |
| 转小写 | `s.toLowerCase()` | `s.lower()` | 同上 |
| 去两端空白 | `s.trim()` | `s.strip()` | 名字不同 |
| 替换 | `s.replace(a, b)` | `s.replace(a, b)` | 名字一样 |
| 是否包含 | `s.includes(sub)` | `sub in s` | Python 用 `in` 关键字 |

**最容易写错的是 `join`**。JS 是"数组在前面"：`arr.join(",")`；Python 是"分隔符在前面"：`",".join(arr)`。

```python
words = ["a", "b", "c"]

# ❌ 新手常写错：words.join(",")
# 报错：AttributeError: 'list' object has no attribute 'join'

# ✅ 正确：分隔符.join(列表)
",".join(words)      # 'a,b,c'
```

为什么 Python 要反着来？因为 `join` 是**字符串的方法**，不是列表的方法——它作用在"分隔符"这个字符串上，
把列表里的元素用自己连起来。这也更符合"字符串是不可变对象"的直觉（第 02 章讲）。

> 一句话记住它：**Python 和 JS 最大的四处分歧是：缩进当语法、没有声明关键字、不做隐式类型转换、`if` 块不产生作用域；再叠加 `None` 只有一个、假值是"空"的东西、`join` 是分隔符在前——把这几点"翻译"过来，你就成功了大半。**

## 1.9 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 忘了激活 venv 就 pip | 包装进了全局，别的项目也"被污染" | `pip` 默认装进当前激活环境或全局 | 每次装包前看命令行有没有 `(.venv)` 前缀 |
| 混用 Tab 和空格 | `IndentationError` 或诡异 `SyntaxError` | 缩进是语法，Tab 和空格不能混 | 统一 4 空格，编辑器设 Tab 转空格 |
| 布尔值写成小写 | `NameError: name 'true' is not defined` | Python 是 `True`/`False` 大写 | 用 `True` / `False` |
| `and`/`or` 写成 `&&`/`\|\|` | `SyntaxError` | Python 用英文单词 | 用 `and` / `or` / `not` |
| 读文件没写 encoding | Windows 下 `UnicodeDecodeError: 'gbk' codec...` | `open()` 默认跟系统编码（GBK） | 显式写 `encoding="utf-8"` |
| 中文 print 乱码 | 控制台是 GBK，输出 UTF-8 | 控制台编码和源码编码不一致 | `sys.stdout.reconfigure(encoding="utf-8")` |
| `python` 指向了错的版本 | 代码在 3.9 上跑，报"语法不支持" | PATH 里多个 Python | `python --version` 确认，或用 `py -3.13` |
| `pip` 和 `python` 不是同一个环境 | pip 装到了别的版本 | `pip` 命令可能指向别的解释器 | 用 `python -m pip install` |
| 模块顶层乱写执行代码 | import 时被意外执行 | 顶层代码 import 就会跑 | 入口代码放 `if __name__ == "__main__":` |
| 以为 `.py` 文件里 `1+2` 会输出 | 运行后什么都不显示 | 文件里不 print 就不输出 | 文件里要显式 `print` |

## 1.10 本章小结

- Python = 语言规范 + CPython 解释器 + 标准库 + pip 包管理，四样打包在一起。
- 标准库极肥，`json`/`os`/`math`/`sqlite3` 开箱即用，能用标准库就别引第三方。
- `py` 是 Windows 的版本调度器，`python` 只是 PATH 里排最前的版本，多版本共存用 `py -3.13`。
- **venv 是每个项目的独立包环境**，建一次 `python -m venv .venv`，每次开工 `activate`。
- `pip` 是 Python 的 npm，`requirements.txt` 是 Python 的 package.json，依赖要锁版本。
- REPL 是最好的草稿纸，`python -m` 用来跑 `venv`/`pip`/`json.tool`/`http.server`，避开多版本坑。
- Python 3 源码一定 UTF-8，但 Windows 系统/控制台默认 GBK，读写文件显式 `encoding="utf-8"`。
- `__name__` 直接运行是 `"__main__"`，被 import 是模块名，`if __name__ == "__main__":` 防误执行。
- 和 JS 的四大差异：缩进当语法、无声明关键字、不做隐式转换、`if` 块不产生作用域。

## 1.11 动手练习

1. 写一个文件 `hello.py`，内容是一行 `print("hello")`。分别在 REPL 里敲 `print("hello")`，
   和用 `python hello.py` 运行，观察两种方式的输出有什么不同。然后回答：为什么文件里不加 `print` 就没输出？

   <details><summary>参考答案</summary>

   REPL 里敲 `print("hello")` 会显示 `hello`，而且 REPL 里即使不写 `print`，直接敲 `"hello"` 也会回显 `'hello'`。
   但 `python hello.py` 运行时，文件里只有 `print("hello")` 才会输出 `hello`；如果文件里写的是 `"hello"`（没 print），
   运行后什么都不显示。因为 REPL 会"自动回显表达式结果"，而脚本文件不会——文件里要看到输出，必须显式 `print`。

   </details>

2. 在命令行依次执行下面三条命令，记录每条的输出，并解释为什么前两条会报错、第三条正常：

   ```bash
   python -c "print('hello' + 1)"
   python -c "print(true)"
   python -c "print('hello' + str(1))"
   ```

   <details><summary>参考答案</summary>

   - 第一条报 `TypeError: can only concatenate str (not "int") to str`：Python 不做隐式类型转换，`str + int` 直接报错。
   - 第二条报 `NameError: name 'true' is not defined`：Python 布尔值是 `True`/`False`（大写），没有小写 `true`。
   - 第三条输出 `hello1`：显式 `str(1)` 把整数转成字符串后再拼接，符合"显式优于隐式"。

   </details>

3. 新建一个项目目录，用 `python -m venv .venv` 建虚拟环境，激活它（Windows 用
   `source .venv/Scripts/activate` 或 `.venv\Scripts\activate`，macOS 用 `source .venv/bin/activate`），
   然后执行 `python -m pip list`。观察：激活前后，命令行提示符有什么区别？

   <details><summary>参考答案</summary>

   激活后命令行提示符前面会出现 `(.venv)`，表示当前 `python` 和 `pip` 命令都作用在这个虚拟环境内。
   `python -m pip list` 列出的是虚拟环境里已装的包（刚建时只有 `pip` 和 `setuptools` 等基础包）。
   激活前 `pip list` 列出的是全局包，两者是隔离的。

   </details>

4. 写两个文件 `a.py` 和 `b.py`：`a.py` 里定义 `def f(): return 42` 并在底部加
   `if __name__ == "__main__": print("A 是主程序")`；`b.py` 里 `import a` 然后 `print(a.f())`。
   分别运行 `python a.py` 和 `python b.py`，观察哪个文件打印了"A 是主程序"，为什么？

   <details><summary>参考答案</summary>

   - 运行 `python a.py` 时，`a.py` 的 `__name__` 是 `"__main__"`，所以会打印 `A 是主程序`。
   - 运行 `python b.py` 时，`a.py` 被 `import`，它的 `__name__` 是 `"a"`，所以 `if __name__ == "__main__"` 不成立，不会打印那句话；`b.py` 只打印 `42`。
   这正是 `if __name__ == "__main__":` 的作用：区分"被直接运行"和"被导入"。

   </details>

5. 故意制造一个 `IndentationError`：写一个 `.py` 文件，`for` 循环体里两行缩进不一致（比如一行 4 空格、一行 6 空格），
   运行它，把报错信息抄下来。然后改成统一 4 空格，再运行，确认能通过。

   <details><summary>参考答案</summary>

   缩进不一致的代码：

   ```python
   for i in range(3):
       print(i)
         print("x")   # 这行 6 空格，和上面 4 空格不一致
   ```

   运行报错：

   ```text
   IndentationError: unindent does not match any outer indentation level
   ```

   改成两行都是 4 空格后正常。这验证了"缩进是语法"：Python 用缩进对齐来表达代码块归属，错位就直接报错。

   </details>

6. 在 REPL 里依次输入下面每一行，把每行的输出抄下来，并解释最后三行的结果为什么和前两行不同：

   ```text
   >>> x = 10
   >>> x
   >>> y = x
   >>> y
   >>> y = 20
   >>> x
   ```

   <details><summary>参考答案</summary>

   逐行输入时，`x = 10` 和 `y = x` 都不显示结果（赋值语句 REPL 不回显）；输入 `x` 回显 `10`；输入 `y` 回显 `10`；
   `y = 20` 不回显；最后输入 `x` 回显 `10`。关键点：`y = x` 是"把 x 的值（10）复制给 y"，不是"让 y 和 x 绑定成一体"，
   所以之后改 `y` 不影响 `x`。注意这里 x、y 都是不可变整数；如果是可变对象（比如列表），`y = x` 的语义就完全不同了（第 02 章重点讲）。

   </details>

7. 用记事本新建一个文本文件，另存为时编码选"UTF-8"（如果记事本提供"UTF-8 带 BOM"选项就选它），
   内容第一行写 `hello`。然后用 Python 读第一行并 `print(repr(...))`，观察开头有没有 `\ufeff`。
   再换成 `encoding="utf-8-sig"` 读一次，对比结果。

   <details><summary>参考答案</summary>

   用 `encoding="utf-8"` 读带 BOM 的文件，第一行开头会出现 `\ufeff`，`repr` 显示为 `'\ufeffhello\n'`。
   换成 `encoding="utf-8-sig"` 后，BOM 被自动吃掉，`repr` 显示 `'hello\n'`。
   这个实验让你亲眼看到 BOM 这个"看不见的字符"如何混进数据，以及 `utf-8-sig` 如何解决它。

   </details>

8. 解释为什么推荐写 `python -m pip install 包名` 而不是直接 `pip install 包名`？
   在装过多个 Python 版本的机器上，这两者可能指向什么不同的东西？

   <details><summary>参考答案</summary>

   `pip` 是一个独立的可执行命令，它可能关联到 PATH 里某个特定 Python 版本的 pip；
   而 `python -m pip` 明确用"你当前敲的 `python` 所对应的那个解释器"的 pip。
   在多版本共存时，`pip` 和 `python` 可能指向不同版本，导致"装错了环境"。
   用 `python -m pip` 保证装进的就是当前 `python` 对应的环境，绝不错位。
   同理，`python -m venv` 也保证用当前解释器创建虚拟环境。

   </details>
