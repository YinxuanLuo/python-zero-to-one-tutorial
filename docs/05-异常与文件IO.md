# 第 05 章 · 异常与文件 I/O

> 这一章教你两件事：**出错的时候怎么优雅地兜住**，以及**怎么把数据写进磁盘、再从磁盘读回来**。
> 两者看似无关，其实共用同一个核心工具——`with`（上下文管理器）。
>
> 本章你需要记住的就一件事：**用 `try/except` 兜住"预料之中的错"，用 `with open(...) as f` 读写文件，绝不用裸 `except:`。**

---

## 5.1 异常到底是什么：和 JS 的 `throw`/`catch` 是一回事

你在 JS 里写过错误处理，大概率长这样：

```js
function divide(a, b) {
  if (b === 0) throw new Error("除数为 0");
  return a / b;
}

try {
  divide(10, 0);
} catch (e) {
  console.log(e.message);   // 除数为 0
} finally {
  console.log("收尾");
}
```

Python 的对应物，语义几乎一一对应，但关键字不一样：

| JS | Python | 说明 |
|---|---|---|
| `throw new Error(...)` | `raise ValueError(...)` | 抛异常 |
| `try { ... }` | `try:` | 可能出错的代码块 |
| `catch (e) { ... }` | `except XxxError as e:` | 捕获异常 |
| `finally { ... }` | `finally:` | 无论如何都执行 |
| 没有 | `else:` | **Python 独有**：没出错才执行 |

```python
def divide(a, b):
    if b == 0:
        raise ValueError("除数为 0")
    return a / b

try:
    print(divide(10, 2))
except ValueError as e:
    print("出错：", e)
finally:
    print("收尾")
```

```text
5.0
收尾
```

你已经能看出两个关键差异：

1. **`except` 必须指定异常类型**（或一组类型），不能像 JS 那样 `catch (e)` 啥都接。
2. **`else` 是 Python 独有的**：`try` 块顺利跑完、没抛异常时执行。JS 里没有它，只能用 `if (ok)` 模拟。

为什么 Python 要多个 `else`？先记住一句：**`else` 让"只有成功时才做的事"和"兜错逻辑"分开，读起来更清楚。** 具体到 5.4 节展开。

### 5.1.1 先斩后奏：EAFP vs LBYL

理解 Python 异常之前，得先懂一个贯穿全语言的哲学缩写——**EAFP**：

> **E**asier to **A**sk **F**orgiveness than **P**ermission（请求宽恕，比请求许可更容易）。

翻译成人话：**先直接做，出错了再兜底**，而不是先做一堆检查。它的对立面叫 **LBYL**（**L**ook **B**efore **Y**ou **L**eap，三思而后行）——先检查条件，再行动。

看同一个需求（从字典取值）的两种写法：

```python
d = {"a": 1}

# LBYL：先检查再动手
if "b" in d:
    print(d["b"])
else:
    print("没有 b")

# EAFP：先动手，错了再兜
try:
    print(d["b"])
except KeyError:
    print("没有 b")
```

```text
没有 b
没有 b
```

两种写法结果一样，但 EAFP 是 Python 社区更推崇的风格。为什么？两个原因：

1. **LBYL 有竞态**。在多线程/多进程里，"检查"和"使用"之间，状态可能被别人改掉——你刚检查完 `"b" in d`，另一个线程就把 `b` 删了，然后 `d["b"]` 还是炸。EAFP 没有这个窗口：直接做，炸了再说。
2. **EAFP 更简洁**。LBYL 要先写检查、再写正常路径、再写异常路径，三段；EAFP 只写"正常路径 + 异常兜底"两段，主逻辑不被检查代码打断。

但 EAFP 也有代价：**滥用 `try/except` 会让正常逻辑被包在层层 try 里，读起来累**。所以 Python 社区的共识是：

- **预期之外、但可以恢复的错误**（文件可能不存在、键可能没有）→ EAFP，直接 `try/except`。
- **可以低成本预判的错误**（比如 `b == 0` 这种一行就能判断的）→ 也可以先判断，两种都行。

JS 读者尤其要转变一下习惯：JS 里大家习惯了 `if (obj && obj.a && obj.a.b)` 这种层层防御（LBYL），
而 Python 更习惯 `try: obj.a.b except AttributeError: ...`。

> 一句话记住它：**Python 的异常体系 ≈ JS 的 `throw`/`catch`，但 `except` 要指定类型，还多了个 `else`；风格上偏爱 EAFP——先做，错了再兜。**

## 5.2 异常的继承层次：为什么 `except Exception` 不能乱写

JS 里所有错误都是 `Error` 的子类（`TypeError`、`ReferenceError`、`RangeError`…），但层级很浅。
Python 里异常的层级更深，而且**顶层不是 `Exception`，是 `BaseException`**。

拿 `FileNotFoundError` 举例，看它的完整继承链（这是真实查出来的）：

```python
print([c.__name__ for c in FileNotFoundError.__mro__])
```

```text
['FileNotFoundError', 'OSError', 'Exception', 'BaseException', 'object']
```

整个异常世界长这样：

```text
BaseException          ← 所有异常的祖宗，几乎不直接捕获它
├── SystemExit         ← 你调用 sys.exit() 时抛出
├── KeyboardInterrupt  ← 用户按 Ctrl+C 时抛出
├── GeneratorExit      ← 生成器关闭时抛出
└── Exception          ← 99% 的异常都在这一支下
    ├── ArithmeticError
    │   ├── ZeroDivisionError
    │   └── OverflowError
    ├── LookupError
    │   ├── KeyError
    │   └── IndexError
    ├── OSError
    │   ├── FileNotFoundError
    │   └── PermissionError
    ├── ValueError
    ├── TypeError
    └── RuntimeError
```

看到关键点了吗：**`SystemExit` 和 `KeyboardInterrupt` 不在 `Exception` 下面，而在 `BaseException` 下面。**

这意味着：

```python
import sys

try:
    sys.exit(0)          # 想退出程序
except Exception:        # 想"兜住所有错误"
    print("被兜住了")     # ← 但 sys.exit 抛的是 SystemExit，不会被捕获
```

`except Exception` 抓不到 `SystemExit`，程序还是正常退出了。这其实是个**好设计**：你想"兜住业务错误"，不该顺带把"用户按 Ctrl+C 想中断程序"这件事也吞掉。

而裸的 `except:`（5.6 节细讲）**连 `SystemExit` 和 `KeyboardInterrupt` 都会吞**——这就是它最危险的地方。

### 5.2.1 顺带学一个硬技能：读懂 traceback

你会写 `try/except` 之前，得先会读报错。Python 报错的完整格式叫 **traceback（回溯）**，
它告诉你三件事：**哪个文件、第几行、抛了什么错**。这是真实的一次报错：

```text
Traceback (most recent call last):
  File "demo.py", line 6, in boot
    load()
    ~~~~^^
  File "demo.py", line 2, in load
    raise FileNotFoundError("config.json 不存在")
FileNotFoundError: config.json 不存在
```

从上往下读（和 JS 的 stack trace 相反，Python 是**从最里层开始往下**）：

1. `File "demo.py", line 6, in boot` —— 在 `boot` 函数里、第 6 行调用了 `load()`。
2. `File "demo.py", line 2, in load` —— 跟着进到 `load` 函数、第 2 行 `raise` 了异常。
3. `FileNotFoundError: config.json 不存在` —— 最后一行是**异常类型 + 人类可读信息**。

**读 traceback 的心法：先看最后一行（什么错），再看上面第一行（哪触发的），中间是调用链。**
排查时 90% 的时间，你只需要最后一行 + 最上面那个"你自己的代码行"。

> 一句话记住它：**异常的老祖宗是 `BaseException`，`except Exception` 只兜业务异常，抓不到 `Ctrl+C` 和 `sys.exit()`；读 traceback 先看最后一行。**

## 5.3 六种常见异常，先混个脸熟

新手最常见的六个异常，下面每个都能一行复现。**不要只背名字，要背"什么时候触发"。**

```python
# 1. ValueError：值类型对，但值本身不合法
int("abc")            # "abc" 是字符串，但不是数字

# 2. TypeError：操作的类型不匹配
"hello" + 1           # str + int

# 3. KeyError：字典里没有这个键
{"a": 1}["b"]

# 4. IndexError：列表下标越界
[1, 2, 3][10]

# 5. ZeroDivisionError：除以 0
1 / 0

# 6. FileNotFoundError：文件不存在
open("不存在的文件.txt")
```

每一行单独运行，真实报错分别是（按顺序）：

```text
ValueError: invalid literal for int() with base 10: 'abc'
TypeError: can only concatenate str (not "int") to str
KeyError: 'b'
IndexError: list index out of range
ZeroDivisionError: division by zero
FileNotFoundError: [Errno 2] No such file or directory: '不存在的文件.txt'
```

对比一下 JS 你会很有感觉：

| 场景 | JS 抛什么 | Python 抛什么 |
|---|---|---|
| 数字转不了 | `NaN`（不报错！） | `ValueError` |
| `"a" + 1` | `"a1"`（隐式转） | `TypeError` |
| 访问对象不存在的键 | `undefined`（不报错） | `KeyError` |
| 数组越界 | `undefined`（不报错） | `IndexError` |

**看出来了吗？** JS 的哲学是"能忍则忍"，给你 `NaN`/`undefined` 让你继续跑，bug 埋到后面才炸。
Python 的哲学是**立刻炸**——`ValueError`、`KeyError`、`IndexError` 全是"当场告诉你哪里不对"。

这又是第 00 章那条"显式优于隐式"的推论：**宁可现在报错，不让你拿着个 `undefined` 继续往下跑。**

> 一句话记住它：**JS 用 `NaN`/`undefined` 容忍错误，Python 用异常当场揭穿错误——这就是"显式优于隐式"。**

## 5.4 `try/except/else/finally` 的完整语义

这一节是本章地基，务必看透。四个子句的执行时机：

- **`try`**：先执行，可能抛异常。
- **`except`**：`try` 抛了**匹配的**异常时执行；没抛就不进。
- **`else`**：`try` **没抛异常**时执行（`except` 和 `else` 二选一，不会都执行）。
- **`finally`**：**无论如何都执行**，不管有没有异常、异常有没有被捕获。

看完整版：

```python
def divide(a, b):
    try:
        result = a / b
    except ZeroDivisionError:
        print(f"{a} / {b} → 除数为 0！")
    else:
        print(f"{a} / {b} = {result}")
    finally:
        print("  (finally 一定会执行)")

divide(10, 2)
divide(10, 0)
```

```text
10 / 2 = 5.0
  (finally 一定会执行)
10 / 0 → 除数为 0！
  (finally 一定会执行)
```

注意观察：第一次调用走了 `try → else → finally`（`except` 没进）；第二次走了 `try → except → finally`（`else` 没进）。**`except` 和 `else` 是互斥的。**

**为什么要单独搞个 `else`？** 看一个反例。没有 `else`，你只能这么写：

```python
def divide(a, b):
    try:
        result = a / b
        print(f"结果是 {result}")   # ❌ 这行也可能"被误认为"会抛错
    except ZeroDivisionError:
        print("除数为 0！")
```

问题在于：`print(f"结果是 {result}")` 这行其实**不会**抛 `ZeroDivisionError`，但它写在 `try` 里，
读代码的人（和未来的你）会以为它也被保护着。更糟的是，如果这行**真的**抛了别的异常，
也会被这个 `except` 区混淆视听。

用 `else` 把"真正的核心逻辑"和"成功后的后续动作"分开：

```python
def divide(a, b):
    try:
        result = a / b          # 只有这行需要保护
    except ZeroDivisionError:
        print("除数为 0！")
    else:
        print(f"结果是 {result}")  # 明确：这行只在成功时跑
```

**`else` 的语义价值 = 缩小 `try` 的范围。** 这是 Python 社区极力推荐的写法。

**`finally` 的用途**：释放资源、关文件、关连接、删临时文件——这些事**成不成功都要做**。
比如：

```python
f = open("data.txt", "w", encoding="utf-8")
try:
    f.write("hello")
finally:
    f.close()   # 无论 write 是否抛异常，文件都要关
```

（不过这种"开了就要关"的场景，5.10 节的 `with` 能帮你自动做，先记住 `finally` 的语义即可。）

### 5.4.1 一个高频坏习惯：把大段代码塞进 `try`

很多新手（尤其是从 JS 过来、习惯了一个大 `try/catch` 包住整个函数的人）会这么写：

```python
def process(data):
    try:
        # 10 行代码：解析、计算、写库、发消息…
        a = parse(data)
        b = compute(a)
        save(b)
        send_notification(b)
    except Exception as e:
        print(f"出错了：{e}")
```

**问题：你根本不知道是哪一步出的错。** `parse` 错、`compute` 错、`save` 错，全都汇到一个 `except`，
报错信息也是同一句。排查时只能靠猜，或者删掉 `try` 再跑一遍看 traceback。

**正确的做法：`try` 只包住"真正可能抛错的那一小段"，让异常类型和位置都精确：**

```python
def process(data):
    a = parse(data)               # 解析：不用 try（或单独兜 ValueError）
    b = compute(a)
    try:
        save(b)                   # 只有写库可能抛 IOError/连接错误
    except OSError as e:
        print(f"保存失败：{e}")
        return
    send_notification(b)
```

记住一个判断标准：**`try` 里放几行，取决于"这几行会不会抛同一种、你能明确处理的异常"。**
如果你兜不住、也不知道该怎么处理，就让它往上抛，别硬包。

这也和第 00 章"显式优于隐式"一脉相承：**异常处理得越精确，问题定位得越快。**

> 一句话记住它：**`except` 和 `else` 二选一，`finally` 无条件执行；`else` 的作用是缩小 `try` 的保护范围；`try` 只包真正会错的那几行。**

## 5.5 捕获多个异常 + `as e` 拿异常对象

一个 `except` 可以同时接多种异常（写在一个元组里），也可以写多个 `except` 分支。

**写法一：一个 `except` 接多种（异常类型放进 `()`）**

```python
def to_int(s):
    try:
        return int(s)
    except (ValueError, TypeError) as e:
        print(f"转 int 失败：{type(e).__name__}: {e}")
        return None

print(to_int("abc"))
print(to_int(None))
```

```text
转 int 失败：ValueError: invalid literal for int() with base 10: 'abc'
None
转 int 失败：TypeError: int() argument must be a string, a bytes-like object or a real number, not 'NoneType'
None
```

`as e` 把异常对象绑定到变量 `e`。异常对象是 `Exception` 的子类实例，`str(e)` 就是那句人类可读的错误信息。

**写法二：多个 `except` 分支（从上到下依次匹配）**

```python
def parse(s):
    try:
        return int(s)
    except ValueError:
        print("值不合法")
    except TypeError:
        print("类型不对")
```

**坑：子类必须写在父类前面。** `except` 从上往下匹配，一旦匹配就不再往下。如果你把 `Exception` 写在前面，后面更具体的 `except ValueError` 永远不会被执行：

```python
try:
    int("abc")
except Exception:
    print("兜住所有")      # ← 先匹配这个
except ValueError:         # ← 永远到不了这里
    print("永远不执行")
```

正确顺序：**具体在前，笼统在后**（和 JS 里 `catch` 的顺序陷阱一模一样）。

> 一句话记住它：**多个异常用 `except (A, B) as e`，多个分支"具体在前、笼统在后"。**

## 5.6 裸 `except:` 为什么是灾难

先看裸 `except:` 长什么样——**冒号后面什么都不写**：

```python
try:
    risky()
except:          # ❌ 裸 except，什么异常都吞
    pass
```

它等价于 `except BaseException:`，也就是**连 `SystemExit`、`KeyboardInterrupt` 都吞**。三个实打实的危害：

**危害一：吞掉 `Ctrl+C`，程序关不掉。** 用户按 `Ctrl+C` 触发 `KeyboardInterrupt`，想中断你的脚本，
结果被 `except:` 吞了，程序继续跑。用户在终端里狂按 `Ctrl+C` 都退不出去。

**危害二：吞掉 `SystemExit`，`sys.exit()` 失效。** 你的代码里某处调了 `sys.exit(1)` 想用退出码告诉调用方"出错了"，
结果被裸 `except:` 拦住，进程最后返回退出码 0——调用方以为一切正常，实际已经埋了雷。

**危害三：吞掉 bug，报错信息消失。** 这是最致命的。真实生产事故里，经常是：

```python
try:
    process_order(order)      # 这里抛了 KeyError，是代码 bug
except:                       # 结果被静默吞掉
    pass                      # 订单没处理，日志也没有，错误信息也没了
```

错误一吞，**你连"哪里错了、错的是什么"都不知道**。排查时只能瞎猜。

**正确的兜底写法**：至少写成 `except Exception`，并且把错误记下来：

```python
try:
    process_order(order)
except Exception as e:
    print(f"处理订单失败: {e}")   # 至少留个痕迹，而不是 pass
    # 或 logging.error("处理订单失败", exc_info=True)
```

你可能会问：那 `except Exception` 就一定好吗？它比裸 `except:` 好一万倍（至少不吞 `Ctrl+C`），
但它仍然会吞掉所有业务异常。**更推荐的顺序**是：

1. 优先捕获**具体的**异常类型（`ValueError`、`KeyError`…）；
2. 只有在"顶层入口、想兜底不让整个程序崩"时，才用 `except Exception as e` + 记日志。

**裸 `except:` 唯一的"合理"用途**：几乎不存在。哪怕你想"清理资源后重抛"，也应该写成：

```python
try:
    risky()
except Exception:
    cleanup()     # 清理
    raise         # 再把异常抛出去，别让它消失
```

看到最后那个 `raise` 了吗？那是下一节的主角。

> 一句话记住它：**裸 `except:` 会吞掉 `Ctrl+C`、`sys.exit()` 和所有 bug 线索，永远写成 `except Exception as e` 并留下痕迹。**

## 5.7 `raise`、异常链 `from`、以及裸 `raise` 重抛

### 5.7.1 `raise` 主动抛异常

`raise` 对应 JS 的 `throw`。抛什么？**抛一个异常类的实例**：

```python
raise ValueError("年龄不能是负数")
```

也可以先构造再抛（等价）：

```python
e = ValueError("年龄不能是负数")
raise e
```

### 5.7.2 裸 `raise`：在 `except` 里把异常原样重抛

这是 5.6 节结尾那个 `raise` 的完整解释。在 `except` 块里写一个**不带参数的 `raise`**，
表示"我刚才捕获的那个异常，原样再抛出去"。典型场景：**先记日志，再让上层去处理**：

```python
def process():
    try:
        int("x")            # 这里抛 ValueError
    except ValueError:
        print("记录日志：转 int 失败")   # 先留痕
        raise               # 原样重抛，让调用方决定怎么办

try:
    process()
except ValueError as e:
    print("上层捕获到：", e)
```

```text
记录日志：转 int 失败
上层捕获到： invalid literal for int() with base 10: 'x'
```

裸 `raise` 保留的是**原始异常的类型和 traceback**，不是新造的。如果你在 `except` 里写 `raise ValueError("新的")`，那是抛一个全新的异常，和原来的无关。

### 5.7.3 异常链：`raise ... from ...`

一个函数抛错，你希望包装成更上层的语义再抛出去，但**又不想丢掉底层原因**——这就是 `from` 的用途。

```python
def load_config():
    raise FileNotFoundError("config.json 不存在")

def boot():
    try:
        load_config()
    except FileNotFoundError as e:
        raise RuntimeError("启动失败：配置缺失") from e   # 用 from 把原因挂上去

boot()
```

运行它的完整 traceback（真实输出，注意最后两段）：

```text
Traceback (most recent call last):
  File "demo.py", line 6, in boot
    load_config()
  File "demo.py", line 2, in load_config
    raise FileNotFoundError("config.json 不存在")
FileNotFoundError: config.json 不存在

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File "demo.py", line 10, in <module>
    boot()
  File "demo.py", line 8, in boot
    raise RuntimeError("启动失败") from e
RuntimeError: 启动失败
```

Python 自动把"底层原因 `FileNotFoundError`"打印在"表层异常 `RuntimeError`"之前，
中间还有一行 `The above exception was the direct cause of the following exception`。
**你一眼就能看到完整因果链**——这是 `from` 的价值：出问题时，排查的人能看到"真正是谁导致的"。

拿 `from e` 挂上去的原因，存在 `e.__cause__` 里：

```python
try:
    boot()
except RuntimeError as e:
    print("主异常:", type(e).__name__, e)
    print("原因:", type(e.__cause__).__name__, e.__cause__)
```

```text
主异常: RuntimeError 启动失败：配置缺失
原因: FileNotFoundError config.json 不存在
```

### 5.7.4 `raise ... from None`：主动切断因果链

如果你明确知道底层原因无关紧要，不想让它污染 traceback，用 `from None` 显式切断：

```python
try:
    1 / 0
except ZeroDivisionError as e:
    raise ValueError("除零了") from None   # __cause__ 被置为 None
```

```text
Traceback (most recent call last):
  File "demo.py", line 4, in <module>
    raise ValueError("除零了") from None
ValueError: 除零了
```

注意：这次没有 `The above exception was the direct cause...` 那段了，traceback 只显示最后的异常。

> 一句话记住它：**`raise` 抛异常，裸 `raise` 原样重抛，`raise ... from e` 保留因果链，`from None` 主动切断。**

## 5.8 自定义异常：让错误说出业务语言

标准异常只描述"程序层面"的错（值不对、类型不对、键不存在）。但你的业务有自己的错：
"余额不足""商品已下架""密码强度不够"——这些用 `ValueError` 表达太勉强。

自定义异常就是**定义一个继承自 `Exception` 的类**：

```python
class InsufficientBalanceError(Exception):
    def __init__(self, balance, amount):
        self.balance = balance
        self.amount = amount
        super().__init__(f"余额 {balance} 不足，无法扣款 {amount}")
```

抛它、抓它，和标准异常一模一样：

```python
try:
    raise InsufficientBalanceError(100, 500)
except InsufficientBalanceError as e:
    print(f"捕获自定义异常: {e}")
    print(f"当前余额: {e.balance}，想扣: {e.amount}")
```

```text
捕获自定义异常: 余额 100 不足，无法扣款 500
当前余额: 100，想扣: 500
```

**自定义异常的三个约定**：

1. **继承 `Exception`，不要继承 `BaseException`**（否则 `except Exception` 抓不到它，还容易误伤 `Ctrl+C`）。
2. **类名以 `Error` 结尾**（PEP 8 约定，`InsufficientBalanceError` 而不是 `InsufficientBalance`）。
3. **在 `__init__` 里调用 `super().__init__(...)` 传入人类可读信息**，这样 `str(e)` 才有内容。

你也可以建一个"业务异常基类"，让所有业务异常继承它，这样上层能一次兜住所有业务错：

```python
class BizError(Exception):
    """所有业务异常的基类"""

class InsufficientBalanceError(BizError):
    pass

class ProductOffShelfError(BizError):
    pass

try:
    raise InsufficientBalanceError("余额不足")
except BizError:          # 一个 except 兜住所有业务异常
    print("业务出错")
```

### 5.8.1 什么时候用自定义异常，什么时候用内置异常

新手容易走两个极端：要么啥都用 `ValueError`，要么动不动就自定义十几个异常类。判断标准很简单：

**用内置异常**，当错误是"程序层面的技术问题"：
- 传入参数类型不对 → `TypeError`
- 传入参数值不合法（负数年龄、空字符串）→ `ValueError`
- 缺少某个键/索引 → `KeyError` / `IndexError`

**用自定义异常**，当错误是"业务规则被违反"，且**调用方可能需要按异常类型做不同处理**：

```python
class InsufficientBalanceError(Exception):
    pass

class AccountFrozenError(Exception):
    pass

def transfer(from_acct, to_acct, amount):
    if from_acct.frozen:
        raise AccountFrozenError("账户被冻结")
    if from_acct.balance < amount:
        raise InsufficientBalanceError("余额不足")
    ...
```

调用方就能针对不同业务错误走不同分支：

```python
try:
    transfer(a, b, 100)
except AccountFrozenError:
    print("提示用户：账户冻结，联系客服")
except InsufficientBalanceError:
    print("提示用户：余额不足，去充值")
```

如果这里全用 `ValueError`，调用方只能靠字符串内容猜是哪类错，脆弱又难读。**自定义异常的价值 = 用"类型"代替"字符串"来区分错误**，让代码可以按类型分流。

> 一句话记住它：**自定义异常 = 继承 `Exception`、类名以 `Error` 结尾、`__init__` 里调 `super().__init__`，让错误说出业务语言；技术错误用内置异常，业务规则违规才自定义。**

## 5.9 文件读写：`open`、`encoding`、以及读文件的四种姿势

### 5.9.1 `open` 的两种参数

`open(path, mode, encoding=...)` 三个参数：

- `path`：文件路径（字符串，或 5.12 节的 `Path` 对象）。
- `mode`：模式，见下表。
- `encoding`：**字符编码，读文本必须显式给 `utf-8`**。

| mode | 含义 | 文件不存在时 | 文件已存在时 |
|---|---|---|---|
| `"r"` | 只读（默认） | 报 `FileNotFoundError` | 从头读 |
| `"w"` | 只写 | 新建 | **清空后重写** |
| `"a"` | 追加 | 新建 | 在末尾接着写 |
| `"x"` | 独占创建 | 新建 | 报 `FileExistsError` |
| `"r+"` | 读写 | 报错 | 从头读写 |
| 加 `"b"` | 二进制（如 `"rb"`/`"wb"`） | — | 不按字符、按字节 |

两个必踩的坑：

**坑一：`"w"` 会清空原文件。** 你只是想改一下文件，用 `"w"` 打开，写之前文件内容就没了。
想"接着写"用 `"a"`（append）。

**坑二：`encoding="utf-8"` 不写会出事。** 看真实对比。

在 Windows 上，`open` 不指定 `encoding` 时用的是系统默认编码（Windows 中文系统常是 GBK/cp936）。
如果你用 utf-8 写、用默认编码读，中文会乱码：

```python
# 写的时候明确 utf-8
with open("t.txt", "w", encoding="utf-8") as f:
    f.write("你好，世界")
```

```text
（文件里存的是 utf-8 编码的 "你好，世界"）
```

如果换个环境不写 `encoding` 去读，就会得到 `UnicodeDecodeError` 或乱码。**结论：读、写文本一律显式写 `encoding="utf-8"`，别赌系统默认值。**

### 5.9.2 读文件的四种姿势

假设 `notes.txt` 内容是：

```text
第一行
第二行
第三行
```

**姿势一：`read()` 一次性全读进一个字符串**

```python
with open("notes.txt", "r", encoding="utf-8") as f:
    content = f.read()
print(repr(content))
```

```text
'第一行\n第二行\n第三行\n'
```

适合小文件。文件几百 MB 时，`read()` 会把整个文件塞进内存，可能撑爆——那时用下面的姿势。

**姿势二：`readline()` 一次读一行（含换行符 `\n`）**

```python
with open("notes.txt", "r", encoding="utf-8") as f:
    first = f.readline()     # 读第一行
    rest = f.readlines()     # 读剩下的所有行，返回 list
print(repr(first))
print(rest)
```

```text
'第一行\n'
['第二行\n', '第三行\n']
```

`readline()` 每次读一行（**包含行尾的 `\n`**，读到文件末尾会返回空字符串 `""`）。
`readlines()` 一次性把剩余所有行读进一个 `list`——注意它仍然是一次性进内存，大文件慎用。

**姿势三：直接迭代文件对象（最常用、最省内存）**

文件对象本身是可迭代的，`for line in f` 一行一行读，**内存里始终只留一行**：

```python
with open("notes.txt", "r", encoding="utf-8") as f:
    for line in f:
        print(repr(line))
```

```text
'第一行\n'
'第二行\n'
'第三行\n'
```

**这是处理大文件的标准姿势**：`for line in f` 内部是流式读取，不会一次性加载整个文件。
和 JS 里 `readline` 接口按行流式读、而不是 `readFileSync` 整读，是同一个道理。

**去掉行尾 `\n`**：读到的每行都带 `\n`，通常用 `line.strip()` 去掉空白：

```python
for line in f:
    print(line.strip())   # 去掉 \n 和多余空格
```

### 5.9.3 写文件

```python
with open("out.txt", "w", encoding="utf-8") as f:
    f.write("第一行\n")
    f.write("第二行\n")
```

注意：`write()` **不会自动加换行**，要自己拼 `\n`。想一次写多行，用 `writelines()`（它也不加换行）：

```python
lines = ["a\n", "b\n", "c\n"]
with open("out.txt", "w", encoding="utf-8") as f:
    f.writelines(lines)
```

### 5.9.4 二进制读写：`"rb"` / `"wb"`

图片、音频、压缩包、序列化数据——这些不是文本，得用**二进制模式**（加 `b`）。

```python
with open("raw.dat", "wb") as f:
    f.write(b"\x00\x01\x02hello")   # 写的是 bytes，不是 str

with open("raw.dat", "rb") as f:
    data = f.read()
    print(data)
    print(type(data))
```

```text
b'\x00\x01\x02hello'
<class 'bytes'>
```

注意两点：

1. 二进制模式**不能传 `encoding`**（它不管编码，操作的是原始字节）。传了会报错。
2. `read()` 回来的是 `bytes` 对象（对应 JS 的 `Uint8Array`/`Buffer`），不是 `str`。

**文本 vs 二进制的本质区别**：文本模式帮你做了"字节 → 字符"的编解码（所以需要 `encoding`），
二进制模式不碰编码，原样读字节。处理图片、Excel、pdf 等文件，一律用 `b` 模式。

> 一句话记住它：**读文本写文本都显式给 `encoding="utf-8"`；大文件用 `for line in f` 流式读，`"w"` 会清空原文件、`"a"` 才是追加；二进制用 `rb`/`wb`，不传 `encoding`。**

## 5.10 上下文管理器 `with`：为什么它能自动关文件（重点）

先看上一节你反复在写的 `with open(...) as f:`。你有没有想过：**为什么文件不用手动 `f.close()`？**

因为 `with` 语句会**自动帮你收尾**——无论 `with` 块正常跑完、还是中途抛异常，`f.close()` 都会被执行。

### 5.10.1 没有 `with` 的世界：你必须手动 `try/finally`

```python
f = open("data.txt", "w", encoding="utf-8")
try:
    f.write("hello")
finally:
    f.close()   # 不写这行，文件可能没刷盘、句柄还泄漏
```

每次都这么写，既啰嗦又容易忘。`with` 把这段模板代码收进了语法里：

```python
with open("data.txt", "w", encoding="utf-8") as f:
    f.write("hello")
# 出了缩进块，f 自动 close，即使 write 抛异常也一样
```

两者**完全等价**。`with` 只是把 `try/finally` 那套样板自动做了。

### 5.10.2 `with` 的原理：`__enter__` / `__exit__`

`with obj as x:` 背后调用的是对象身上的两个魔术方法：

1. 进入 `with` 时，调用 `obj.__enter__()`，**返回值赋给 `as` 后面的变量**（对文件来说，返回的是文件对象本身）。
2. 退出 `with` 时，调用 `obj.__exit__(exc_type, exc_val, exc_tb)`，无论有没有异常。

看一个自制的"上下文管理器"，把两个方法都打出来：

```python
class Managed:
    def __enter__(self):
        print("__enter__ 被调用")
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        print(f"__exit__ 被调用，exc_type = {exc_type}")
        return False   # 返回 False 表示"不吞异常"

with Managed():
    print("with 块内部")
```

```text
__enter__ 被调用
with 块内部
__exit__ 被调用，exc_type = None
```

注意 `__exit__` 的三个参数：当 `with` 块**没抛异常**时，`exc_type` 是 `None`；抛了异常时，它是异常的类型。

**`__exit__` 的返回值决定"要不要吞异常"**：

- 返回 `False`（或 `None`）：异常继续往外抛（正常行为）。
- 返回 `True`：**异常被吞掉**，不再向上传播。

文件对象的 `__exit__` 返回 `False`，所以文件读写出错，异常照样抛，只是顺带关了文件。

### 5.10.3 用 `contextlib.contextmanager` 写，比写类省一半

自己写 `__enter__`/`__exit__` 太啰嗦。标准库 `contextlib` 提供 `contextmanager` 装饰器，
把一个**带 `yield` 的生成器函数**变成上下文管理器：

```python
import time
from contextlib import contextmanager

@contextmanager
def timer(name):
    print(f"{name} 开始")
    start = time.perf_counter()
    yield                      # 分界线：yield 之前 = __enter__，之后 = __exit__
    end = time.perf_counter()
    print(f"{name} 结束，耗时 {end - start:.4f}s")

with timer("计时器"):
    time.sleep(0.001)
```

```text
计时器 开始
计时器 结束，耗时 0.0011s
```

`yield` 是分水岭：**`yield` 之前是"进入时做什么"，`yield` 之后是"退出时做什么"**。
如果 `with` 块里抛了异常，`yield` 那行会把它抛出来，你需要自己用 `try/finally` 兜住 `yield` 之后的清理逻辑：

```python
@contextmanager
def managed_resource():
    print("获取资源")
    try:
        yield "资源"
    finally:
        print("释放资源")   # 无论 with 块有没有异常，都会释放

with managed_resource() as r:
    print("使用", r)
```

```text
获取资源
使用 资源
释放资源
```

记住：**用 `@contextmanager` 时，清理逻辑要放进 `try/finally`，`yield` 放中间**，否则 `with` 块抛异常时清理不会执行。

### 5.10.4 多个上下文与嵌套 `with`

一次要开两个文件（比如一边读一边写），可以在一行里放多个 `with`：

```python
with open("src.txt", "r", encoding="utf-8") as src, \
     open("dst.txt", "w", encoding="utf-8") as dst:
    dst.write(src.read())
```

（`\` 是行连接符，一行太长时用。也可以直接写在一行里。）

**退出顺序是"后进先出"**：`dst` 先关、`src` 后关。等价于嵌套写法：

```python
with open("src.txt", "r", encoding="utf-8") as src:
    with open("dst.txt", "w", encoding="utf-8") as dst:
        dst.write(src.read())
```

**一个实战场景：文件锁（跨进程互斥）也靠上下文管理器。** 标准库 `threading` 的 `Lock` 也支持 `with`：

```python
import threading

lock = threading.Lock()
with lock:                 # 自动 acquire / release
    print("临界区，只有一个线程能进")
```

看到没，`with` 不只是给文件用的——**任何"获取资源 → 使用 → 释放资源"的模式，都能封装成上下文管理器**。数据库连接、网络连接、锁、临时文件，全都是这个套路。

> 一句话记住它：**`with` = 自动执行的 `try/finally`；原理是 `__enter__`/`__exit__`，用 `@contextmanager` 能把一个 `yield` 函数直接变成上下文管理器；任何"获取/释放资源"都该用它。**

## 5.11 `json`：把 Python 对象存进文件

后端最常见的文件 I/O 就是**读写 JSON**。Python 的 `dict`/`list` 和 JSON 的对象/数组几乎一一对应：

| Python | JSON |
|---|---|
| `dict` | object `{}` |
| `list`/`tuple` | array `[]` |
| `str` | string |
| `int`/`float` | number |
| `True`/`False` | `true`/`false` |
| `None` | `null` |

两个核心函数：

- `json.dumps(obj)`：Python 对象 → JSON 字符串（**d**ump **s**tring）。
- `json.loads(s)`：JSON 字符串 → Python 对象（**l**oad **s**tring）。
- 加 `json.dump(obj, f)` / `json.load(f)`：直接读写**文件**（没有 s，操作文件对象）。

```python
import json

data = {"name": "张三", "age": 30, "hobbies": ["读书", "游泳"], "active": True}
s = json.dumps(data, ensure_ascii=False, indent=2)
print(s)
```

```text
{
  "name": "张三",
  "age": 30,
  "hobbies": [
    "读书",
    "游泳"
  ],
  "active": true
}
```

两个必记参数：

1. **`ensure_ascii=False`**：默认 `json.dumps` 会把中文转成 `\u5f20\u4e09` 这种转义。加 `ensure_ascii=False` 才输出可读中文。
2. **`indent=2`**：缩进美化，方便人看。

读回来：

```python
back = json.loads(s)
print(back)
print(type(back), type(back["hobbies"]))
```

```text
{'name': '张三', 'age': 30, 'hobbies': ['读书', '游泳'], 'active': True}
<class 'dict'> <class 'list'>
```

注意 `true` 读回来变成了 Python 的 `True`。

**读写文件**（结合 `with`）：

```python
with open("config.json", "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False, indent=2)

with open("config.json", "r", encoding="utf-8") as f:
    loaded = json.load(f)
```

**坑：`json.dumps` 遇到不认识的类型会抛 `TypeError`。** 比如 `datetime`、`set`、自定义对象，`json` 默认不认识：

```python
import json
json.dumps({"when": "2026-01-01"})          # 字符串，OK
json.dumps({"tags": {"a", "b"}})            # ❌ set 无法序列化
```

```text
TypeError: Object of type set is not JSON serializable
```

解决办法（第 07 章会细讲序列化）是给 `json.dumps` 传 `default=` 回调，或先把 `set` 转成 `list`。

### 5.11.1 处理无效 JSON

读进来的 JSON 可能是坏的（文件被截断、格式错误），`json.loads` 会抛 `json.JSONDecodeError`（它是 `ValueError` 的子类）：

```python
import json

try:
    json.loads("{这不是合法的 JSON")
except json.JSONDecodeError as e:
    print("JSON 解析失败：", e)
    print("出错位置：第", e.lineno, "行，第", e.colno, "列")
```

```text
JSON 解析失败： Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
出错位置：第 1 行，第 2 列
```

`JSONDecodeError` 自带 `lineno`/`colno`，能直接告诉你坏在哪一行哪一列——排查畸形 JSON 时很有用。
所以读外部 JSON 时，**永远包一层 `try/except json.JSONDecodeError`**，别让一个坏文件把整个服务打崩。

> 一句话记住它：**`dumps`/`loads` 处理字符串，`dump`/`load` 处理文件；中文记得加 `ensure_ascii=False`，不认识的类型（set、datetime）会抛 `TypeError`；读外部 JSON 要兜 `JSONDecodeError`。**

## 5.12 `pathlib`：现代路径处理，替代 `os.path`

旧代码里处理路径用 `os.path`（一堆函数：`os.path.join`、`os.path.dirname`、`os.path.splitext`…）。
Python 3.4 起有了 `pathlib`，把"路径"变成**对象**，用起来更顺。

```python
from pathlib import Path

p = Path("data") / "users" / "info.json"   # 用 / 拼接路径
print(p)
print(p.parent)      # 父目录
print(p.name)        # 文件名（含后缀）
print(p.suffix)      # 后缀
```

```text
data\users\info.json
data\users
info.json
.json
```

几个和 `os.path` 的对比，你一眼能看出 `pathlib` 好在哪：

| 操作 | `os.path`（旧） | `pathlib`（新） |
|---|---|---|
| 拼接路径 | `os.path.join("a", "b", "c")` | `Path("a") / "b" / "c"` |
| 取父目录 | `os.path.dirname(p)` | `p.parent` |
| 取文件名 | `os.path.basename(p)` | `p.name` |
| 取后缀 | `os.path.splitext(p)[1]` | `p.suffix` |
| 判断是否存在 | `os.path.exists(p)` | `p.exists()` |
| 读文本 | `open(p).read()` | `p.read_text(encoding="utf-8")` |

`pathlib` 的 `Path` 对象可以直接传给 `open()`：

```python
p = Path("notes.txt")
with open(p, "w", encoding="utf-8") as f:
    f.write("hello")
```

还有几个高频方法：

```python
from pathlib import Path

p = Path("data") / "users"
print(p.exists())           # 是否存在
# p.mkdir(parents=True, exist_ok=True)   # 递归建目录，已存在也不报错
# p.glob("*.py")             # 匹配文件（返回生成器）
# p.read_text(encoding="utf-8")          # 直接读全文
# p.write_text("内容", encoding="utf-8")  # 直接写全文
```

**`read_text`/`write_text` 是最方便的**：不用 `open`，一行读写整个文件：

```python
from pathlib import Path
Path("hello.txt").write_text("你好", encoding="utf-8")
print(Path("hello.txt").read_text(encoding="utf-8"))
```

```text
你好
```

**结论：新代码一律用 `pathlib`，别再用 `os.path`。** 这也是第 00 章"一种明显正确的做法"的体现——官方已经在用 `pathlib` 取代 `os.path`。

### 5.12.1 遍历目录：`iterdir` 与 `glob`

处理文件绕不开"遍历目录"。`pathlib` 提供两个方法：

```python
from pathlib import Path

# iterdir()：列出目录下所有条目（不递归）
for p in Path(".").iterdir():
    print(p.name)

# glob("*.py")：按通配符匹配（只匹配当前目录一层）
for p in Path(".").glob("*.py"):
    print(p)

# rglob("*.py")：递归匹配所有子目录
for p in Path(".").rglob("*.py"):
    print(p)
```

`iterdir()` 返回目录下的直接子项；`glob("*.py")` 按通配符过滤；`rglob` 多一个 `r`（recursive）递归到底。
**处理大量文件时，`glob`/`rglob` 返回的是生成器，懒加载，不会一次性列出所有文件塞进内存**——和 5.9 节 `for line in f` 是同一个省内存的思路。

典型场景：统计某个目录下所有 `.json` 文件：

```python
from pathlib import Path

count = sum(1 for _ in Path("data").rglob("*.json"))
print(f"data 目录下共 {count} 个 json 文件")
```

> 一句话记住它：**用 `Path` 对象和 `/` 拼路径，用 `read_text`/`write_text` 直接读写，用 `iterdir`/`glob`/`rglob` 遍历目录，弃用 `os.path`。**

## 5.13 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 裸 `except:` | 程序吞掉所有错误，`Ctrl+C` 关不掉、报错信息消失 | 它等价于 `except BaseException`，连 `KeyboardInterrupt`/`SystemExit` 都吞 | 写成 `except Exception as e`，至少记日志 |
| `except` 顺序写反 | 更具体的异常永远不被捕获 | `except` 从上到下匹配，`Exception` 排前面就截胡了 | 具体异常在前，`Exception` 兜底在后 |
| 打开文件忘关 | 文件句柄泄漏，数据没刷盘 | 只 `open` 不 `close` | 用 `with open(...) as f` |
| 读中文乱码 | 中文变成乱码或报 `UnicodeDecodeError` | 读写编码不一致（默认用了系统 GBK） | 读写都显式 `encoding="utf-8"` |
| `"w"` 打开已有文件 | 文件内容被清空 | `"w"` 会先清空再写 | 想保留旧内容用 `"a"` 追加 |
| `read()` 读大文件 | 内存暴涨甚至 OOM | `read()`/`readlines()` 一次性全读进内存 | 用 `for line in f` 流式读 |
| 忘写 `ensure_ascii=False` | JSON 里的中文变成 `\uXXXX` | `json.dumps` 默认 ASCII 转义 | 加 `ensure_ascii=False` |
| 序列化 set/datetime | `TypeError: Object of type set is not JSON serializable` | `json` 只认识 dict/list/str/数字/bool/None | 先转成可序列化类型或传 `default=` |
| `readline()` 带 `\n` | 每行读出来末尾多个换行 | `readline`/`for line in f` 保留行尾换行 | 用 `line.strip()` 去掉 |
| `@contextmanager` 不写 `try/finally` | `with` 块抛异常时清理逻辑不执行 | `yield` 抛异常会中断函数，跳过 yield 之后的代码 | 清理逻辑放 `try/finally`，`yield` 夹中间 |
| `__exit__` 返回 `True` | 异常被静默吞掉 | `__exit__` 返回真值会吞异常 | 默认返回 `False`/`None` 让异常继续传播 |

## 5.14 本章小结

- **异常体系**：`BaseException` 是祖宗，`Exception` 是业务异常的根，`KeyboardInterrupt`/`SystemExit` 在 `Exception` 之外。
- **`try/except/else/finally`**：`except` 兜错、`else` 只在成功时跑（两者互斥）、`finally` 无条件执行。
- **捕获**：`except (A, B) as e` 接多种；多个分支"具体在前、笼统在后"。
- **抛异常**：`raise` 抛、裸 `raise` 重抛、`raise ... from e` 保留因果链、`from None` 切断。
- **自定义异常**：继承 `Exception`，类名以 `Error` 结尾，`__init__` 调 `super().__init__`。
- **文件读写**：`open(path, mode, encoding="utf-8")`；`read`/`readline`/`readlines`/`for line in f`；大文件用流式。
- **`with`**：等价于自动 `try/finally`，原理 `__enter__`/`__exit__`，`@contextmanager` 简化自定义。
- **`json`**：`dumps`/`loads`（字符串）、`dump`/`load`（文件），中文加 `ensure_ascii=False`。
- **`pathlib`**：`Path` + `/` 拼路径，`read_text`/`write_text` 读写，替代 `os.path`。

## 5.15 动手练习

1. 写一个 `safe_divide(a, b)`，`b` 为 0 时返回 `None` 并打印原因，其他情况返回 `a / b`，并确保任何情况下都打印一行 `"计算结束"`。

   <details><summary>参考答案</summary>

   ```python
   def safe_divide(a, b):
       try:
           result = a / b
       except ZeroDivisionError as e:
           print("除数为 0：", e)
           return None
       else:
           return result
       finally:
           print("计算结束")

   print(safe_divide(10, 2))
   print(safe_divide(10, 0))
   ```
   </details>

2. 定义一个自定义异常 `NegativeAgeError`，写一个 `set_age(age)`，当 `age < 0` 时抛出它并带上年龄值，然后 `try/except` 捕获并打印。

   <details><summary>参考答案</summary>

   ```python
   class NegativeAgeError(Exception):
       def __init__(self, age):
           self.age = age
           super().__init__(f"年龄不能为负数：{age}")

   def set_age(age):
       if age < 0:
           raise NegativeAgeError(age)
       return age

   try:
       set_age(-3)
   except NegativeAgeError as e:
       print("捕获到：", e)
   ```
   </details>

3. 把一段包含中文的字符串写入文件 `msg.txt`（用 `with` 和 `utf-8`），再用 `for line in f` 逐行读回来打印。

   <details><summary>参考答案</summary>

   ```python
   with open("msg.txt", "w", encoding="utf-8") as f:
       f.write("你好\n")
       f.write("世界\n")

   with open("msg.txt", "r", encoding="utf-8") as f:
       for line in f:
           print(line.strip())
   ```
   </details>

4. 写一个 `@contextmanager` 版本的 `silent()`，在 `with silent():` 块里无论抛什么异常都被吞掉，但块外照常抛异常。

   <details><summary>参考答案</summary>

   ```python
   from contextlib import contextmanager

   @contextmanager
   def silent():
       try:
           yield
       except Exception:
           pass   # 吞掉块内异常

   with silent():
       int("abc")   # 这里抛 ValueError，被吞掉
   print("继续执行")
   ```
   </details>

5. 用 `pathlib` 和 `json`：把一个含中文的 dict 写成 `data.json`，再读回来，验证内容一致。

   <details><summary>参考答案</summary>

   ```python
   import json
   from pathlib import Path

   data = {"城市": "深圳", "人口": 1756}
   p = Path("data.json")
   p.write_text(json.dumps(data, ensure_ascii=False), encoding="utf-8")
   loaded = json.loads(p.read_text(encoding="utf-8"))
   print(loaded == data)   # True
   ```
   </details>
