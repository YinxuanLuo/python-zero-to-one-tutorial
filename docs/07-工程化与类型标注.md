# 第 07 章 · 工程化与类型标注

> 前面六章，你学的是"怎么写对一段代码"。这一章开始，学的是"怎么写出一堆**不会腐烂**的代码"。
> 脚本和工程的区别，不在代码量，而在三件事：**类型能不能被机器读懂、项目结构清不清楚、能不能被别人装走复用。**
>
> 本章你需要记住的就一件事：**类型标注不是给 Python 看的，是给你和你的同事看的；`mypy` 才是那个真正"看标注"的机器。**

---

## 7.1 为什么 Python 需要类型标注

先给结论：**Python 是动态类型语言——变量没有固定类型，函数也不知道参数是什么类型。** 这在写几十行的脚本时是"爽"，在写几万行的项目时是"慌"。

你是有 JS 基础的人，这一幕你早就见过：JS 也是动态类型，所以后来才有了 TypeScript。Python 走的是同一条路，但**分叉点很关键**：

| | TypeScript | Python 类型标注 |
|---|---|---|
| 谁在检查 | 编译器 `tsc` | 第三方工具 `mypy` |
| 检查后 | 编译成 JS 再跑 | **标注被完全忽略**，直接跑 |
| 运行时 | 类型信息已经没了 | 类型信息还在，但没人执行它 |

看清楚最后一行：**TS 的检查发生在编译期，检查完类型就"焊死"了；Python 的检查发生在运行之前，但运行时 Python 自己根本不管类型。**

先看一个让你感同身受的场景。假设你接手了一段别人写的代码：

```python
def process(user, order, config):
    return user["name"] + str(order["total"]) + config["currency"]
```

盯着看十秒，你能确定这三件事吗：

1. `user` 到底是个 `dict` 还是对象？`user["name"]` 会不会 KeyError？
2. `order["total"]` 是数字还是字符串？为什么要 `str()` 包一层？
3. `config["currency"]` 存在吗？拼出来是 `"alice100USD"` 这种没分隔符的字符串吗？

**答案是你不能。** 函数一多，跨文件一调用，每个参数是什么类型，全靠你的记忆和猜测。这正是动态类型在工程里的代价。

而加了标注之后，同样的函数变成这样：

```python
def process(
    user: dict[str, str],
    order: dict[str, int],
    config: dict[str, str],
) -> str:
    return user["name"] + str(order["total"]) + config["currency"]
```

现在你能一眼看出：`user` 是"字符串到字符串"的字典，`order` 是"字符串到整数"的字典，返回一个字符串。**你省下的不是一次两次的猜测，是接手整个项目的心智成本。**

> 一句话记住它：**类型标注解决的是"人读不懂代码"，不是"机器跑不了代码"。**

## 7.2 类型注解基础：三种写法

先给结论：注解的语法就三件事——**参数后加 `: 类型`，返回值前加 `-> 类型`，变量后加 `: 类型`。** 没别的了。

### 函数注解

```python
def add(a: int, b: int) -> int:
    return a + b


def greet(name: str) -> str:
    return f"hello, {name}"
```

`a: int` 是参数注解，`-> int` 是返回值注解。读起来就是："`add` 接收两个 `int`，返回一个 `int`。"

### 变量注解

```python
name: str = "alice"
age: int = 30
score: float = 98.5
is_active: bool = True
```

变量注解写在变量名和赋值号之间。注意：**注解和赋值是两回事**，`name: str` 只是声明"`name` 应该是 `str`"，真正赋值还是 `= "alice"`。

### 容器泛型（3.9+）

容器要标出"里面装什么类型"，用方括号：

```python
nums: list[int] = [1, 2, 3]
scores: dict[str, int] = {"alice": 90, "bob": 80}
matrix: list[list[int]] = [[1, 2], [3, 4]]
points: tuple[int, int] = (1, 2)   # 元组：长度固定，每个位置类型可不同
unique: set[int] = {1, 2, 3}       # 集合：装 int
```

`list[int]` 读作"整数列表"，`dict[str, int]` 读作"字符串到整数的字典"。
`tuple[int, int]` 能精确到"两个位置各是什么类型"（第一个 `int`、第二个 `int`），
这是它比 `list[int]` 更强的地方——`list` 长度可变，只能标"每个元素"的类型。

### 没有返回值：`-> None`

一个函数如果只做事不返回东西，标注 `-> None`：

```python
def log_message(msg: str) -> None:
    print(msg)
```

`-> None` 明确表示"这个函数返回空"。注意别和"返回 `None` 的字符串"搞混——
`-> None` 是"没有返回值"，`-> str | None` 是"返回字符串或空值"，两码事。

> 版本注意：`list[int]` 这种直接写法是 **Python 3.9** 才支持的。3.8 及以前必须从 `typing` 里导入大写版 `List[int]`、`Dict[str, int]`。本教程基于 3.13，直接用小写。

### Optional / Union：这个值可能是 None

一个函数"可能返回字符串，也可能返回 `None`"，这是最常见的需求。有两种写法：

```python
# 写法一（3.10+，推荐）：用 | 竖线
def find_user(user_id: int) -> str | None:
    users = {1: "alice", 2: "bob"}
    return users.get(user_id)

# 写法二（老版本兼容）：用 typing.Optional
from typing import Optional

def find_user_old(user_id: int) -> Optional[str]:
    users = {1: "alice", 2: "bob"}
    return users.get(user_id)
```

`str | None` 和 `Optional[str]` 是完全等价的两个写法，前者更现代、更好读。

"可能是 A 也可能是 B"的更一般形式是 `Union`：

```python
from typing import Union

def parse_id(raw: str) -> Union[int, str]:
    # 能转成数字就返回 int，否则原样返回 str
    return int(raw) if raw.isdigit() else raw
```

`Union[int, str]` 表示"返回 `int` 或 `str` 都行"，3.10+ 也能写成 `int | str`。

### 类型别名：给复杂类型起个名字

当类型又长又重复出现时，起个名字：

```python
UserId = int
UserDict = dict[int, str]

users: UserDict = {1: "alice", 2: "bob"}
```

别名**不创建新类型**，只是让代码更短更清楚。`UserId` 就是 `int`，mypy 不会区分它俩。

### 完整跑一遍

把上面这些放进一个文件运行，看看输出：

```python
name: str = "alice"
age: int = 30
score: float = 98.5
is_active: bool = True

nums: list[int] = [1, 2, 3]
scores: dict[str, int] = {"alice": 90, "bob": 80}

def add(a: int, b: int) -> int:
    return a + b

def find_user(user_id: int) -> str | None:
    users = {1: "alice", 2: "bob"}
    return users.get(user_id)

print(add(1, 2))             # 3
print(name, age, score, is_active)  # alice 30 98.5 True
print(nums)                  # [1, 2, 3]
print(scores)                # {'alice': 90, 'bob': 80}
print(find_user(1))          # alice
print(find_user(99))         # None
```

运行结果：

```text
3
alice 30 98.5 True
[1, 2, 3]
{'alice': 90, 'bob': 80}
alice
None
```

> 一句话记住它：**注解就三件事——`参数: 类型`、`-> 返回类型`、`变量: 类型`；容器用 `list[int]`，可空用 `X | None`。**

## 7.3 运行时 vs 静态检查：注解到底管不管用

先给结论，而且这个结论会颠覆你的预期：**Python 的类型注解在运行时几乎什么都不做。** 你写 `x: int = "hello"`，Python 照样跑，一个字都不抱怨。

看这段代码，注意最后两行：

```python
def fake_typed(x: int) -> int:
    return x

# 你声明了"x 是 int"，但传一个字符串进去，运行时完全不拦你
print(fake_typed("not a number"))
```

运行结果：

```text
not a number
```

**没有报错。** 为什么？因为注解只是被存进一个叫 `__annotations__` 的属性里，运行时**从来不读它来检查**。你甚至可以自己看一眼：

```python
def fake_typed(x: int) -> int:
    return x

print(fake_typed.__annotations__)
```

运行结果：

```text
{'x': <class 'int'>, 'return': <class 'int'>}
```

注解变成了一个字典，躺在函数的 `__annotations__` 里，仅此而已。它既不改变执行，也不拦截错误。

那注解还有什么用？**答案是：给静态检查器看。** 这就是"运行时检查"和"静态检查"的分水岭：

| 维度 | 运行时检查 | 静态检查（mypy） |
|---|---|---|
| 什么时候发生 | 程序跑起来之后 | 程序跑起来**之前**（命令行） |
| 谁在检查 | Python 解释器 | 第三方工具 mypy |
| 检查什么 | 语法、运行时错误（除以零、索引越界） | 类型对不对 |
| 发现错误的时机 | 已经太晚了（上线才炸） | 还没运行就拦住 |
| 代价 | 无 | 要多写注解、多跑一步命令 |

**用一个类比收束：** 注解是"给机器看的备注"，mypy 是"读备注的机器"。你写了备注但没跑 mypy，等于在代码里写了一堆没人看的注释——纯自我安慰。

> 一句话记住它：**注解在运行时是"空气"，只有交给 mypy 才会变成"警察"。**

## 7.4 mypy：把注解变成"执法"

先给结论：**mypy 是一个静态类型检查器。它在运行代码之前读一遍代码，发现类型对不上就报错。** 它是 Python 生态里"类型标注"这件事的官方默认答案。

### 安装

```bash
pip install mypy
```

装完确认一下：

```bash
mypy --version
```

输出（本机实测）：

```text
mypy 2.4.0 (compiled: yes)
```

> 版本可能更新，只要有 `mypy` 字样就是装好了。

### 怎么用

```bash
mypy your_file.py
```

它对文件做一次"纯静态"扫描——**不执行任何代码**，只看类型关系。

### 真实报错一：把 int 赋给 str 变量

写这样一个文件 `demo.py`：

```python
def add(a: int, b: int) -> int:
    return a + b

result: str = add(1, 2)   # add 返回 int，却赋给了 str 变量
name: str = 123           # 把 int 赋给 str
```

跑 mypy：

```bash
mypy demo.py
```

真实输出：

```text
demo.py:4: error: Incompatible types in assignment (expression has type "int", variable has type "str")  [assignment]
demo.py:5: error: Incompatible types in assignment (expression has type "int", variable has type "str")  [assignment]
Found 2 errors in 1 file (checked 1 source file)
```

看关键信息：**`Incompatible types in assignment`**——赋值两边类型不兼容，还精确告诉你哪一行（`demo.py:4`）。

### 真实报错二：Optional 没处理 None

这是 mypy 最有价值的一类报错。看这段：

```python
def find_user(user_id: int) -> str | None:
    users = {1: "alice"}
    return users.get(user_id)

user = find_user(1)
print(user.upper())   # user 可能是 None，调 .upper() 会炸
```

这段代码**运行时**可能没事（因为 `find_user(1)` 真返回了 `"alice"`），但**逻辑上是危险的**：万一哪天传了不存在的 id，`user` 就是 `None`，`None.upper()` 会抛 `AttributeError`。mypy 在运行前就抓到了：

```bash
mypy demo.py
```

真实输出：

```text
demo.py:6: error: Item "None" of "str | None" has no attribute "upper"  [union-attr]
Found 1 error in 1 file (checked 1 source file)
```

**这就是 mypy 的核心价值：它抓的是"现在没炸、迟早会炸"的隐藏 bug。** 运行时能抓的 bug 已经晚了，mypy 抓的是还没发生的。

修复方式就是显式处理 None：

```python
user = find_user(1)
if user is not None:          # 收窄类型：这里 user 一定是 str
    print(user.upper())
else:
    print("用户不存在")
```

再跑 mypy，就干净了：

```text
Success: no issues found in 1 source file
```

### mypy 只查你"标注过"的部分

一个关键事实：**mypy 不会对没标注的函数挑刺。** 看这个：

```python
def add(a, b):        # 没写任何注解
    return a + b

print(add(1, "x"))    # 运行时会炸，但 mypy 不管
```

跑 mypy：

```text
Success: no issues found in 1 source file
```

因为 `add` 没有注解，mypy 默认把它当 `Any`，直接跳过。所以**标注覆盖率越高，mypy 越有用**——这也是为什么工程里会追求"全量标注"。

### 用配置文件控制严格度

mypy 的行为可以在 `pyproject.toml` 里配置。最常见的两个开关：

```toml
[tool.mypy]
python_version = "3.13"
strict = true
warn_return_any = true
```

- `strict = true`：打开所有严格检查，包括"**强制每个函数都必须有注解**"。开了它，上面那个没标注的 `add` 就会报错，而不是被悄悄跳过。
- `warn_return_any = true`：函数返回 `Any` 时警告，防止类型信息悄悄流失。

新手建议**先别开 strict**，否则历史代码会给你铺天盖地的报错。等注解补得差不多了，再逐步收紧。

### mypy 在真实项目里的位置：CI

mypy 单独跑一两次意义不大，真正的价值是**挂在 CI（持续集成）里，每次提交都自动跑**：

```bash
pip install mypy
mypy .    # 检查整个项目，有任何类型错误就让提交失败
```

这样类型错误根本进不了主分支。这是"工程化"和"我本地跑一下"的本质区别——**检查要自动化、常态化，而不是想起来才跑。**

> 一句话记住它：**mypy 是"编译期"的免费 bug 探测器，但只对"写了注解"的代码有效；挂进 CI 它才真正值钱。**

## 7.5 typing 模块：几个进阶类型

先给结论：基础类型（`int`/`str`/`list`）表达不了的复杂类型关系，`typing` 模块来补。但**能不用就不用**——简单注解永远优先于花哨注解。

挑最有用的六个讲，其余用到再查。

### Any：主动放弃检查

```python
from typing import Any

def parse(data: Any) -> Any:
    return data
```

`Any` 表示"我不在乎类型，别查我"。它像一个逃生舱，跟 JS 的 `any` 是同一个东西。**用多了等于没标注**——一个全是 `Any` 的项目，mypy 形同虚设。只在"确实不知道类型"（比如第三方库返回）时用。

### Callable：注解"一个函数"

当参数本身是一个函数时：

```python
from typing import Callable

def apply_twice(f: Callable[[int], int], x: int) -> int:
    return f(f(x))

def plus_one(n: int) -> int:
    return n + 1

print(apply_twice(plus_one, 10))   # 12
```

`Callable[[int], int]` 读作"接收一个 `int`、返回 `int` 的函数"。方括号里是参数列表，逗号后是返回类型。

### TypeVar + Generic：保留类型关系

这是最容易困惑、也最有用的一对。先看问题：有个函数返回列表的第一个元素，怎么注解？

```python
def first(items):
    return items[0] if items else None
```

如果传 `list[int]`，返回 `int`；传 `list[str]`，返回 `str`。**"传什么类型就返回什么类型"这种关系，普通注解表达不了。** 这时用 `TypeVar`：

```python
from typing import TypeVar

T = TypeVar("T")

def first(items: list[T]) -> T | None:
    return items[0] if items else None
```

`T = TypeVar("T")` 声明一个"类型变量"，`list[T] -> T | None` 表达"输入 `T` 的列表，输出 `T` 或 `None`"。mypy 就能推断：

```python
print(first([1, 2, 3]))        # 返回 int
print(first(["a", "b"]))       # 返回 str
```

运行结果：

```text
1
a
```

类型变量放进类里，就是 `Generic`：

```python
from typing import TypeVar, Generic

T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, value: T) -> None:
        self.value = value

    def get(self) -> T:
        return self.value

int_box = Box(42)
str_box = Box("hi")
print(int_box.get())   # 42
print(str_box.get())   # hi
```

`Box[int]` 和 `Box[str]` 是"同一个类、不同参数化"，这就是泛型的意义——一套代码，多种类型。

#### TypeVar 进阶：约束类型范围

有时你不想让 `T` 是"任意类型"，而想限制它"必须属于某一类"。用 `bound`：

```python
from typing import TypeVar

T = TypeVar("T", bound=int | float)   # T 只能是 int 或 float

def double(x: T) -> T:
    return x * 2

print(double(3))     # 6
print(double(2.5))   # 5.0
```

`bound=int | float` 告诉 mypy："`T` 必须是 `int` 或 `float`"，于是 `double("abc")` 会被 mypy 拦住，而普通 `TypeVar("T")` 不会。

#### 多个类型变量

一个函数涉及两个独立类型时，声明两个 `TypeVar`：

```python
from typing import TypeVar

K = TypeVar("K")
V = TypeVar("V")

def get_or_default(mapping: dict[K, V], key: K, default: V) -> V:
    return mapping.get(key, default)

print(get_or_default({"a": 1}, "a", 0))   # 1
print(get_or_default({"a": 1}, "b", 0))   # 0
```

`K` 是键的类型，`V` 是值的类型，mypy 能检查出"键和 `key` 同类型、值和 `default` 同类型"这种跨参数关系。

### Protocol：把鸭子类型"显式化"

还记得第 04 章的鸭子类型吗——"不看它是什么类，只看它有没有那个方法"。`Protocol` 就是把鸭子类型**写进类型系统**：

```python
from typing import Protocol

class HasArea(Protocol):
    def area(self) -> float: ...

class Square:
    def __init__(self, side: float) -> None:
        self.side = side
    def area(self) -> float:
        return self.side * self.side

class Circle:
    def __init__(self, radius: float) -> None:
        self.radius = radius
    def area(self) -> float:
        return 3.14 * self.radius * self.radius

def total_area(shapes: list[HasArea]) -> float:
    return sum(s.area() for s in shapes)

print(total_area([Square(2), Circle(3)]))   # 32.26
```

关键在于：**`Square` 和 `Circle` 都没有 `class Square(HasArea)` 这样继承。** 只要它们有 `area() -> float` 方法，mypy 就自动认为它们"符合 `HasArea`"。这就是结构性子类型（structural typing），和 TS 的"接口自动匹配"是同一套思路。

### TypedDict：给字典的"形状"做注解

普通 `dict[str, int]` 只能说明"键是字符串、值是整数"，但说明不了"这个字典必须有哪些键"。`TypedDict` 解决这个：

```python
from typing import TypedDict

class Movie(TypedDict):
    title: str
    year: int

movie: Movie = {"title": "The Matrix", "year": 1999}
print(movie["title"])   # The Matrix
```

`Movie` 告诉 mypy："这是一个字典，必须有 `title`（str）和 `year`（int）两个键。" 于是**少一个键、多一个不存在的键、类型写错**，mypy 都能抓到——而普通 `dict` 注解抓不到这些。

> 版本注意：`TypedDict` 在 3.8+ 可用，但运行时它**不强制**——少写了键照样能跑，只有 mypy 会报。它本质也是"给静态检查看的"。

### 小结：什么时候用哪个

| 场景 | 用什么 |
|---|---|
| 放弃检查 | `Any` |
| 参数是函数 | `Callable[[...], ...]` |
| 传什么返回什么 | `TypeVar` / `Generic` |
| 鸭子类型的静态化 | `Protocol` |
| 字典的固定形状 | `TypedDict` |

> 一句话记住它：**`typing` 模块解决"基础类型表达不了的关系"，但记住——能用 `int`/`str`/`list` 说清楚，就别上花活。**

## 7.6 dataclasses：告别手写样板代码

先给结论：**`@dataclass` 一个装饰器，自动帮你生成 `__init__`、`__repr__`、`__eq__` 这三个手写起来又臭又长、还容易写错的方法。**

### 先看手写有多痛苦

写一个"代表坐标点"的类，不带 dataclass：

```python
class Point:
    def __init__(self, x: int, y: int):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Point(x={self.x}, y={self.y})"

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented
        return self.x == other.x and self.y == other.y

p1 = Point(1, 2)
p2 = Point(1, 2)
print(p1)         # Point(x=1, y=2)
print(p1 == p2)   # True
```

**9 行，其中 7 行是"样板代码"**——它们没有业务逻辑，就是机械地把字段存起来、打印出来、比较一下。一个项目里几十个这样的类，样板代码就是几百行的纯噪音。

### dataclass 版：3 行

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

p1 = Point(1, 2)
p2 = Point(1, 2)
print(p1)         # Point(x=1, y=2)
print(p1 == p2)   # True
print(p1 == Point(3, 4))   # False
```

运行结果：

```text
Point(x=1, y=2)
True
False
```

三件事自动发生：

1. **`__init__`**：`Point(1, 2)` 能直接构造，字段按声明顺序传。
2. **`__repr__`**：`print(p1)` 打印出 `Point(x=1, y=2)`，而不是难看的 `<__main__.Point object at 0x...>`。
3. **`__eq__`**：`p1 == p2` 按**字段值**比较，而不是按对象身份比较。

> 对 JS 开发者来说，这大概类似"自动生成的构造函数 + `JSON.stringify` + 深比较"，但它是语言层面的，零运行时开销。

### 可变默认值：必须用 field

dataclass 里最经典的坑，和函数默认参数的坑是**同一个**。看这个：

```python
from dataclasses import dataclass, field

@dataclass
class User:
    name: str
    tags: list[str] = field(default_factory=list)   # ✅ 正确

u1 = User("alice")
u2 = User("bob")
u1.tags.append("new")
print(u1.tags)   # ['new']
print(u2.tags)   # []  ← 两个实例的 tags 是独立的
```

运行结果：

```text
['new']
[]
```

为什么不能直接写 `tags: list[str] = []`？因为那个 `[]` 只在**类定义时创建一次**，之后所有实例会共享同一个列表——和 `def f(x, lst=[])` 是同一个坑。`field(default_factory=list)` 的意思是"每次创建实例时，**调用** `list()` 生成一个新的空列表"。

其实直接写 `= []` 连 Python 都会拦你，运行会看到：

```text
ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory
```

dataclass 把"可变默认值"这个历史坑，变成了**编译期直接报错**，这是它设计得好的地方。

### 顺便：带默认值

```python
from dataclasses import dataclass

@dataclass
class User:
    name: str
    age: int = 18          # 有默认值的字段

print(User("alice"))       # User(name='alice', age=18)
print(User("bob", 30))     # User(name='bob', age=30)
```

运行结果：

```text
User(name='alice', age=18)
User(name='bob', age=30)
```

### 两个常用参数：frozen 和 order

`@dataclass` 接受几个开关参数，最常用的两个：

```python
from dataclasses import dataclass

@dataclass(frozen=True)   # 冻结：实例创建后字段不可改
class Config:
    host: str
    port: int

c = Config("localhost", 8080)
print(c.host)   # localhost
```

`frozen=True` 让实例变成"不可变"，改字段会报错：

```python
c.port = 9090
```

运行会看到真实报错：

```text
dataclasses.FrozenInstanceError: cannot assign to field 'port'
```

这在"配置对象、坐标点"这类创建后就不该改的场景里很有用——用异常类型在源头拦住误改。

`order=True` 则自动生成比较方法（`<`、`>` 等），让 dataclass 实例能直接排序：

```python
from dataclasses import dataclass

@dataclass(order=True)
class Score:
    value: int

scores = [Score(3), Score(1), Score(2)]
print(sorted(scores))   # [Score(value=1), Score(value=2), Score(value=3)]
```

运行结果：

```text
[Score(value=1), Score(value=2), Score(value=3)]
```

> 注意 `order=True` 是**按字段声明顺序**依次比较的，多字段时先比第一个字段。

### asdict / astuple：转成普通容器

有时要把 dataclass 实例转成字典（比如交给 JSON 序列化），用 `dataclasses.asdict`：

```python
from dataclasses import dataclass, asdict

@dataclass
class Point:
    x: int
    y: int

print(asdict(Point(1, 2)))   # {'x': 1, 'y': 2}
```

运行结果：

```text
{'x': 1, 'y': 2}
```

> 一句话记住它：**`@dataclass` 帮你删掉 `__init__`/`__repr__`/`__eq__` 三坨样板代码；可变字段必须用 `field(default_factory=...)`，要不可变加 `frozen=True`，要转字典用 `asdict`。**

## 7.7 项目结构：一个正经工程长什么样

先给结论：**脚本是"一个文件"，工程是"一套约定好的目录"。** 目录结构越标准，别人（和三个月后的你）越不用猜。

一个最小的现代 Python 工程长这样：

```text
myproject/
├── pyproject.toml          # 项目元信息 + 依赖 + 工具配置（唯一标准）
├── requirements.txt        # 运行时依赖（可选，部署时用）
├── requirements-dev.txt    # 开发依赖（可选）
├── src/
│   └── mypackage/          # 你的包，用 src 布局避免导入混乱
│       ├── __init__.py
│       └── core.py
└── tests/
    └── test_core.py        # 第 08 章讲测试
```

### pyproject.toml：一切配置的归宿

`pyproject.toml` 是现在**唯一该用的**项目配置文件。它一次性描述"这个项目叫什么、要什么 Python、依赖哪些包"：

```toml
[project]
name = "myproject"
version = "0.1.0"
description = "一个示例项目"
requires-python = ">=3.9"
dependencies = [
    "requests>=2.0",
]

[project.optional-dependencies]
dev = [
    "pytest",
    "mypy",
    "ruff",
]
```

- `dependencies`：**运行时**依赖，用户装你的包时自动带上。
- `optional-dependencies.dev`：**开发**依赖，只有 `pip install -e ".[dev]"` 时才装。

### requirements.txt vs requirements-dev.txt

这是老派的依赖管理方式，现在还有大量项目在用：

```text
# requirements.txt —— 运行时依赖（部署到服务器也要装）
requests>=2.0
flask>=3.0

# requirements-dev.txt —— 开发依赖（只在开发机装）
pytest
mypy
ruff
```

两者的区别就一条：**运行时依赖是"程序没它跑不起来"，开发依赖是"只有你开发时用得到"。** 把测试工具装到生产服务器上，是浪费和攻击面。

### src 布局 vs 平铺布局

上面的目录用了 `src/mypackage/` 这种"src 布局"。还有一种是老式的"平铺布局"，包直接放在根目录：

```text
# 平铺布局（老式）
myproject/
├── mypackage/       # 包直接放根目录
│   └── __init__.py
└── tests/
```

**src 布局更好的原因很硬核：它逼你测试的是"安装后的包"，而不是"当前目录下的源码"。** 平铺布局下，你 `import mypackage` 可能导入的是根目录那份（因为 Python 会优先找当前目录），而不是真正安装的那份——于是"测试通过但打包后坏了"这种乌龙就有了生存空间。src 布局把源码挪到 `src/`，当前目录不再自动可见，测试只能 import 安装版，问题提前暴露。

> 一句话结论：**新项目一律用 src 布局。**

### `__init__.py` 是干嘛的

你可能注意到每个包目录里都有一个空的 `__init__.py`。它做两件事：

1. **标记"这是一个包"**。没有它，Python 不会把这个目录当成可导入的包（Python 3.3+ 引入了 namespace package，空的 `__init__.py` 可以省略，但显式写出来更清楚）。
2. **放包的初始化代码**。你可以在里面定义"从这个包导出什么"：

```python
# mypackage/__init__.py
from .core import hello   # 让用户能直接 mypackage.hello 调用
```

这样外部用户不用记"`hello` 在 `core` 模块里"，直接 `import mypackage; mypackage.hello()` 就行。

### setup.py 演进史：三代更迭

了解这段历史，你在网上搜到老代码时就不会懵：

| 时代 | 文件 | 特点 | 问题 |
|---|---|---|---|
| 第一代 | `setup.py` | 一段 Python 代码，调用 `setup()` | 是"代码"不是"配置"，能执行任意逻辑，有安全风险 |
| 第二代 | `setup.cfg` | 纯 INI 配置 | 安全了，但表达力弱，工具各搞各的 |
| 第三代 | `pyproject.toml` | 统一标准，pip/build 直接读 | 现在的事实标准 |

**现在的结论很干脆：新项目只用 `pyproject.toml`，`setup.py` 是历史遗留，见到别慌但别模仿。**

> 一句话记住它：**工程化的第一步不是写代码，是把目录和 `pyproject.toml` 立起来——标准目录比任何注释都更能说明问题。**

## 7.8 打包：让别人 `pip install` 装上你的代码

先给结论：**打包就是把你的代码变成一个 `.whl` 文件，别人 `pip install` 就能装。** 开发时用可编辑安装，发布时用 `build`。

### 可编辑安装：pip install -e .

开发阶段，你想"边改代码边测试"，不希望每改一行就重装一次。这时用 `-e`（editable）：

```bash
pip install -e .
```

它的效果是**安装一个"链接"而不是"拷贝"**——你改代码，安装的那份立即跟着变。真实演示，用一个最小包：

```text
pkgdemo/
├── pyproject.toml
└── src/
    └── demopkg/
        └── __init__.py
```

`pyproject.toml`：

```toml
[build-system]
requires = ["setuptools>=61"]
build-backend = "setuptools.build_meta"

[project]
name = "demopkg"
version = "0.1.0"
requires-python = ">=3.9"
```

`__init__.py`：

```python
VERSION = "0.1.0"

def hello(name: str) -> str:
    return f"hello, {name}"
```

跑安装：

```bash
pip install -e .
```

真实输出（截取关键几行）：

```text
Successfully built demopkg
Installing collected packages: demopkg
Successfully installed demopkg-0.1.0
```

装完就能在任何地方 `import`：

```python
import demopkg
print(demopkg.hello("world"))
```

输出：

```text
hello, world
```

### 发布：python -m build 出 wheel

要发布给全世界，用 `build` 工具：

```bash
pip install build
python -m build
```

它会产出 `dist/` 目录下的两个文件：

```text
dist/
├── demopkg-0.1.0-py3-none-any.whl    # wheel：二进制安装包
└── demopkg-0.1.0.tar.gz              # sdist：源码包
```

真实输出（截取结尾）：

```text
Successfully built demopkg-0.1.0.tar.gz and demopkg-0.1.0-py3-none-any.whl
```

几个名词记一下：

| 名词 | 是什么 | 类比 |
|---|---|---|
| `wheel`（`.whl`） | 预构建的安装包，`pip install` 直接解压 | 类似 npm 的 `node_modules` 包 |
| `sdist`（`.tar.gz`） | 源码分发包，别人拿到后要重新构建 | 类似源码仓库的 tar |
| `editable`（`-e`） | 链接式安装，改代码立即生效 | 类似 `npm link` |

### 别人怎么装你的 wheel

拿到 `.whl` 文件的人，一条命令就能装：

```bash
pip install dist/demopkg-0.1.0-py3-none-any.whl
```

或者如果你把包发布到了 PyPI（Python 官方的包仓库，相当于 npm registry），别人直接：

```bash
pip install demopkg
```

这就是 Python "生态即宇宙"的机制——`pip install` 背后就是"下载 wheel → 解压到 site-packages"。

### 可编辑安装的原理（为什么 -e 能实时生效）

普通安装是把你的代码**拷贝**进 `site-packages`，所以你改了源码，装的那份还是旧的。而 `-e`（editable）安装的是**一个指向你源码目录的"指针"**（一个 `.pth` 文件），Python 每次 import 都会顺着指针找到你正在编辑的源码。

**代价**：指针只在你的开发机上有效，换个机器就不成立了。所以 `-e` 只能开发时用，发布必须用真正的 wheel。

> 一句话记住它：**开发时 `pip install -e .`（装指针），发布时 `python -m build`（出 `.whl` 给别人装）。**

## 7.9 代码风格：别自己记，交给工具

先给结论：Python 社区对风格统一的执念，落到工具上，就是**一个 linter（查问题）+ 一个 formatter（改格式）**。你自己不用记规则。

### PEP 8：风格的"宪法"

PEP 8 是 Python 官方风格指南。核心几条：

| 规则 | 内容 |
|---|---|
| 缩进 | 4 个空格，**禁止 Tab** |
| 命名 | 变量函数 `snake_case`、类 `PascalCase`、常量 `UPPER_CASE` |
| 行宽 | 一行最多 79 字符（工程里常放宽到 88） |
| 引号 | 单双引号等价，但项目内统一 |

你不需要背——工具会替你检查。

### 三个工具，分工不同

| 工具 | 角色 | 一句话 |
|---|---|---|
| `black` | 格式化器 | 把代码格式"拍平"到唯一格式，不商量 |
| `ruff` | 新一代 linter + formatter | 极快，一个工具干两件事（推荐） |
| `flake8` | 经典 linter | 老牌，慢但稳 |

安装和使用（以 `ruff` 为例）：

```bash
pip install ruff
ruff check .        # 检查问题（linter）
ruff format .       # 自动格式化（formatter）
```

`ruff check` 抓到问题时的真实输出风格是这样：

```text
example.py:1:8: F401 [*] `os` imported but unused
Found 1 error.
[*] 1 fixable with the `--fix` option.
```

`F401` 是规则编号（未使用的导入），`[*]` 表示能自动修。

> 一句话记住它：**风格规则交给 `ruff`/`black` 自动处理，你只负责写逻辑；团队统一风格的唯一成本是"大家都用同一个工具"。**

## 7.10 日志：别再用 print 调试

先给结论：**`print` 是给人临时看的，`logging` 是给系统长期看的。** 到了工程阶段，该把 `print` 换成 `logging`。

### 为什么 print 不够

`print` 有三个致命问题：**没法分级**（你不能区分"普通信息"和"严重错误"）、**没法关闭**（上线了你不想刷屏，但删又删不掉）、**没有时间戳和来源**（日志混在一起，不知道谁打的）。

`logging` 全解决：

```python
import logging

logging.basicConfig(level=logging.INFO)
logging.info("用户 %s 登录", "alice")
logging.warning("磁盘空间不足")
logging.error("数据库连接失败")
```

运行结果：

```text
INFO:root:用户 alice 登录
WARNING:root:磁盘空间不足
ERROR:root:数据库连接失败
```

看输出的结构：**级别 + 来源 + 消息**，一眼就知道严重程度。

### 五个级别

从低到高，级别决定"要不要显示"：

```python
import logging

logging.basicConfig(level=logging.WARNING)   # 只显示 WARNING 及以上

logging.debug("调试信息")      # 被过滤，不显示
logging.info("普通信息")       # 被过滤，不显示
logging.warning("警告")        # 显示
logging.error("错误")          # 显示
```

运行结果：

```text
WARNING:root:警告
ERROR:root:错误
```

`level=logging.WARNING` 的意思是"只显示 WARNING 及以上级别"，`DEBUG` 和 `INFO` 被拦掉。**开发时设 `DEBUG`，上线设 `WARNING`，不用改代码就能控制日志量。**

级别表：

| 级别 | 数值 | 用途 |
|---|---|---|
| `DEBUG` | 10 | 调试细节，开发时看 |
| `INFO` | 20 | 正常流程，如"用户登录" |
| `WARNING` | 30 | 异常但能继续，如"磁盘快满" |
| `ERROR` | 40 | 出错了，如"数据库连不上" |
| `CRITICAL` | 50 | 致命，如"服务要崩了" |

> 一句话记住它：**`print` 是一次性的，`logging` 是分级的、可开关的、带来源的——工程里用后者。**

## 7.11 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 以为注解会强制类型 | `def f(x: int)` 传字符串不报错 | 注解在运行时被忽略 | 用 `mypy` 做静态检查 |
| 只写注解不跑 mypy | 类型错误照常上线 | 注解是给 mypy 看的，不跑等于没写 | CI 里加 `mypy .` |
| 没标注的代码 mypy 不管 | mypy 报 `Success` 但代码有 bug | 没标注的部分按 `Any` 跳过 | 追求全量标注 |
| 用 `list[int]` 在 3.8 报错 | `TypeError: 'type' object is not subscriptable` | `list[int]` 是 3.9+ 语法 | 3.8 用 `typing.List[int]` |
| `Optional` 没处理 None | mypy 报 `union-attr` | 标注了 `X \| None` 却直接调方法 | `if x is not None` 收窄后再用 |
| dataclass 可变默认值 | `ValueError: ... use default_factory` | 直接写 `= []` 会共享列表 | `field(default_factory=list)` |
| 生产环境装开发依赖 | 服务器装了 pytest/mypy | 依赖没拆 runtime/dev | 拆 `requirements.txt` 和 `-dev.txt` |
| 用 `setup.py` 建新项目 | 网上老教程都这么写 | 那是历史遗留 | 新项目用 `pyproject.toml` |
| 用 `print` 打日志 | 上线日志刷屏、关不掉 | print 无级别、无开关 | 用 `logging` 分级 |

## 7.12 本章小结

- **类型标注解决"人读不懂代码"**，不是"机器跑不了代码"；它的本质是给静态检查器看的备注。
- 注解语法就三件事：`参数: 类型`、`-> 返回类型`、`变量: 类型`；容器用 `list[int]`（3.9+），可空用 `X | None`。
- **注解在运行时是空气**，存在 `__annotations__` 里没人执行；真正执法的是 `mypy`。
- `mypy` 抓的是"现在没炸、迟早会炸"的隐藏 bug，尤其擅长抓 `Optional` 没处理 `None`。
- `typing` 模块补基础类型表达不了的关系：`Any` 放弃检查、`Callable` 注解函数、`TypeVar`/`Generic` 保留类型关系、`Protocol` 静态化鸭子类型、`TypedDict` 固定字典形状。
- `@dataclass` 自动生成 `__init__`/`__repr__`/`__eq__`；可变字段必须 `field(default_factory=...)`。
- 项目结构的标准答案是 `pyproject.toml` + `src/` 布局；`setup.py` 是历史，`requirements.txt` 管依赖拆分。
- 开发用 `pip install -e .`（可编辑），发布用 `python -m build`（出 `.whl`）。
- 风格交给 `ruff`/`black`，日志交给 `logging`——别自己记规则、别用 `print` 打日志。

1. 给下面这个没标注的函数补全类型注解，并用 `mypy` 检查通过：

   ```python
   def merge(left, right):
   ```

   ```python
   def merge(left: list[int], right: list[int]) -> list[int]:
       result: list[int] = []
       result.extend(left)
       result.extend(right)
       return result
   ```

   保存后 `mypy` 检查应输出 `Success: no issues found`。
   </details>

2. 下面这段代码有一个"现在能跑、迟早会炸"的隐藏 bug，请用 `mypy` 找出来并修复：

   ```python
   def get_username(uid: int) -> str | None:
       table = {1: "alice"}
       return table.get(uid)

   name = get_username(2)
   print(name.upper())
   ```

   <details><summary>参考答案</summary>

   `mypy` 会报 `Item "None" of "str | None" has no attribute "upper"`。
   因为 `get_username(2)` 返回 `None`，`None.upper()` 运行时会抛 `AttributeError`。修复：

   ```python
   name = get_username(2)
   if name is not None:
       print(name.upper())
   else:
       print("用户不存在")
   ```
   </details>

3. 写一个 `@dataclass` 类 `Order`，字段有 `order_id: int`、`items: list[str]`、`total: float`，
   要求 `items` 使用 `default_factory`。然后验证：两个实例的 `items` 互不影响。

   <details><summary>参考答案</summary>

   ```python
   from dataclasses import dataclass, field

   @dataclass
   class Order:
       order_id: int
       total: float
       items: list[str] = field(default_factory=list)

   o1 = Order(1, 9.9)
   o2 = Order(2, 19.9)
   o1.items.append("apple")
   print(o1.items)   # ['apple']
   print(o2.items)   # []
   ```
   </details>

4. 把 `print` 换成 `logging`：写一段代码，开发时能打印 `DEBUG` 日志，但上线时（改一个配置）
   只显示 `WARNING` 及以上。

   <details><summary>参考答案</summary>

   ```python
   import logging

   # 开发：logging.DEBUG；上线：logging.WARNING
   logging.basicConfig(level=logging.DEBUG)

   logging.debug("进入函数")
   logging.warning("这里有问题")

   # 把 level 改成 logging.WARNING 后，debug 那一行就不显示了
   ```
   </details>
