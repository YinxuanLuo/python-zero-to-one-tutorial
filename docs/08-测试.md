# 第 08 章 · 测试：让代码敢被改

> 前七章你写的是"能跑的代码"。这一章解决一个更隐蔽的问题：**你怎么证明你的代码是对的，而且以后改了也不会坏？**
>
> 本章你需要记住的就一件事：**没测试的代码不是"代码"，是"没人敢动的定时炸弹"——测试给你的不是正确性证明，是"改动的勇气"。**

---

## 8.1 为什么需要测试：从 Jest 说起

先给结论：**你有 JS 基础，那么 Jest 你已经会了——pytest 和它干的是同一件事，只是语法不同。** 把思维直接搬过来就行。

先对个表，你立刻就有坐标感：

| 概念 | Jest（JS） | pytest（Python） |
|---|---|---|
| 测试文件 | `*.test.js` | `test_*.py` |
| 测试函数 | `test("...", () => {...})` | `def test_xxx():` |
| 断言 | `expect(x).toBe(y)` | `assert x == y` |
| 跑测试 | `npm test` | `pytest` |
| 测试异常 | `expect(() => f()).toThrow()` | `pytest.raises(...)` |
| 准备数据 | `beforeEach` / `beforeAll` | `@pytest.fixture` |
| 多组数据 | `it.each([...])` | `@pytest.mark.parametrize` |
| Mock | `jest.mock` | `unittest.mock` |

看，思想一模一样，只是换个皮。**你不需要重新学"测试"，只需要学"Python 怎么表达测试"。**

### 为什么测试值得写

先看一个没有测试时必然发生的故事。你写了个函数：

```python
def calc_total(price, quantity, discount=0.0):
    return price * quantity * (1 - discount)
```

三个月后，需求变了："数量为 0 时应该返回 0，而不是 0 元"。你改成：

```python
def calc_total(price, quantity, discount=0.0):
    if quantity == 0:
        return price          # 手滑，本意是 return 0
    return price * quantity * (1 - discount)
```

改完你"感觉没问题"，上线了。结果一个"空订单"场景突然显示订单金额等于单价。**这就是没有测试的代价：你不敢改，改了也不知道改没改对。**

如果有个测试：

```python
def test_calc_total_zero_quantity():
    assert calc_total(100, 0) == 0   # 这个断言会拦住你的手滑
```

你改完一跑，测试当场红了。**测试不是证明"你这次写对了"，是证明"你这次没把之前对的改坏"。**

> 一句话记住它：**测试买到的是"以后敢改的勇气"——没测试的代码，改一行都提心吊胆。**

## 8.2 pytest 快速上手：最朴素的断言

先给结论：**pytest 的核心就一个 `assert`。** 你平时怎么"心里验证"代码，就怎么写测试，几乎零学习成本。

### 安装

```bash
pip install pytest
```

确认：

```bash
pytest --version
```

输出（本机实测）：

```text
pytest 9.1.1
```

### 第一个测试

先写一段要测的业务代码（就放同一个文件里）：

```python
def add(a, b):
    return a + b


def average(nums):
    if not nums:
        raise ValueError("列表不能为空")
    return sum(nums) / len(nums)
```

再写测试。注意：**测试函数必须以 `test_` 开头**，否则 pytest 不会收集它：

```python
def test_add_basic():
    assert add(1, 2) == 3
    assert add(-1, 1) == 0


def test_average():
    assert average([2, 4, 6]) == 4
    assert average([5]) == 5
```

跑起来：

```bash
pytest test_demo.py -v
```

真实输出：

```text
test_demo.py::test_add_basic PASSED      [ 50%]
test_demo.py::test_average PASSED        [100%]

========================= 2 passed in 0.05s ==========================
```

### 和 Jest 的断言对比

```python
# Jest:  expect(add(1, 2)).toBe(3)
# pytest: assert add(1, 2) == 3
```

pytest 用的是**语言原生的 `assert`**，而不是 `expect(...).toBe(...)` 那套方法链。这意味着：**任何返回布尔值的判断都能直接当断言**——`assert len(x) == 3`、`assert "a" in lst`、`assert x is not None`，全都可以。

### 失败的测试长什么样

把测试故意写错，看真实报错：

```python
def test_add_wrong():
    assert add(1, 2) == 4   # 故意写错
```

跑：

```bash
pytest test_demo.py
```

真实输出：

```text
    def test_add_wrong():
>       assert add(1, 2) == 4
E       assert 3 == 4
E        +  where 3 = add(1, 2)

test_demo.py:5: AssertionError
=========================== short test summary info ===========================
FAILED test_demo.py::test_add_wrong - assert 3 == 4
1 failed in 0.48s
```

注意 pytest 失败信息里的 `where 3 = add(1, 2)`——**它把断言拆解了**，告诉你"`add(1, 2)` 算出来是 3，但你期望 4"。这是 pytest 比 `print` 调试强的地方：它自动帮你定位到"哪一步错了"。

### 四个最常用的命令行参数

`pytest` 后面可以挂一堆开关，掌握这四个日常够用：

| 参数 | 作用 | 场景 |
|---|---|---|
| `-v` | 详细输出，每个测试一行 | 想看每个测试的名字 |
| `-k "关键字"` | 只跑名字含关键字的测试 | 只跑 `test_add` 相关的 |
| `-x` | 遇到第一个失败就停 | 快速失败，不浪费时间跑后面 |
| `-s` | 显示 `print` 输出 | 调试时想看 print |

```bash
pytest -v              # 详细模式
pytest -k "divide"     # 只跑名字里含 divide 的测试
pytest -x              # 一红就停
pytest -s              # 让 print 显示出来
```

> `-k` 特别有用：项目有几百个测试时，你只想跑自己刚改的那几个，`pytest -k "average"` 一条命令搞定，不用等全套跑完。

> 一句话记住它：**pytest 的断言就是语言原生的 `assert`，测试函数叫 `test_xxx`，跑 `pytest` 看绿/红；`-v`/`-k`/`-x`/`-s` 四个参数日常够用。**

## 8.3 测试异常：pytest.raises

先给结论：**要测"这个函数该抛异常"时，用 `with pytest.raises(异常类型)`。** 不能直接调用——因为一调用程序就真的抛异常、测试就崩了。

比如这段业务代码：

```python
def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("除数不能为 0")
    return a / b
```

测它"除以零必须抛异常"，正确写法：

```python
import pytest

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)
```

`with pytest.raises(ZeroDivisionError)` 的意思是："下面这段代码应该抛 `ZeroDivisionError`，如果抛了，测试通过；如果没抛，测试失败。"

### 还能精确匹配异常消息

只匹配类型还不够时，加 `match` 参数匹配消息内容：

```python
def test_divide_by_zero_message():
    with pytest.raises(ZeroDivisionError, match="除数不能为 0"):
        divide(1, 0)
```

`match="除数不能为 0"` 要求异常消息里**包含**这段文字（是正则匹配）。这样你不仅能测"抛了异常"，还能测"抛的是**对的**异常"。

### 如果没抛异常，会发生什么

把代码改成"不该抛异常却用 raises 包着"，看看真实失败：

```python
def test_no_exception_but_expected():
    with pytest.raises(ZeroDivisionError):
        divide(10, 2)   # 这里根本不会抛异常
```

真实输出（截取关键行）：

```text
E       Failed: DID NOT RAISE ZeroDivisionError
```

`DID NOT RAISE`——pytest 直白地告诉你"我等着它抛异常，结果它没抛"。这是测试失败的信号：要么你的测试写错了，要么代码行为变了。

> 一句话记住它：**测异常用 `with pytest.raises(类型, match="消息")`，别直接调用会抛异常的函数。**

## 8.4 fixture：准备和复用测试数据

先给结论：**fixture 是"测试的前置准备"，对应 Jest 的 `beforeEach`。** 当多个测试需要同一份数据时，别在每个测试里重复写，抽成一个 fixture。

### 没有 fixture 时，代码是重复的

```python
def test_sum():
    data = [1, 2, 3, 4, 5]
    assert sum(data) == 15


def test_len():
    data = [1, 2, 3, 4, 5]   # 又写一遍
    assert len(data) == 5
```

`data = [1, 2, 3, 4, 5]` 出现两次。数据一变，两个测试都得改。

### 用 fixture 抽出来

```python
import pytest

@pytest.fixture
def sample_numbers():
    return [1, 2, 3, 4, 5]

def test_sum(sample_numbers):
    assert sum(sample_numbers) == 15

def test_len(sample_numbers):
    assert len(sample_numbers) == 5
```

关键机制：**测试函数声明一个参数叫 `sample_numbers`，pytest 发现同名 fixture，就把 fixture 的返回值传进来。** 不用 import、不用手动调用，参数名对上就行。

### fixture 的 scope：控制"准备一次还是每次"

默认 fixture 每个测试函数都重新执行一次（对应 Jest 的 `beforeEach`）。要"整个文件只执行一次"（对应 `beforeAll`），用 `scope`：

```python
@pytest.fixture(scope="module")
def expensive_setup():
    print("连接数据库")        # 整个模块只打印一次
    return {"conn": "fake-connection"}
```

`scope` 可选值：

| scope | 作用范围 | 类比 Jest |
|---|---|---|
| `function`（默认） | 每个测试函数 | `beforeEach` |
| `module` | 每个测试文件 | `beforeAll` |
| `session` | 整个测试会话 | 全局 `beforeAll` |

### teardown：用 yield 做清理

fixture 不止能"准备"，还能"清理"。对应 Jest 的 `afterEach`。写法是用 `yield`：

```python
import pytest

@pytest.fixture
def db_connection():
    conn = {"conn": "open"}      # 准备：yield 之前的部分
    yield conn                   # 把 conn 交给测试
    conn["conn"] = "closed"      # 清理：测试跑完后执行
    print("连接已关闭")
```

`yield` 之前的代码是"准备"（setup），`yield` 之后的代码是"清理"（teardown）。**不管测试通过还是失败，`yield` 之后的清理代码都会执行**——这正是 teardown 的价值，保证资源一定被释放。

对比 Jest：

```js
// Jest 的 beforeEach + afterEach
beforeEach(() => { db.open(); });
afterEach(() => { db.close(); });
```

Python 里把"打开"和"关闭"写进同一个 fixture，用 `yield` 分隔，一个地方管完。

### fixture 依赖 fixture

fixture 可以"用"另一个 fixture，只要把另一个 fixture 的名字声明为参数：

```python
import pytest

@pytest.fixture
def user_id():
    return 42

@pytest.fixture
def user(user_id):          # user 依赖 user_id
    return {"id": user_id, "name": "alice"}

def test_user(user):
    assert user["id"] == 42
    assert user["name"] == "alice"
```

`user` fixture 声明了参数 `user_id`，pytest 就会先执行 `user_id`，把结果传进来，再执行 `user`。**这是 fixture 的组合能力**：复杂的环境可以一层层搭起来，每个 fixture 只负责一件事。

> 一句话记住它：**fixture 用 `yield` 分隔"准备"和"清理"（对应 beforeEach/afterEach），还能用参数声明依赖另一个 fixture；默认每次重跑，用 `scope` 改生命周期。**

## 8.5 参数化：一份逻辑跑多组数据

先给结论：**`@pytest.mark.parametrize` 让一个测试函数跑 N 组数据，对应 Jest 的 `it.each`。** 这是消灭"复制粘贴测试"最锋利的刀。

### 没参数化时，你会写三个几乎一样的测试

```python
def test_add_1_and_2():
    assert add(1, 2) == 3

def test_add_5_and_5():
    assert add(5, 5) == 10

def test_add_negative():
    assert add(-1, -1) == -2
```

三个测试，逻辑完全相同，只有数据不同。这是测试代码里的"重复代码"，和业务代码的重复一样臭。

### 参数化后：一个函数搞定

```python
import pytest

@pytest.mark.parametrize("a, b, expected", [
    (1, 2, 3),
    (5, 5, 10),
    (-1, -1, -2),
    (100, 1, 101),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

`"a, b, expected"` 是参数名，下面是 4 组数据。pytest 会**自动生成 4 个测试用例**，跑起来是：

```text
test_add[1-2-3] PASSED
test_add[5-5-10] PASSED
test_add[-1--1--2] PASSED
test_add[100-1-101] PASSED
```

注意测试名里 `[1-2-3]` 这种后缀——**每组数据一个独立的测试**，哪组挂了，从名字就能定位到是哪组数据。

### 给每组数据起个可读的名字

默认的后缀 `[1-2-3]` 是直接把参数拼起来，数据一复杂就看不懂。用 `ids` 参数自定义：

```python
import pytest

@pytest.mark.parametrize("a, b, expected", [
    (1, 2, 3),
    (5, 5, 10),
    (-1, -1, -2),
], ids=["正数相加", "相同数相加", "负数相加"])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

现在测试名变成：

```text
test_add[正数相加] PASSED
test_add[相同数相加] PASSED
test_add[负数相加] PASSED
```

失败时你看到的是"负数相加挂了"，而不是"`[-1--1--2]` 挂了"——可读性天差地别。

### 参数化 + fixture 可以混用

参数化和 fixture 不冲突，一个测试可以同时要"数据"（参数化）和"环境"（fixture）：

```python
import pytest

@pytest.fixture
def base():
    return 10

@pytest.mark.parametrize("x, expected", [
    (1, 11),
    (2, 12),
])
def test_add_base(base, x, expected):
    assert base + x == expected
```

> 一句话记住它：**`parametrize` 把"复制粘贴的 N 个测试"压成一个，每组数据独立成一个用例，对应 Jest 的 `it.each`。**

## 8.6 conftest.py：跨文件共享 fixture

先给结论：**fixture 默认只在当前文件有效；要跨文件共享，放进 `conftest.py`。** 这是 pytest 的"全局 setup"机制。

### 问题：多个测试文件都要用同一个 fixture

假设你有两个测试文件 `test_a.py` 和 `test_b.py`，都需要"连接数据库"这个 fixture。如果在每个文件里都写一遍 `@pytest.fixture`，又回到重复代码的老路。

### 解决：放 conftest.py

```text
tests/
├── conftest.py          # 共享 fixture，所有 test_*.py 自动可见
├── test_a.py
└── test_b.py
```

`conftest.py` 里：

```python
import pytest

@pytest.fixture
def db_connection():
    return {"conn": "fake-db"}
```

然后 `test_a.py` 和 `test_b.py` **都不需要 import 它**，直接声明参数就能用：

```python
# test_a.py
def test_query_a(db_connection):
    assert db_connection["conn"] == "fake-db"
```

关键机制：**pytest 在收集测试时，会自动加载测试目录下的 `conftest.py`，把里面的 fixture 注入作用域内的所有测试文件。** 你不需要任何 import 语句。

### conftest.py 的作用域规则

`conftest.py` 放在哪个目录，就对**该目录及子目录**的所有测试生效：

```text
tests/
├── conftest.py           # 对整个 tests/ 生效
├── unit/
│   └── test_a.py         # 能用最外层 conftest 的 fixture
└── integration/
    ├── conftest.py       # 只对 integration/ 生效
    └── test_b.py         # 能用两个 conftest 的 fixture
```

> 一句话记住它：**`conftest.py` 是 pytest 自动加载的共享 fixture 仓库，放在哪个目录就管到哪个目录的子级。**

## 8.7 用 unittest 做对照：标准库、零依赖

先给结论：**`unittest` 是 Python 标准库自带的测试框架，思想是"类 + 断言方法"，和 pytest 的"函数 + assert"不一样，但能干同一件事。** 它唯一的优势是**零依赖**——不装任何东西就能用。

你可能会问：都有 pytest 了，干嘛还学 unittest？两个理由：

1. **很多老项目、很多官方库用的是 unittest**，你得能读懂、能接。
2. **某些受限环境（离线、内网）装不了 pytest**，unittest 是最后的救命稻草。

### 基本写法：TestCase + assertEqual

```python
import unittest

def add(a, b):
    return a + b

class TestAdd(unittest.TestCase):
    def test_add(self):
        self.assertEqual(add(1, 2), 3)
        self.assertEqual(add(-1, 1), 0)

if __name__ == "__main__":
    unittest.main()
```

对比 pytest 的 `assert add(1, 2) == 3`，unittest 用 `self.assertEqual(add(1, 2), 3)`。**区别在于：unittest 的断言是"方法"（`assertEqual`、`assertTrue`、`assertRaises`），pytest 的断言是"语句"（`assert`）。**

跑起来：

```bash
python test_demo.py -v
```

真实输出：

```text
test_add (__main__.TestAdd.test_add) ... ok

----------------------------------------------------------------------
Ran 1 test in 0.000s

OK
```

### 测试异常：assertRaises

unittest 测异常，用 `assertRaises`：

```python
import unittest

def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("除数不能为 0")
    return a / b

class TestDivide(unittest.TestCase):
    def test_divide_by_zero(self):
        with self.assertRaises(ZeroDivisionError):
            divide(1, 0)
```

`with self.assertRaises(...)` 和 pytest 的 `pytest.raises` 是同一个思路，只是换了个名字。

### 失败的样子

unittest 失败时的输出和 pytest 不同，更"啰嗦"：

```python
class TestAdd(unittest.TestCase):
    def test_add_fail(self):
        self.assertEqual(add(1, 2), 4)   # 故意写错
```

跑：

```text
.F
======================================================================
FAIL: test_add_fail (__main__.TestAdd.test_add_fail)
----------------------------------------------------------------------
Traceback (most recent call last):
  ...
AssertionError: 3 != 4
```

最后那行 `AssertionError: 3 != 4` 是精髓——它只告诉你"3 不等于 4"，**不像 pytest 那样拆解出 `add(1, 2)` 算出来是 3**。这也是 pytest 体验更好的原因之一。

### 怎么选

| | pytest | unittest |
|---|---|---|
| 依赖 | 第三方，要装 | 标准库，零依赖 |
| 写法 | 函数 + `assert` | 类 + `assertEqual` |
| 失败信息 | 拆解详细 | 只有 `3 != 4` |
| 生态 | 插件丰富（pytest-mock 等） | 少 |
| 建议 | **新项目首选** | 老项目维护、受限环境 |

> 一句话记住它：**`unittest` 是标准库的保底方案（类 + assertEqual），`pytest` 是体验更好的首选（函数 + assert）；能装 pytest 就装 pytest。**

## 8.8 mock：隔离外部依赖

先给结论：**测试不应该真的去连数据库、调 API、发邮件——又慢又不可控。mock 用一个"假替身"换掉这些外部依赖。** 对应 Jest 的 `jest.mock`。

### 为什么必须 mock

看这段业务代码：

```python
class UserService:
    def __init__(self, client):
        self.client = client

    def get_user_name(self, user_id):
        user = self.client.fetch(user_id)
        return user["name"]
```

`get_user_name` 依赖 `self.client.fetch`。真实场景里，`fetch` 会去查数据库或调 API。如果测试真的这么干：

1. **慢**：每次测试都要等网络/数据库。
2. **脆弱**：数据库挂了，测试也挂了——可你的逻辑根本没坏。
3. **污染**：测试写入真实数据库，跑一次脏一次。

所以 mock 掉 `client`，让测试只关心"`get_user_name` 的逻辑对不对"。

### 用 MagicMock（标准库 unittest.mock）

```python
from unittest.mock import MagicMock

def test_get_user_name():
    client = MagicMock()
    client.fetch.return_value = {"name": "alice"}   # 让 fetch 返回假数据
    service = UserService(client)

    assert service.get_user_name(1) == "alice"
```

`MagicMock()` 创造一个"假对象"，你给它指定 `fetch` 的返回值，它就不真的去查数据库。**测试飞快、稳定、不污染**。

### 还能验证"被怎么调用了"

mock 不只"代替"，还能"记录"。你可以断言"它到底被怎么调用了"：

```python
from unittest.mock import MagicMock

def test_fetch_called_with_correct_id():
    client = MagicMock()
    client.fetch.return_value = {"name": "bob"}
    service = UserService(client)

    service.get_user_name(42)

    client.fetch.assert_called_once_with(42)   # 验证 fetch 被精确调用了一次，参数是 42
```

`assert_called_once_with(42)` 的含义是："`fetch` 必须被调用**恰好一次**，且参数是 `42`。" 如果代码里多调了一次、少调了一次、或参数错了，测试都会红。

### side_effect：让 mock 模拟"更真实"的行为

`return_value` 让 mock 每次都返回同一个值。要模拟"抛异常""依次返回不同值"，用 `side_effect`：

```python
from unittest.mock import MagicMock

def test_fetch_raises_when_network_down():
    client = MagicMock()
    client.fetch.side_effect = ConnectionError("网络不通")   # 让 fetch 抛异常
    service = UserService(client)

    try:
        service.get_user_name(1)
    except ConnectionError:
        print("成功捕获到 mock 抛出的异常")
```

`side_effect` 还能是"一个列表"，表示"第一次调用返回 A，第二次返回 B"：

```python
mock = MagicMock()
mock.fetch.side_effect = [{"name": "alice"}, {"name": "bob"}]

print(mock.fetch(1))   # {'name': 'alice'}  第一次
print(mock.fetch(2))   # {'name': 'bob'}    第二次
```

运行结果：

```text
{'name': 'alice'}
{'name': 'bob'}
```

`return_value` 是"死的固定值"，`side_effect` 是"活的脚本"——能抛异常、能按顺序变。模拟"第一次失败、第二次成功"这类真实场景，靠的就是它。

### patch：临时替换一个函数

`MagicMock` 适合"传入的依赖"。如果是"模块级的函数"（比如直接调用 `os.environ.get`），用 `patch` 临时替换：

```python
from unittest.mock import patch

def send_email(to, content):
    # 真实实现会连 SMTP 服务器
    return f"sending to {to}"

def notify(user):
    return send_email(user, "hello")

with patch("__main__.send_email", return_value="MOCKED") as m:
    result = notify("alice")
    print(result)          # MOCKED
    print(m.call_args)      # call('alice', 'hello')
```

输出：

```text
MOCKED
call('alice', 'hello')
```

`patch("__main__.send_email", ...)` 把 `send_email` 这个函数临时换成假的，`with` 块结束后自动还原。

### pytest-mock：mocker fixture

pytest 有个官方插件 `pytest-mock`，把 `patch` 包装成更好用的 `mocker` fixture：

```bash
pip install pytest-mock
```

```python
import os

def get_env_var(name):
    return os.environ.get(name)

def test_get_env_var(mocker):
    mocker.patch.dict(os.environ, {"MY_VAR": "hello"})
    assert get_env_var("MY_VAR") == "hello"
```

`mocker` 是一个 fixture，直接用就行（不用 import `unittest.mock`）。`mocker.patch.dict` 临时改环境变量，测试结束自动还原。

> 一句话记住它：**mock 让测试"只关心你的逻辑，不关心外部世界"；`MagicMock` 造替身，`patch`/`mocker` 换函数，还能验证"被怎么调用了"。**

## 8.9 测试命名约定：让测试自己说话

先给结论：**测试的名字不是写给机器看的，是写给人看的——它要能在不看代码的情况下，说清楚"测了什么、期望什么"。**

### 三条约定

1. **文件名以 `test_` 开头**：`test_user_service.py`。pytest 默认只收集 `test_*.py` 或 `*_test.py`。
2. **函数名以 `test_` 开头**：`test_get_user_name`。pytest 只收集 `test_` 开头的函数。
3. **类名以 `Test` 开头**（如果用类）：`TestUserService`。

### 命名要描述"行为"，不是描述"实现"

对比两套命名：

```python
# ❌ 差：描述了实现，没说测什么
def test_fetch():
    ...

def test_check():
    ...

# ✅ 好：描述了行为和期望
def test_get_user_name_returns_name_from_client():
    ...

def test_divide_by_zero_raises_zero_division_error():
    ...
```

好的测试名是一句完整的句子："`get_user_name` 返回 client 里的名字"、"除以零抛 `ZeroDivisionError`"。当测试失败时，你从名字就能知道**什么行为坏掉了**，不用翻代码。

### 一个经验法则

名字遵循这个模板：

```text
test_<被测对象>_<条件>_<期望结果>
```

例如：

- `test_add_negative_numbers_returns_negative_sum`
- `test_average_empty_list_raises_value_error`
- `test_get_user_name_unknown_id_returns_none`

> 一句话记住它：**测试命名用 `test_对象_条件_期望` 的句式，让"哪个行为坏了"一眼可见，而不是"哪个函数挂了"。**

## 8.10 覆盖率的坑：高覆盖率 ≠ 测得好

先给结论：**覆盖率只回答"代码被执行了没有"，不回答"执行的结果被检查了没有"。** 覆盖率 100% 的测试，可能一个 bug 都抓不到。

### 覆盖率是什么

覆盖率工具（如 `coverage.py` 或 `pytest-cov`）统计"你的测试跑到了多少行代码"：

```bash
pip install pytest-cov
pytest --cov=your_module
```

输出类似：

```text
Name            Stmts   Miss  Cover
------------------------------------
your_module.py     20      2    90%
```

`90%` 表示"20 行代码里，有 18 行被测试执行到了"。

### 但"执行到"不等于"验证对"

看这个经典反例——**100% 覆盖率的空测试**：

```python
def calc_total(price, quantity, discount=0.0):
    if quantity == 0:
        return 0
    return price * quantity * (1 - discount)

def test_calc_total_covers_every_line():
    calc_total(100, 5, 0.1)   # 执行了，但什么也没断言！
```

这个测试**执行到了所有代码行**，覆盖率是 100%。但它没有任何 `assert`——`calc_total` 就算返回一个错误的数字（比如 `price` 写成了 `discount`），测试照样绿。**它证明了"代码能跑"，没证明"代码跑得对"。**

所以：**覆盖率衡量的是"测试有没有踩到这块代码"，衡量不了"踩到之后有没有检查结果"。** 后者才是测试的意义。

### 怎么正确看待覆盖率

1. **覆盖率是"下限"，不是"目标"**。它告诉你"哪里完全没测到"（一片红色的未覆盖代码），但覆盖到的部分可能测得很烂。
2. **别为了凑数字写无意义测试**。为了 100% 去写 `test_xxx_covers_every_line` 这种空测试，是自欺欺人。
3. **真正要盯的是"断言质量"**：每个测试有没有验证一个明确的行为？

一个健康的指标用法是：**看覆盖率的"低洼区"，而不是"总分"**。90% 但关键分支没测到，比 70% 但关键分支全测到更危险。

> 一句话记住它：**覆盖率告诉你"哪没测"，不告诉你"测得好不好"；没断言的 100% 覆盖，等于 0% 的保护。**

## 8.11 集成测试 vs 单元测试：测的层次不一样

先给结论：**单元测试测"一个函数/类"，隔离所有依赖；集成测试测"几个组件配合起来"，允许真实依赖。** 两者不是二选一，是金字塔的两层。

### 单元测试：快、隔离、聚焦

单元测试测最小单元（一个函数、一个方法），**mock 掉一切外部依赖**：

```python
def test_average():
    assert average([2, 4, 6]) == 4   # 只测 average，不碰数据库、不碰网络
```

特点：**快**（毫秒级）、**稳定**（不依赖环境）、**定位准**（红了就知道是这个函数的问题）。

### 集成测试：真、慢、测配合

集成测试测"多个组件合在一起对不对"——比如"真的连数据库，写入再读出来"：

```python
def test_save_and_load_user():
    db = RealDatabase("postgres://...")   # 真的连
    db.save({"id": 1, "name": "alice"})
    assert db.load(1)["name"] == "alice"
```

特点：**真实**（能暴露单元测试发现不了的连接问题）、**慢**（要等 I/O）、**脆弱**（数据库环境变了就红）。

### 测试金字塔

业界共识是"金字塔"结构：

```text
         /\
        /  \          集成测试：少而慢，测关键路径
       /----\
      /      \
     /--------\       单元测试：多而快，测每个函数
    /__________\
```

- **底部大量单元测试**：快、便宜，覆盖绝大多数逻辑。
- **顶部少量集成测试**：慢、贵，只测"组件之间的配合"这条最关键的链。

反模式是"倒金字塔"——全是集成测试，跑一次十分钟，红了一个排查半天。**单元测试是主力，集成测试是哨兵。**

> 一句话记住它：**单元测试测"零件"，快而多；集成测试测"装配"，慢而少；别让慢的集成测试当主力。**

## 8.12 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 测试函数没以 `test_` 开头 | pytest 显示 `collected 0 items` | pytest 只收集 `test_` 开头的函数 | 命名 `test_xxx` |
| 文件名没以 `test_` 开头 | pytest 找不到你的测试 | 默认只认 `test_*.py` / `*_test.py` | 文件名 `test_xxx.py` |
| 直接调用抛异常的函数 | 测试崩了而不是通过 | 没包 `pytest.raises`，异常真抛了 | `with pytest.raises(...)` |
| fixture 名字拼错 | `fixture 'xxx' not found` | 参数名和 fixture 名没对上 | 检查拼写，参数名要一致 |
| 可变默认值当 fixture 返回 | 多个测试共享同一份数据 | fixture 返回同一个 `list` | 每次返回新对象，或用工厂 |
| 测试真的连数据库 | 测试慢、脆弱、污染数据 | 没 mock 外部依赖 | 用 `MagicMock`/`mocker` 隔离 |
| 为了覆盖率写空测试 | 100% 覆盖却抓不到 bug | 只执行没断言 | 每个测试都要验证明确行为 |
| 用 `==` 比较浮点数 | 测试时好时坏 | 浮点有精度误差 | `pytest.approx` 或 `assertAlmostEqual` |
| 测试顺序依赖 | 单独跑挂、一起跑过 | 测试间共享了状态 | 每个测试独立，用 fixture 隔离 |
| 只跑一次就不管了 | 上线后才炸 | 没挂进 CI | CI 里自动 `pytest` |

## 8.13 本章小结

- **pytest 的思想和 Jest 完全一样**，只是语法不同：断言用 `assert`，测试函数叫 `test_xxx`。
- **核心就一个 `assert`**，任何布尔判断都能当断言；失败时 pytest 会拆解出"哪一步算错了"。
- **测异常用 `with pytest.raises(类型, match="消息")`**，别直接调用会抛异常的函数。
- **fixture 对应 Jest 的 beforeEach/beforeAll**：以参数名注入，`scope` 控制生命周期。
- **`parametrize` 对应 `it.each`**：一份逻辑跑多组数据，每组独立成用例。
- **`conftest.py` 是跨文件共享 fixture 的仓库**，放在哪个目录就管到哪个子目录。
- **`unittest` 是标准库保底方案**（类 + `assertEqual`），零依赖但体验不如 pytest。
- **mock 让测试只关心逻辑**：`MagicMock` 造替身、`patch`/`mocker` 换函数，还能验证调用参数。
- **覆盖率是下限不是目标**：没断言的 100% 覆盖等于 0 保护。
- **单元测试是主力（多而快），集成测试是哨兵（少而慢）**，别倒过来。

## 8.14 动手练习

1. 给下面的函数写一个 pytest 测试，覆盖"正常情况"和"除以零抛异常"两种情况：

   ```python
   def safe_divide(a, b):
       if b == 0:
           raise ValueError("除数不能是 0")
       return a / b
   ```

   <details><summary>参考答案</summary>

   ```python
   import pytest

   def test_safe_divide_normal():
       assert safe_divide(10, 2) == 5

   def test_safe_divide_by_zero():
       with pytest.raises(ValueError, match="除数不能是 0"):
           safe_divide(10, 0)
   ```
   </details>

2. 用 `@pytest.mark.parametrize` 把下面三个重复的测试压成一个：

   ```python
   def is_even(n):
       return n % 2 == 0

   def test_is_even_2():
       assert is_even(2) is True

   def test_is_even_3():
       assert is_even(3) is False

   def test_is_even_100():
       assert is_even(100) is True
   ```

   <details><summary>参考答案</summary>

   ```python
   import pytest

   @pytest.mark.parametrize("n, expected", [
       (2, True),
       (3, False),
       (100, True),
   ])
   def test_is_even(n, expected):
       assert is_even(n) is expected
   ```
   </details>

3. 下面的测试"覆盖率 100% 但毫无意义"，请指出问题并改进：

   ```python
   def apply_discount(price, rate):
       if rate >= 1:
           return price          # rate 无效时返回原价
       return price * (1 - rate)

   def test_apply_discount():
       apply_discount(100, 0.2)   # 执行了，但没断言
   ```

   <details><summary>参考答案</summary>

   问题：测试执行了代码但**没有任何 `assert`**，`apply_discount` 返回错值也测不出来。
   改进：对关键行为加断言：

   ```python
   def test_apply_discount_normal():
       assert apply_discount(100, 0.2) == 80

   def test_apply_discount_invalid_rate():
       assert apply_discount(100, 1.5) == 100   # rate 无效时原样返回
   ```
   </details>

4. 写一个 fixture，让两个测试共用同一个测试用户字典，并验证它们互不影响（每个测试拿到的是独立副本）。

   <details><summary>参考答案</summary>

   ```python
   import pytest

   @pytest.fixture
   def user():
       return {"name": "alice", "age": 30}

   def test_user_name(user):
       assert user["name"] == "alice"

   def test_user_age(user):
       user["age"] = 99          # 改自己的，不影响别的测试
       assert user["age"] == 99

   def test_user_age_original(user):
       assert user["age"] == 30  # 拿到的是新副本，还是 30
   ```

   因为 fixture 默认 `scope="function"`，每个测试都重新执行 `user()`，拿到全新字典。
   </details>
