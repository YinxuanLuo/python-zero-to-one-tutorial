# 第 06 章 · 并发与异步

> 这一章是全书最难、也最能区分"会用 Python"和"真懂 Python"的一章。
> 它回答一个 JS 开发者必问的问题：**为什么 Python 有线程，却跑不动多线程的 CPU 计算？**
>
> 本章你需要记住的就一件事：**CPU 密集用多进程，I/O 密集用线程或 `asyncio`，多线程永远无法并行跑 CPU 计算（因为 GIL）。**

---

## 6.1 先分清两个词：CPU 密集 vs I/O 密集

在聊并发之前，必须先分清你要优化的是哪种"慢"。同样是"程序跑得慢"，原因天差地别：

| 类型 | 慢在哪 | 典型例子 | 瓶颈 |
|---|---|---|---|
| **CPU 密集**（CPU-bound） | CPU 一直在算，忙不过来 | 图像处理、加密、矩阵运算、训练模型 | CPU 核数 |
| **I/O 密集**（I/O-bound） | 大部分时间在等 I/O，CPU 基本闲着 | 读数据库、调 HTTP 接口、读写文件、等用户输入 | 网络/磁盘延迟 |

这是整个并发世界的分水岭。**同一种"提速手段"，对一种慢有效，对另一种可能完全无效。**

用一个生活类比：**CPU 密集 = 一个人做 100 道数学题**（人手不够就得雇人，一个脑子不够用）；
**I/O 密集 = 一个人等 100 个外卖**（人大部分时间在等，一个人就能同时等很多单）。

JS 读者对这个其实有天然优势：Node.js 单线程之所以能扛住高并发 HTTP，就是因为 **HTTP 服务是典型的 I/O 密集**——
CPU 大部分时间在等数据库、等网络返回，单线程靠事件循环就能"同时"处理几万个连接。

但注意：Node 处理 CPU 密集（比如大 JSON 解析、图片压缩）也会卡死整个事件循环——这正是 Python 和 JS 共同的软肋。

### 6.1.1 怎么判断你的程序卡在哪

光知道两个词没用，得会**判断自己的程序属于哪种**。三个实用方法：

**方法一：看代码特征（最快）。**

- 代码里大量 `for`/`while` 循环做数学计算、字符串处理、递归 → **CPU 密集**。
- 代码里大量 `sleep`、`requests.get`、数据库查询、文件读写、等锁 → **I/O 密集**。

**方法二：看 CPU 占用率（最直观）。** 跑起来后打开任务管理器（Windows）或 `top`（Linux/Mac）：

- CPU 占用率飙到 100%（单核占满）→ CPU 密集。
- CPU 占用率很低（< 10%），程序却在"卡" → I/O 密集，它在等网络/磁盘。

**方法三：写个计时小实验（最可靠）。** 把任务跑一遍，记下时间；再改成 4 个并发跑，看时间：

- 4 个并发 ≈ 1 个串行 → 说明是 CPU 密集（被 GIL 卡住，见 6.5）。
- 4 个并发 ≈ 1/4 时间 → 说明是 I/O 密集（等待被重叠）。

**为什么判断这个这么重要？** 因为选错方案 = 白忙活：

- 拿多线程去优化 CPU 密集任务 → 速度没变，还多了线程切换开销（6.5 节会证明）。
- 拿多进程去优化 I/O 密集任务 → 能提速，但浪费了大量内存和进程启动时间，杀鸡用牛刀。

> 一句话记住它：**先判断是 CPU 密集还是 I/O 密集——它们的提速手段完全不同，用错了白费力气；看代码特征、看 CPU 占用率、跑个计时实验，三者结合判断最准。**

## 6.2 并发 vs 并行：一个被滥用的词

"并发"和"并行"在中文里常被混着说，但它们不是一回事：

- **并发（Concurrency）**：多个任务**交替**执行，看起来"同时在跑"，实际任意时刻只有一个在跑。单核 CPU 就能实现。
- **并行（Parallelism）**：多个任务**真正同时**执行，需要多核 CPU 或多个进程。

画成时间线，一眼看出差别：

```text
并发（单核，交替执行，宏观上像同时）：
任务A: ████░░░░░░░░████
任务B: ░░░░████████░░░░
       时间 →

并行（多核，真同时）：
任务A: ████████████████
任务B: ████████████████
       时间 →
```

**JS 的 `Promise`/事件循环是"并发"，不是"并行"**——它用单线程交替执行，制造出"同时"的错觉。
Python 的 `asyncio` 同理，也是单线程并发。而 `multiprocessing` 才是真正的并行。

为什么要较这个真？因为**只有并行才需要多核，只有多核才能让 CPU 密集任务变快**。
并发只能让"等待"重叠（I/O 密集有用），不能让"计算"翻倍（CPU 密集没用）。

### 6.2.1 JS 并发 vs Python 并发：一张迁移地图

你有 JS 基础，脑子里已经有一套并发模型了。把它和 Python 对应起来，能省一半学习成本：

| 概念 | JavaScript | Python |
|---|---|---|
| 异步任务 | `Promise` | 协程（coroutine）/ `asyncio.Future` |
| 声明异步函数 | `async function` | `async def` |
| 等待结果 | `await promise` | `await coroutine` |
| 并发等全部 | `Promise.all([...])` | `asyncio.gather(...)` |
| 先启动后等 | `const p = f(); ... await p` | `t = create_task(f()); ... await t` |
| 异步睡眠 | `setTimeout` 或 `sleep` | `await asyncio.sleep(ms)` |
| 事件循环 | 浏览器/Node 的事件循环 | `asyncio` 事件循环 |
| 多线程（真并行 CPU） | `Worker` 线程 | `multiprocessing` 进程 |
| 将来有结果的对象 | `Promise` | `concurrent.futures.Future` |

**关键洞察：JS 的"单线程 + 事件循环 + Promise"这套东西，Python 全部有对应物（就是 `asyncio`）。**
所以你在 JS 里已经会的东西，搬到 Python 只是换套关键字。

**但 Python 比 JS 多了一块：真正的多进程并行。** JS 的 `Worker` 用起来麻烦（要打包、要传消息），
而 Python 的 `multiprocessing` 是标准库一等公民，CPU 密集任务能直接上多进程真并行——这是 JS 主线程永远做不到的。

反过来，**Python 缺 JS 的"天然异步生态"**：JS 里 `fetch`、文件读取天生就是异步的；Python 标准库里
`urllib`、文件读取默认是**同步阻塞**的，想异步得专门找异步版库（`aiohttp` 等）。这是从 JS 转 Python 最需要适应的一点。

> 一句话记住它：**并发是"交替做"，并行是"同时做"；事件循环和协程是并发，多进程才是并行；JS 的 Promise/事件循环 = Python 的 asyncio，但 Python 多了多进程真并行、少了 JS 那样遍地开花的异步生态。**

## 6.3 GIL：为什么 Python 多线程跑不动 CPU 计算（重点）

这是全 Python 被问得最多、误解也最多的一个东西。别急着记结论，先把"它是什么"搞清楚。

### 6.3.1 GIL 是什么

**GIL = Global Interpreter Lock（全局解释器锁）。** 它是 CPython（最主流、你正在用的那个 Python 实现）解释器内部的一把**互斥锁**。

它的规则一句话说清：

> **同一时刻，只有一个线程能持有 GIL、执行 Python 字节码。**

哪怕你开了 8 个线程，在任意一个瞬间，也只有 1 个线程在真正运行 Python 代码。其他 7 个线程在排队等这把锁。

### 6.3.2 为什么要有它：为了一次简单到极致的优化

原因藏在 Python 的内存管理里。CPython 用**引用计数**做垃圾回收（第 04 章会讲对象模型）：

```python
a = [1, 2, 3]   # 这个 list 的引用计数变成 1
b = a           # 变成 2
del a           # 变回 1
```

问题来了：**如果两个线程同时改一个对象的引用计数，会发生什么？** 竞态——两个线程同时 `+1`，可能丢掉一次。

解决办法有两种：

1. **给每个对象加锁**：太慢，锁本身的开销巨大。
2. **用一把全局大锁（就是 GIL）**：同一时刻只有一个线程在跑 Python 代码，引用计数就永远不会被并发修改，**根本不需要给每个对象加锁**。

CPython 选了方案 2。代价你已经猜到了：**多线程无法并行执行 Python 字节码**。收益是：**解释器实现简单、单线程性能极好、C 扩展写起来安全。**

**还有一个附带好处**：很多 C 扩展（比如 `numpy`、`pandas`）在写 C 代码时，默认 GIL 保证了"不会有别的 Python 线程突然插进来"，让 C 扩展写起来简单得多。这也是为什么 Python 生态能这么繁荣的原因之一——GIL 降低了写扩展的难度。

### 6.3.3 GIL 限制了什么，又不限制什么

这决定了你什么时候能用多线程、什么时候必须换招：

**GIL 限制的**：多线程**并行执行纯 Python 的 CPU 密集代码**。开 4 个线程算矩阵，和 1 个线程串行算，速度几乎一样，有时还更慢（线程切换有开销）。

**GIL 不限制的**（重点，逐条记）：

1. **I/O 密集**：线程在等网络、等磁盘、`time.sleep` 时，会**主动释放 GIL**。所以 4 个线程并发请求 4 个接口，总耗时约等于 1 次请求的时间。
2. **多进程**：每个进程有**自己独立的 Python 解释器和独立的 GIL**。开 4 个进程，就是 4 把独立的锁，互不干扰，CPU 密集任务能真并行。
3. **C 扩展**：`numpy` 等库在底层做大量计算时，会**释放 GIL**再算，算完再拿回来。所以 `numpy` 的多线程计算真能跑满多核。
4. **`asyncio` 协程**：单线程的协程调度，压根不涉及多线程，GIL 管不着它。

### 6.3.4 一个常被问的题：GIL 会取消吗？

会，但没那么快。官方在 PEP 703 里提出了"自由线程（free-threaded）"方案，Python 3.13 已经把它作为**实验性、可选**特性放出（编译时用 `--disable-gil` 开关，不是默认开启）。但生态里的 C 扩展几乎都还假设 GIL 存在，所以短期内（至少几年内）**默认 CPython 依然是带 GIL 的**。面试被问到这个，答"3.13 已支持实验性的 no-GIL 构建，但默认仍带 GIL"就是满分。

### 6.3.5 一个必须澄清的误解：GIL ≠ 线程安全

很多人学完 GIL 会得出一个错误结论：**"有 GIL 在，Python 多线程就安全了，不用加锁。"** 大错特错。

GIL 保证的是**"单个字节码原子执行"**——同一时刻只有一个线程在跑字节码。但你的业务操作通常是由**多个字节码**组成的：

```python
counter += 1
```

这一行看着是一步，实际是三步字节码：**读 counter → 加 1 → 写回 counter**。GIL 只保证"读"这一步执行时别的线程插不进来，**不保证"读-加-写"三步之间不被打断**。

用图看（线程 A 和 B 都执行 `counter += 1`，`counter` 初始为 0）：

```text
线程A: 读 counter(0) ──加1── 写回 counter(1)
线程B:              读 counter(0) ──加1── 写回 counter(1)
                                        ↑
                   两个线程都读到了 0，都写回 1，本应是 2，结果还是 1
```

**这就是竞态条件（race condition）：两个线程交错执行，丢失了一次更新。** GIL 完全管不了这件事。
只有当"读-改-写"三步恰好被 GIL 保护成不可分割的一整块时，它才碰巧安全——但这是**偶然**，不是保证。

**真正的线程安全要靠 `Lock`（锁）**，下一节会演示。记住这条铁律：

> **GIL 简化了 CPython 的实现，但它不替你的业务代码做线程同步。共享可变状态，永远要加锁。**

### 6.3.6 GIL 的切换与释放时机

既然 GIL 是"同一时刻只有一个线程跑"，那它总得有"换人"的机制。CPython 的规则：

**主动释放（线程自己交还 GIL）**：
- 执行会阻塞的系统调用时（`time.sleep`、`read` 文件、`socket.recv`、`requests.get` 内部）——线程阻塞前释放 GIL，等 I/O 回来再抢。
- 调用某些 C 扩展时（`numpy` 做矩阵运算会释放 GIL 再算）。

**被动切换（解释器强制换人）**：
- 每执行一小段时间（默认 **5 毫秒**，可用 `sys.getswitchinterval()` 查）或每执行一定数量的字节码后，解释器会释放 GIL，让其他线程有机会抢。

```python
import sys
print("GIL 切换间隔（秒）:", sys.getswitchinterval())
```

```text
GIL 切换间隔（秒）: 0.005
```

这 5 毫秒解释了很多现象：

1. **为什么 I/O 密集的多线程有效**：线程在等 I/O 时主动释放 GIL，别的线程能立刻接上，所以多个等待能重叠。
2. **为什么 CPU 密集的多线程无效**：线程一直在算、一直占着 GIL，5ms 到了被迫切换——但切换只是"换个线程继续算"，CPU 还是一个核在干活，没并行。
3. **为什么简单的 `counter += 1` 常常"碰巧"不丢数据**（6.4.4 那个坑）：因为 5ms 内能跑海量个 `+=`，切换点很少恰好落在"读"和"写"之间。但"碰巧安全"不是"真安全"，一旦夹杂 I/O 或耗时操作，竞态立刻暴露。

> 一句话记住它：**GIL 让多线程只能并发不能并行 CPU 计算，但 I/O 密集、多进程、C 扩展、协程都不受它限制；GIL 也绝不等于线程安全，共享变量照样要加锁；线程在等 I/O 时主动释放 GIL，所以 I/O 并发才有效。**

## 6.4 线程 `threading`：I/O 密集的正确打开方式

`threading` 是标准库的线程模块。基本用法和 JS 的 `Worker` 心智类似：**把函数交给线程去跑，主线程继续做别的**。

### 6.4.1 创建和启动线程

```python
import threading
import time

def greet(name):
    time.sleep(0.5)          # 模拟 I/O 等待
    print(f"hello {name}")

t1 = threading.Thread(target=greet, args=("alice",))
t2 = threading.Thread(target=greet, args=("bob",))

t1.start()   # 启动线程（立即返回，不阻塞）
t2.start()

t1.join()    # 等 t1 跑完
t2.join()    # 等 t2 跑完
print("两个线程都结束了")
```

```text
hello alice
hello bob
两个线程都结束了
```

三个关键点：

1. **`Thread(target=函数, args=(参数,))`** 创建线程。注意 `args` 是**元组**，单个参数也要写成 `("alice",)`（末尾逗号不能省）。
2. **`start()` 才真正启动**，且立即返回，主线程不等它。
3. **`join()` 阻塞等待线程结束**。不 `join` 的话，主线程可能先跑完退出，子线程被强制中断。

### 6.4.2 为什么线程适合 I/O 密集

关键在于 6.3 说的：**线程在等 I/O 时会释放 GIL**。所以 4 个线程并发 `sleep(1)`，总耗时约 1 秒，而不是 4 秒：

```python
import threading
import time

def io_task(name):
    time.sleep(1)            # 模拟等网络/磁盘
    print(f"  {name} 完成")

start = time.perf_counter()
threads = [threading.Thread(target=io_task, args=(f"任务{i}",)) for i in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"4 个线程并发 sleep(1): {time.perf_counter() - start:.3f}s（串行要 4s）")
```

```text
  任务0 完成
  任务2 完成
  任务3 完成
  任务1 完成
4 个线程并发 sleep(1): 1.001s（串行要 4s）
```

看到没：**4 个任务 1 秒搞定**。这就是线程在 I/O 密集场景的威力——等 I/O 的时间被"重叠"了。
真实场景里，把 `time.sleep` 换成 `requests.get(...)`、数据库查询，效果一模一样。

### 6.4.3 `daemon` 线程：主线程死了它跟着死

默认线程是**非守护**的：主线程即使执行完，也会等所有非守护线程结束才退出。想让"主线程结束，后台线程自动结束"，用 `daemon=True`：

```python
t = threading.Thread(target=background_job, daemon=True)
```

守护线程适合"日志上报""心跳""缓存清理"这类**可有可无的后台任务**——主程序退出，它们不该卡住进程。

### 6.4.4 线程安全与竞态条件（重要）

上一节 6.3.5 说了：**GIL 不保证线程安全**。现在用真实代码验证——多个线程同时给一个共享变量 `counter += 1`，会丢失更新：

```python
import threading
import time

counter = 0

def read_inc_write():
    global counter
    for _ in range(1000):
        v = counter        # 读
        time.sleep(0)      # 强制让出 GIL，制造竞态窗口
        counter = v + 1    # 写

threads = [threading.Thread(target=read_inc_write) for _ in range(8)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"8 线程各 +1000，期望 8000，实际 {counter}")
```

```text
8 线程各 +1000，期望 8000，实际 1512
```

期望 8000，实际只有 1512——**丢了 6000 多次更新**。这就是竞态：多个线程同时"读 counter(旧值) → 各自 +1 → 写回同一个值"，把彼此的更新覆盖掉了。

（注：我用 `time.sleep(0)` 是为了**可靠复现**竞态。如果只是裸的 `counter += 1`，因为 GIL 每 5ms 才切换一次、而这步操作太短，可能碰巧跑不出错——但"碰巧没事"不代表"安全"，一旦操作里夹杂 I/O 或函数调用，竞态立刻爆发。）

**修复：用 `Lock` 锁住临界区。** 锁保证同一时刻只有一个线程进入被保护的代码段：

```python
import threading
import time

counter = 0
lock = threading.Lock()

def read_inc_write_locked():
    global counter
    for _ in range(1000):
        with lock:              # 获取锁 → 执行 → 释放锁
            v = counter
            counter = v + 1

threads = [threading.Thread(target=read_inc_write_locked) for _ in range(8)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(f"加锁后：期望 8000，实际 {counter}")
```

```text
加锁后：期望 8000，实际 8000
```

`Lock` 的用法：

- **`lock.acquire()` / `lock.release()`**：手动加锁/解锁（记得 `release` 要放 `finally`，否则异常了锁不释放）。
- **`with lock:`**：自动 acquire/release（推荐，和文件 `with` 一个套路）。

**什么情况下要加锁？** 一句话：**多个线程读写同一个可变对象时。** 常见场景：多个线程往同一个列表 `append`、往同一个字典写、改同一个计数器、操作同一个数据库连接。凡是"共享的可变状态"，都要加锁保护。

（`append` 这种单字节码操作在 CPython 里其实是原子的，但别依赖这种细节——"看起来原子"的代码最坑人，统一加锁最稳妥。）

### 6.4.5 线程间的协调：`Event`

除了 `Lock`（互斥），线程间还有一种常见需求：**"等某个条件发生了，我再继续"**。比如一个线程负责准备数据，其他线程等它准备好了再开始。这用 `Event`（事件）实现：

```python
import threading
import time

event = threading.Event()

def waiter(name):
    print(f"{name} 等待事件...")
    event.wait()          # 阻塞在这里，直到别的线程调用 set()
    print(f"{name} 事件被触发了！")

threads = [threading.Thread(target=waiter, args=(f"线程{i}",)) for i in range(2)]
for t in threads:
    t.start()

time.sleep(1)
print("主线程触发事件")
event.set()               # 唤醒所有在 wait() 的线程

for t in threads:
    t.join()
```

```text
线程0 等待事件...
线程1 等待事件...
主线程触发事件
线程0 事件被触发了！
线程1 事件被触发了！
```

`Event` 三个方法：

- **`event.wait()`**：阻塞，直到事件被触发。
- **`event.set()`**：触发事件，唤醒所有等待的线程。
- **`event.clear()`**：重置事件（下次 `wait` 又要等）。
- 还有 `event.is_set()`：查询当前是否已触发。

`Event` 和 JS 里的"手动 reset 的 Promise"或"信号量"心智类似，适合"一发广播、多方响应"的场景。

顺带记几个 `threading` 的实用工具：

```python
import threading
threading.current_thread().name   # 当前线程的名字
threading.active_count()          # 当前活跃线程数
threading.enumerate()             # 列出所有活跃线程
```

调试多线程程序时，`threading.enumerate()` 能帮你看到"现在到底有几个线程在跑"。

> 一句话记住它：**线程适合 I/O 密集——等 I/O 时释放 GIL，多个等待能重叠；`start` 启动、`join` 等待，后台任务用 `daemon=True`；共享可变状态必须加 `Lock`，线程间"等条件发生"用 `Event`。**

## 6.5 线程跑 CPU 密集：真实验证 GIL（用计时说话）

上一节说线程适合 I/O 密集。那 CPU 密集呢？**别信我嘴说，看计时。** 下面是完整对照实验：

```python
import time
import threading
import multiprocessing

def cpu_task(n):
    """CPU 密集：纯计算，无任何 I/O"""
    total = 0
    for i in range(n):
        total += i * i
    return total

N = 30_000_000   # 单次约 1 秒

# ① 单线程串行跑 4 次
start = time.perf_counter()
for _ in range(4):
    cpu_task(N)
serial = time.perf_counter() - start
print(f"单线程串行跑 4 次 CPU 任务: {serial:.3f}s")

# ② 4 线程跑 4 次
def run_threads():
    ts = [threading.Thread(target=cpu_task, args=(N,)) for _ in range(4)]
    for t in ts: t.start()
    for t in ts: t.join()

start = time.perf_counter()
run_threads()
print(f"4 线程跑 4 次 CPU 任务:    {time.perf_counter() - start:.3f}s")

# ③ 4 进程跑 4 次
start = time.perf_counter()
with multiprocessing.Pool(processes=4) as pool:
    pool.map(cpu_task, [N] * 4)
print(f"4 进程跑 4 次 CPU 任务:    {time.perf_counter() - start:.3f}s")
```

这是我在本机（16 逻辑核）多轮测试取典型值后的结果：

```text
单线程串行跑 4 次 CPU 任务: 4.4s
4 线程跑 4 次 CPU 任务:    4.4s   ← 和串行一样，GIL 锁死
4 进程跑 4 次 CPU 任务:    2.4s   ← 真并行，明显变快
```

> 注：具体数字随机器负载波动（进程部分在本机约为 1.8 倍加速，而不是理论上的 4 倍——因为进程创建有固定开销，且这台机器的真实可用核心数少于 16）。**但规律永远不变：4 线程 ≈ 串行，4 进程 < 串行。**

三个数字说明了一切：

1. **4 线程 = 串行**：GIL 让线程没法并行算，甚至因为线程切换还有额外开销。
2. **4 进程 < 串行**：进程绕开了 GIL，真并行，速度接近翻倍。
3. **如果想 4 倍加速，得看机器有没有 4 个真核**——这也解释了为什么"多进程"不是万能药，核心数摆在那。

**结论一句话：CPU 密集任务，多线程在 CPython 里是白忙活，必须上多进程（或改用能释放 GIL 的 C 库，如 numpy）。**

> 一句话记住它：**CPU 密集别用多线程——GIL 让它约等于串行；要么多进程，要么用 numpy 这类会释放 GIL 的库。**

## 6.6 `multiprocessing`：绕开 GIL 做真正的并行

`multiprocessing` 是标准库的多进程模块。它**不给解释器加锁，而是干脆开多个解释器进程**——每个进程自带独立 GIL，互不干扰。

### 6.6.1 `Pool`：进程池，批量并行

```python
import multiprocessing

def cpu_task(n):
    total = 0
    for i in range(n):
        total += i * i
    return total

if __name__ == "__main__":          # Windows 必须加这行守卫，见 6.6.3
    with multiprocessing.Pool(processes=4) as pool:
        results = pool.map(cpu_task, [10_000_000] * 4)
    print("4 个进程的结果：", results)
```

```text
4 个进程的结果： [999999900000000, 999999900000000, 999999900000000, 999999900000000]
```

`Pool.map(func, iterable)` 的语义和内置 `map` 一模一样：把 `iterable` 里的每个元素交给 `func`，由进程池并行处理，返回结果列表。**注意：结果顺序和输入顺序一致**。

### 6.6.2 进程间通信：`Queue`

进程不像线程共享内存（每个进程是独立的内存空间），所以进程间**不能直接共享变量**，要用 `Queue` 或 `Pipe` 传数据：

```python
import multiprocessing

def square_worker(queue, x):
    queue.put(x * x)      # 把结果放进队列

if __name__ == "__main__":
    q = multiprocessing.Queue()
    p = multiprocessing.Process(target=square_worker, args=(q, 9))
    p.start()
    p.join()
    print("子进程通过 Queue 传回:", q.get())
```

```text
子进程通过 Queue 传回: 81
```

`Queue` 是跨进程安全的队列，`put` 塞数据、`get` 取数据。真实场景里常用于"多个 worker 进程消费一个任务队列"（生产者-消费者模型）。

### 6.6.3 Windows 上的两个大坑（必看）

**坑一：必须用 `if __name__ == "__main__":` 守卫。**

Windows 下 `multiprocessing` 默认用 **spawn** 方式启动子进程：它会**重新导入你的脚本**来创建子进程。
如果你的顶层代码（没在守卫里的部分）里有 `Pool(...)`、`Process(...)` 这种创建进程的语句，子进程会再次执行它们，**再创建新的子进程 → 无限套娃，程序卡死甚至崩溃**。

所以**任何创建进程/进程池的代码，必须写在 `if __name__ == "__main__":` 里面**。这几乎成了 Python 多进程的第一铁律。

**坑二：进程入口函数必须是"模块顶层函数"，不能是局部函数或 lambda。**

spawn 方式下，子进程通过 **pickle 序列化**把函数传过去。局部函数、`lambda` 无法被 pickle，会直接报错：

```python
def main():
    def worker():          # ❌ 局部函数，不能传给 Process
        return 1
    p = multiprocessing.Process(target=worker)
    p.start()
```

真实报错：

```text
AttributeError: Can't get local object 'main.<locals>.worker'
```

解决办法：把 `worker` 提到模块顶层（缩进顶格写）。

### 6.6.4 `Pool` 的三个方法：`map` / `starmap` / `imap`

`Pool` 提供了几个形似内置函数的并行版本：

```python
import multiprocessing

def add(a, b):
    return a + b

if __name__ == "__main__":
    # starmap：每个任务传多个参数（元组自动解包）
    with multiprocessing.Pool(2) as pool:
        print("starmap:", pool.starmap(add, [(1, 2), (3, 4), (5, 6)]))
```

```text
starmap: [3, 7, 11]
```

| 方法 | 作用 | 返回 |
|---|---|---|
| `map(func, iterable)` | 一个参数，全量并行 | 列表（结果按输入顺序） |
| `starmap(func, iterable_of_tuples)` | 多个参数，元组解包传入 | 列表 |
| `imap(func, iterable)` | 一个参数，**懒加载** | 生成器，边算边出 |

`imap` 和 `map` 的区别是**惰性**：`imap` 返回生成器，结果一个个出，不会一次性把全部结果堆在内存里：

```python
if __name__ == "__main__":
    with multiprocessing.Pool(2) as pool:
        for result in pool.imap(add, [10, 20, 30], [1, 2, 3]):
            print(result, end=" ")
```

```text
11 22 33
```

处理海量任务、结果也很大时，用 `imap` 边算边消费，省内存。

### 6.6.5 用 `Manager` 共享复杂数据

`Queue` 适合"传单个消息"。但如果多个进程要**共享同一个字典/列表**（比如共享一份统计结果、共享一份缓存），`Queue` 就不好使了——你得用 `Manager`：

```python
import multiprocessing

def worker(d, key, val):
    d[key] = val          # 往共享字典里写

if __name__ == "__main__":
    with multiprocessing.Manager() as m:
        d = m.dict()      # 创建一个跨进程共享的字典
        ps = [multiprocessing.Process(target=worker, args=(d, f"k{i}", i)) for i in range(3)]
        for p in ps:
            p.start()
        for p in ps:
            p.join()
        print("主进程通过 Manager 看到:", dict(d))
```

```text
主进程通过 Manager 看到: {'k0': 0, 'k1': 1, 'k2': 2}
```

`Manager` 在后台起一个"管理进程"，真正的数据存在那里，其他进程通过代理（proxy）读写它。所以**子进程写的字典，主进程能读到**。

`Manager` 支持的类型：`m.dict()`（字典）、`m.list()`（列表）、`m.Queue()`（队列）、`m.Value`/`m.Array`（单值/数组）等。

**但注意代价**：`Manager` 背后是进程间通信 + 锁，读写共享数据比本地变量慢得多。所以它是"数据量小、需要跨进程共享"时的选择，不是高频读写的性能方案。

> 一句话记住它：**多进程 = 每个进程一把独立 GIL，用 `Pool.map` 并行、用 `Queue` 通信；Windows 下创建进程的代码必须放 `if __name__ == "__main__"` 里，入口函数必须是顶层函数；多参数用 `starmap`，省内存用 `imap`，共享复杂数据用 `Manager`。**

## 6.7 线程 vs 进程：一张表讲清怎么选

| 维度 | `threading`（线程） | `multiprocessing`（进程） |
|---|---|---|
| 共享内存 | 共享，变量直接读 | 不共享，要 `Queue`/`Pipe` |
| 启动开销 | 小（毫秒级） | 大（每进程要起一个解释器，Windows 上百毫秒级） |
| 内存开销 | 小（共享进程内存） | 大（每进程独立内存） |
| CPU 密集任务 | **无效**（GIL） | **有效**（真并行） |
| I/O 密集任务 | 有效 | 有效但没必要（杀鸡用牛刀） |
| 通信成本 | 低（共享内存） | 高（序列化 + 跨进程拷贝） |
| 崩溃影响 | 一个线程崩，整个进程崩 | 一个进程崩，其他进程不受影响 |
| 适用场景 | 大量并发 I/O、轻量任务 | CPU 密集、需要隔离的任务 |

**选择口诀**：

- **任务在等 I/O**（网络、磁盘、数据库）→ 线程或 `asyncio`（下一节）。
- **任务在烧 CPU**（计算、加密、图像处理）→ 多进程。
- **任务又烧 CPU 又怕崩、要隔离** → 多进程（进程崩溃不影响别的）。
- **任务既轻量又频繁** → 线程（进程启动太贵）。

一句话总结：**线程便宜但被 GIL 卡 CPU，进程贵但能真并行。**

> 一句话记住它：**I/O 密集选线程，CPU 密集选进程；线程共享内存但受 GIL 限制，进程真并行但要付出启动和通信成本。**

## 6.8 `asyncio`：协程与事件循环（重点，JS 玩家主场）

这是你（有 JS 基础的人）最有优势的一节。**`asyncio` 的心智模型，几乎就是 JS 的 `Promise` + 事件循环。**

### 6.8.1 一张对照表，先建立映射

| JavaScript | Python `asyncio` | 说明 |
|---|---|---|
| `async function f() {}` | `async def f():` | 声明协程 |
| `await promise` | `await coroutine` | 等待另一个异步任务 |
| `new Promise(...)` | 协程对象（或 `asyncio.Future`） | 一个"将来会有结果"的东西 |
| `Promise.all([...])` | `asyncio.gather(...)` | 并发等待多个 |
| `setTimeout(() => {}, ms)` | `asyncio.sleep(ms)` | 异步睡眠 |
| 事件循环（浏览器/Node） | 事件循环（`asyncio` 内部） | 单线程调度所有协程 |
| `fetch(url)` | `aiohttp` / `urllib`（异步版） | 异步 HTTP |

如果你写过 `await Promise.all([fetchA(), fetchB()])`，你已经在用 `asyncio` 的思维了。

### 6.8.2 `async def` + `await`：最小例子

```python
import asyncio

async def hello():
    await asyncio.sleep(0.5)   # 异步等待，不阻塞其他协程
    return "hello"

async def main():
    result = await hello()
    print(result)

asyncio.run(main())   # 启动事件循环，跑 main，跑完关闭循环
```

```text
hello
```

三个要点：

1. **`async def` 定义的函数是"协程函数"**，调用它**不会执行函数体**，而是返回一个协程对象（类似 JS 里调用 `async` 函数返回 `Promise`）。
2. **`await` 只能在 `async def` 函数内部用**，它把控制权交回事件循环，让别的协程先跑。
3. **`asyncio.run(协程)` 是程序入口**：创建事件循环、跑协程、关闭循环，一条龙。

### 6.8.3 一个高频坑：忘了 `await`

如果你调用 `async def` 函数却不 `await`，它**根本不会执行**，只拿到一个协程对象：

```python
import asyncio

async def foo():
    return 1

foo()   # ❌ 没 await，函数体没执行，只创建了协程对象
```

运行会看到真实警告：

```text
RuntimeWarning: coroutine 'foo' was never awaited
  foo()
```

这和 JS 里"调用了返回 `Promise` 的函数却不 `await` 也不 `.then`"是完全一样的坑——**任务被创建了但没人等它执行完**。

### 6.8.4 `asyncio.gather`：并发跑多个（对应 `Promise.all`）

```python
import asyncio

async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    print(f"  {name} 完成")
    return f"{name}-result"

async def main():
    results = await asyncio.gather(
        fetch("A", 1),
        fetch("B", 1),
        fetch("C", 1),
    )
    print("gather 返回:", results)

asyncio.run(main())
```

```text
  A 完成
  B 完成
  C 完成
gather 返回: ['A-result', 'B-result', 'C-result']
```

3 个各 1 秒的任务，**总耗时 1 秒**（不是 3 秒）。`gather` 一次性启动所有协程，等全部完成，按传入顺序返回结果列表——和 `Promise.all` 一毛一样。

### 6.8.5 `create_task`：先启动、稍后再等（对应"先创建 Promise 再 await"）

```python
import asyncio

async def task(name, s):
    await asyncio.sleep(s)
    return f"{name} 完成"

async def main():
    t1 = asyncio.create_task(task("A", 1))   # 立即调度，不阻塞
    t2 = asyncio.create_task(task("B", 1))
    await asyncio.sleep(0.5)                  # 这 0.5 秒里，两个任务已经在跑
    print("0.5 秒后，两个任务都在后台跑着")
    results = await asyncio.gather(t1, t2)
    print("结果:", results)

asyncio.run(main())
```

```text
0.5 秒后，两个任务都在后台跑着
结果: ['A 完成', 'B 完成']
```

`create_task` 的作用是**"先把任务挂到事件循环上跑起来，别等我"**，之后你可以先做别的事，最后再 `await` 拿结果。
对应 JS 里"先 `const p = fetch(...)` 拿到 Promise 让它先跑，稍后再 `await p`"的写法。

### 6.8.6 一个坑：`await` 非协程对象

```python
async def main():
    await 42   # ❌ 42 不是 awaitable
```

```text
TypeError: object int can't be used in 'await' expression
```

`await` 后面必须是"可等待对象"（协程、`Task`、`Future`），和 JS 里 `await` 一个非 Promise 会出错同理。

### 6.8.7 事件循环到底是怎么"同时"跑多个协程的

你可能还在想：单线程，怎么做到三个 `sleep(1)` 总共才 1 秒？**答案在 `await` 的语义上。**

`await` 不是"傻等"，而是**"挂起自己，把控制权交回事件循环"**。事件循环手里攥着一堆协程，谁在等 I/O，它就跳过谁、去跑下一个能跑的。画成图：

```text
事件循环（单线程）轮询：
协程A: 开始 → await sleep(1) ──────(挂起等待)──────── → 恢复 → 结束
协程B: 开始 → await sleep(1) ──────(挂起等待)──────── → 恢复 → 结束
协程C: 开始 → await sleep(1) ──────(挂起等待)──────── → 恢复 → 结束
        └────────────────── 1 秒内，三个一起等 ──────────────────┘
```

每个协程执行到 `await` 就挂起，把执行权让给循环；循环发现"A 在等、B 在等、C 也在等，都没到点"，
就空转等 I/O 事件；1 秒后三个几乎同时"醒了"，循环再依次恢复它们。所以总耗时 ≈ 最长的那个等待（1 秒），
而不是三个相加（3 秒）。

**你可以显式地"让出控制权"**，用 `await asyncio.sleep(0)`：

```python
import asyncio

async def main():
    print("A")
    await asyncio.sleep(0)   # 主动让出，让别的协程先跑
    print("C")

async def other():
    print("B")

async def run():
    await asyncio.gather(main(), other())

asyncio.run(run())
```

```text
A
B
C
```

`main` 打印 A 后 `await asyncio.sleep(0)`，主动把控制权让给 `other`，`other` 打印 B，再回到 `main` 打印 C。
**这就是协作式调度**：每个协程靠自己 `await` 让出 CPU，没人让就一直占着（所以阻塞调用会卡死循环，见 6.9）。

再感受一下"等待期间别的协程在跑"：

```python
import asyncio

async def slow():
    print("slow 开始")
    await asyncio.sleep(0.5)
    print("slow 结束")

async def fast():
    print("fast 开始")
    await asyncio.sleep(0.1)
    print("fast 结束")

async def run():
    await asyncio.gather(slow(), fast())

asyncio.run(run())
```

```text
slow 开始
fast 开始
fast 结束      ← 0.1 秒后 fast 先醒，先结束
slow 结束      ← 0.5 秒后 slow 才醒
```

`fast` 等 0.1 秒先醒、先结束，`slow` 等 0.5 秒后醒——**两个协程是穿插执行的，谁先等到谁先跑**。这就是事件循环的核心。

### 6.8.8 `asyncio.wait`：更精细的等待控制

`gather` 是"等全部完成"。有时你需要更精细的控制：**等任意一个完成、加超时、区分完成和未完成**，这时用 `asyncio.wait`。

```python
import asyncio

async def t(name, s):
    await asyncio.sleep(s)
    return name

async def main():
    tasks = [asyncio.create_task(t(n, s)) for n, s in [("A", 1), ("B", 2), ("C", 3)]]
    done, pending = await asyncio.wait(tasks, timeout=1.5)
    print("完成的:", sorted(f.result() for f in done))
    print("还没完成的数量:", len(pending))

asyncio.run(main())
```

```text
完成的: ['A']
还没完成的数量: 2
```

1.5 秒时，`A`（1 秒）完成了，`B`（2 秒）和 `C`（3 秒）还没完成。`asyncio.wait` 返回一个 `(done, pending)` 元组：`done` 是已完成的任务集合，`pending` 是还没完成的任务集合。

两个重要区别（`wait` vs `gather`）：

1. **`gather` 接受协程**（`gather(f1(), f2())`）；**`wait` 必须接受 `Task`**（要先用 `create_task` 包起来）。如果你直接 `wait(f1(), f2())`，会看到真实报错：

```text
TypeError: Passing coroutines is forbidden, use tasks explicitly.
```

2. **`wait` 支持 `timeout` 和 `return_when`**，能"等第一个完成就返回"：

```python
done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
```

`return_when` 可选：`FIRST_COMPLETED`（第一个完成就返回）、`ALL_COMPLETED`（默认，全完成）、`FIRST_EXCEPTION`（第一个抛异常就返回）。

> 一句话记住它：**`asyncio` 就是 Python 版的 Promise + 事件循环：`async def` 造协程、`await` 等它、`gather` 并发等多个、`create_task` 先跑后等、`asyncio.run` 是入口；`await` 是"挂起并让出控制权"，所以单线程也能"同时"等一堆 I/O；要加超时或"先完成先返回"就用 `asyncio.wait`（它只收 Task）。**

## 6.9 线程 vs `asyncio`：I/O 密集选哪个

同样是"并发 I/O"，线程和 `asyncio` 都能干，选谁？这是面试和实战都爱问的。

| 维度 | `threading` | `asyncio` |
|---|---|---|
| 并发模型 | 多线程（抢占式调度） | 单线程协程（协作式调度） |
| 单任务开销 | 线程，约几 KB~MB 栈内存 | 协程，极小（一个对象） |
| 能开多少个 | 几百~几千个就吃力 | **几万、几十万个**没问题 |
| 适合 | 少量并发、或要调阻塞库 | 海量并发 I/O（几万连接） |
| 心智负担 | 有锁、竞态、死锁 | 基本无锁（单线程） |
| 前提 | 无 | **所有 I/O 必须用异步版本**（否则一个阻塞调用卡死整个循环） |

**核心差别在第 4、6 行**：

1. **协程比线程便宜得多**，所以 `asyncio` 能轻松撑起几万个并发连接（线程做不到）。
2. 但 `asyncio` 要求**你调用的每个 I/O 操作都是异步版**。如果你在一个协程里调了 `time.sleep(1)` 或阻塞的 `requests.get()`，整个事件循环被卡死，所有协程一起等。

第二点是最容易翻车的地方。看真实问题：

```python
import asyncio
import time

async def bad():
    time.sleep(1)        # ❌ 阻塞的 sleep，卡死整个事件循环
    print("bad 完成")

async def main():
    await asyncio.gather(bad(), bad(), bad())

asyncio.run(main())
```

上面这个写法，`time.sleep` 是阻塞的，三个协程**串行执行，总耗时 3 秒**。正确应该用 `await asyncio.sleep(1)`。

**那如果我不得不用一个阻塞的库呢？** 用 `asyncio.to_thread` 把它丢到线程池，不阻塞事件循环：

```python
import asyncio
import time

def blocking_call():
    time.sleep(1)
    return "阻塞调用结束"

async def main():
    result = await asyncio.to_thread(blocking_call)   # 扔到线程池跑
    print(result)

asyncio.run(main())
```

```text
阻塞调用结束
```

`asyncio.to_thread` 把阻塞函数丢进一个后台线程池执行，事件循环继续跑别的协程。这是"协程 + 线程"混用的正确姿势。

**选型口诀**：海量并发、且能全用异步库 → `asyncio`；少量并发、或要大量调用同步阻塞库 → 线程。

### 6.9.5 实战：用 `asyncio` 并发抓取多个接口（模拟）

把前面学的串起来，写一个"并发抓取多个 URL"的完整例子（用 `asyncio.sleep` 模拟网络请求，这样不用装任何第三方库）：

```python
import asyncio
import time

# 模拟一个 HTTP 请求：耗时随机，返回结果
async def fetch(url):
    delay = {"api/a": 1, "api/b": 1, "api/c": 1}[url]
    await asyncio.sleep(delay)          # 模拟网络延迟
    return f"{url} 返回的数据"

async def main():
    urls = ["api/a", "api/b", "api/c"]
    start = time.perf_counter()
    results = await asyncio.gather(*(fetch(u) for u in urls))
    elapsed = time.perf_counter() - start
    for r in results:
        print(r)
    print(f"3 个接口并发抓取耗时 {elapsed:.2f}s（串行要 3s）")

asyncio.run(main())
```

```text
api/a 返回的数据
api/b 返回的数据
api/c 返回的数据
3 个接口并发抓取耗时 1.00s（串行要 3s）
```

两个你可能没见过的语法：

1. **`*(fetch(u) for u in urls)`**：`fetch(u) for u in urls` 是生成器表达式，`*` 把它展开成三个独立参数传给 `gather`。等价于 `gather(fetch(urls[0]), fetch(urls[1]), fetch(urls[2]))`。
2. **`await asyncio.gather(...)`**：等所有请求都返回，拿到结果列表。

真实项目里，把 `asyncio.sleep` 换成异步 HTTP 库（如 `aiohttp`、`httpx` 的异步模式）就能真的并发抓取。**核心套路完全一样**：定义 `async def` 任务 → `gather` 并发等 → 拿结果。

> 一句话记住它：**`asyncio` 协程比线程便宜，能扛几万并发，但前提是每个 I/O 都得是异步版；实在要调阻塞代码，用 `asyncio.to_thread` 丢线程池；并发抓取的套路永远是 `async def` 任务 + `gather`。**

## 6.10 `concurrent.futures`：线程和进程的统一接口

你可能会觉得 `threading` 和 `multiprocessing` 两套 API 有点割裂。标准库给了个统一层——`concurrent.futures`，用**同一套代码**切换线程池和进程池，只改一个类名。

```python
import time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def square(x):
    time.sleep(0.5)          # 模拟 I/O
    return x * x

# 线程池版
with ThreadPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(square, [1, 2, 3, 4]))
print("线程池结果:", results)

# 进程池版（只改类名，其余不变）
with ProcessPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(square, [1, 2, 3, 4]))
print("进程池结果:", results)
```

```text
线程池结果: [1, 4, 9, 16]
进程池结果: [1, 4, 9, 16]
```

两种用法：

- **`executor.map(func, iterable)`**：和内置 `map` 一样，按顺序返回结果，简单。
- **`executor.submit(func, *args)`**：返回一个 `Future` 对象，之后用 `.result()` 拿结果，更灵活：

```python
with ThreadPoolExecutor(max_workers=4) as ex:
    futures = [ex.submit(square, i) for i in range(4)]
    results = [f.result() for f in futures]
print(results)
```

```text
[0, 1, 4, 9]
```

**`Future` 对象 = JS 的 `Promise`**：一个"将来会有结果"的占位符，`.result()` 阻塞等待结果。

**选型提示**：`ThreadPoolExecutor` 适合 I/O 密集（内部就是线程池），`ProcessPoolExecutor` 适合 CPU 密集（内部就是进程池）。
**它同样受 GIL 约束**——`ThreadPoolExecutor` 跑 CPU 密集任务不会变快，那得用 `ProcessPoolExecutor`。

### 6.10.1 `as_completed`：谁先完成先处理谁

`map` 和 `submit` 都按"提交顺序"返回结果。但有些场景你想"谁先算完就先处理谁"（比如抢答、实时展示），这时用 `as_completed`：

```python
import time
from concurrent.futures import ThreadPoolExecutor, as_completed

def slow_square(x):
    time.sleep(0.5 - x * 0.1)   # x 越大，睡得越短，完成越快
    return x * x

with ThreadPoolExecutor(max_workers=4) as ex:
    futures = [ex.submit(slow_square, i) for i in range(1, 5)]
    for f in as_completed(futures):   # 按完成顺序，不是提交顺序
        print("完成一个:", f.result())
```

```text
完成一个: 16     ← x=4 睡得最短，最先完成
完成一个: 9
完成一个: 4
完成一个: 1      ← x=1 睡得最长，最后完成
```

`as_completed(futures)` 返回一个迭代器，**谁先完成，谁先被 yield 出来**。对比 `map`（按提交顺序 `[1, 4, 9, 16]`），`as_completed` 的顺序是 `[16, 9, 4, 1]`。

### 6.10.2 任务抛异常怎么办

如果 `submit` 的任务内部抛了异常，`Future.result()` 会**把异常重新抛出来**（而不是静默吞掉）：

```python
from concurrent.futures import ThreadPoolExecutor

def risky(x):
    if x == 0:
        raise ValueError("x 不能是 0")
    return 10 / x

with ThreadPoolExecutor(max_workers=2) as ex:
    futures = [ex.submit(risky, i) for i in [2, 0, 5]]
    for f in futures:
        try:
            print(f.result())
        except ValueError as e:
            print("捕获到任务异常：", e)
```

```text
5.0
捕获到任务异常： x 不能是 0
2.0
```

注意：异常在**调用 `.result()` 的时候**才抛出，而不是在任务执行的时候。所以要记得在 `result()` 外面包 `try/except`，否则一个任务失败会拖垮整个处理流程。

### 6.10.3 选型决策：一图看清线程 / 进程 / 协程怎么选

把全章的结论浓缩成一张决策图。当你遇到一个"想提速"的任务，按这个顺序问自己：

```text
任务很慢，怎么提速？
│
├─ 是 I/O 密集（在等网络/磁盘/数据库）？
│    │
│    ├─ 并发量大（几千~几万连接）且能全用异步库 → asyncio 协程
│    │
│    └─ 并发量小（几百以内）或要调大量同步阻塞库 → threading 线程
│
└─ 是 CPU 密集（在算、在循环、在加密）？
     │
     ├─ 能用 numpy/pandas 等 C 库 → 优先用它们（内部释放 GIL，多核真并行）
     │
     └─ 纯 Python 计算 → multiprocessing 进程（进程数 ≈ CPU 核数）
```

三条补充铁律：

1. **进程数别超过 CPU 核数**：开 16 核机器上开 64 个进程，反而因频繁切换变慢。`multiprocessing.cpu_count()` 能拿到核数。
2. **线程和协程都救不了 CPU 密集**：它们都跑在一个 GIL 下（协程干脆是单线程），CPU 计算该多慢还多慢。
3. **优先用最省事的**：能用 `concurrent.futures` 就别手写 `threading`；能用 `asyncio` 就别手写事件循环。抽象层越高越不容易出错。

### 6.10.4 并发不是免费的：什么时候别并发

最后泼一盆冷水：**并发不是万能药，用错了反而更慢。** 并发本身有成本，下面是三个常见"越并发越慢"的场景：

**场景一：任务太轻，调度开销 > 任务本身。** 开 100 个线程去执行"加一"这种微秒级任务，线程创建/切换的时间比任务本身还长，总耗时反而超过串行。**并发适合"单个任务有一定耗时"的场景**，任务越小越不划算。

**场景二：进程数超过 CPU 核数。** CPU 密集任务开 4 个进程（4 核机器）能 4 倍加速；开 64 个进程，进程在 4 个核上疯狂切换，切换开销把收益吃光，比 4 个进程还慢。**经验值：进程数 = CPU 核数，最多略超一点。**

**场景三：所有任务争抢同一个资源。** 比如 100 个线程都往同一个文件写、都抢同一把锁、都打同一个数据库连接——并行度被这个"瓶颈资源"卡死，甚至因为锁竞争比串行还慢（Amdahl 定律：整体提速被"不可并行的部分"限制）。

**判断"要不要并发"的三个问题**：

1. 任务是不是真的能拆成互不依赖的几块？（有依赖就只能串行）
2. 单块任务的耗时，是否明显大于并发调度开销？（太轻就别并发）
3. 任务之间会不会争抢同一个瓶颈资源？（抢资源就别指望线性提速）

三者都满足，才值得上并发。**一句话：先测串行基线，再测并发版本，用数据决定，别凭感觉。**

> 一句话记住它：**`concurrent.futures` 用一套 API（`map`/`submit`）统一线程池和进程池；`Future` 就是 Python 版的 Promise；`as_completed` 按完成顺序返回，异常在 `.result()` 时抛出；但并发有调度成本，任务太轻、进程太多、资源被抢时，并发反而更慢。**

## 6.11 本章常见坑速查

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| CPU 密集用多线程 | 开了 4 线程，速度和单线程一样甚至更慢 | GIL 同一时刻只让一个线程跑字节码 | CPU 密集改用多进程或 numpy |
| 协程里调阻塞函数 | `asyncio` 并发失效，任务变串行 | `time.sleep`/`requests.get` 阻塞了整个事件循环 | 用 `await asyncio.sleep` 或异步库；或 `asyncio.to_thread` |
| 调 `async` 函数不 `await` | 函数体根本没执行，还报 `RuntimeWarning: coroutine was never awaited` | `async def` 调用只创建协程对象，不执行 | 记得 `await`（或 `create_task` + `await`） |
| `await` 非协程 | `TypeError: object int can't be used in 'await' expression` | `await` 只认可等待对象 | 只 `await` 协程/Task/Future |
| 事件循环里再调 `asyncio.run` | `RuntimeError: asyncio.run() cannot be called from a running event loop` | 一个线程同一时刻只能有一个运行中的事件循环 | 循环内用 `await`，别嵌套 `asyncio.run` |
| Windows 多进程没加守卫 | 程序卡死、子进程无限套娃 | spawn 会重新导入脚本，顶层代码被反复执行 | 创建进程的代码放 `if __name__ == "__main__"` 里 |
| 进程入口是局部函数/lambda | `AttributeError: Can't get local object '...'` | spawn 用 pickle 传函数，局部函数序列化不了 | 入口函数提为模块顶层函数 |
| 忘记 `join()` 线程 | 主线程先退出，子线程没跑完就被中断 | 主线程不 `join` 不会等子线程 | 需要等结果就 `join()` |
| 进程间直接共享变量 | 子进程里改的变量，主进程看不到 | 进程内存隔离，不共享 | 用 `Queue`/`Pipe`/`Manager` 通信 |
| `args=("x")` 少了逗号 | 报错或参数被打散 | `("x")` 是字符串不是元组，`args` 必须是元组 | 单个参数写成 `("x",)` |

---

## 6.12 本章小结

- **先分 CPU 密集 / I/O 密集**：慢的原因不同，提速手段不同。
- **并发 ≠ 并行**：并发是交替执行，并行是真同时；事件循环/协程是并发，多进程是并行。
- **GIL**：CPython 的全局解释器锁，同一时刻只有一个线程跑字节码；为了简化内存管理和 C 扩展而存在；**不限制** I/O 密集、多进程、C 扩展、协程。
- **线程 `threading`**：适合 I/O 密集（等 I/O 时释放 GIL），`start`/`join`/`daemon`。
- **进程 `multiprocessing`**：绕开 GIL 做 CPU 并行，`Pool.map` + `Queue` 通信；Windows 要 `__main__` 守卫 + 顶层函数。
- **`asyncio`**：Python 版 Promise + 事件循环，`async def`/`await`/`gather`/`create_task`/`asyncio.run`；协程比线程便宜，能扛海量并发，但要求 I/O 全异步。
- **`concurrent.futures`**：统一线程池/进程池接口，`map`/`submit`，`Future` 对应 Promise。
